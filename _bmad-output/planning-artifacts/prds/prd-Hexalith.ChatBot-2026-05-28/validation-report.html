Adversarial review — Critical findings

review-adversarial-general.md

A 1,260-line incantation of governance vocabulary that promises a fully governed, fail-closed, cross-surface, multi-tenant, audit-perfect, AI-mediated, idempotent email-to-project platform — and then calls it an MVP delivered in one release. The PRD repeats the same five risk-management adjectives in every section while quietly punting nearly every quantitative target to "tenant policy," "evaluation dataset," "operating baseline," or "depends on A1–A9." It has a clear thesis and a usable lifecycle model, but the so-called "minimum slice" is wider than most teams ship in two quarters, and the precision/recall, latency, RPO/RTO, adoption, and accessibility numbers are presented as commitments without a single referenced baseline measurement. Not yet a buildable PRD — a maximalist policy manifesto that hopes architecture and stories will silently absorb the scope it refuses to cut.

critical

C1. "Minimum Release Slice" is wider than the rest of the PRD admits — the MVP is not an MVP

lines 213–229; 865–893
The "minimum" slice enumerates nine workstreams; the must-have list expands this into 25 bullets including tenant isolation across nine actor types, Keycloak, Aspire, dependency failure handling for seven dependency classes, and security tests across nine actor types. This is the entire product, not a vertical slice. The PRD admits "the release is broad for a single MVP" (line 942) and then refuses to cut anything because "trust requires the full vertical path." Without explicit, ruthless sequencing, this PRD will either slip indefinitely or quietly drop fail-closed behavior under deadline pressure — which the PRD itself names as the worst possible outcome.
Fix: sequence the minimum slice into three or more increments. Increment 1: deterministic association + UI review + audit lookup + one surface (UI). CLI/MCP parity, AI mediation, and outbound send move to later increments.
critical

C2. Precision/recall targets have no provenance and no dataset behind them

line 141; A9 line 1159
"95% precision," "90% recall," "0 critical false-positives" against "seeded evaluation datasets" — no baseline, no dataset size, no class balance, no labeling protocol, no inter-rater agreement, no owner. A9 reveals the dataset is still an assumption. The acceptance threshold is anchored to a dataset that does not exist yet, will be built by an unnamed party, and will be calibrated by the same team that has to hit the threshold — a textbook circular acceptance criterion.
Fix: commit a named owner, sampling protocol, target dataset size, and refresh cadence — or delete the precision/recall/false-positive numbers from Success Criteria.
critical

C3. T_high and T_low are fictional knobs with no operating range

line 120; FR9 line 1018
Confidence thresholds introduced as tenant policy. Nothing specifies the underlying scoring function, the domain of the score, how a tenant admin would calibrate against precision/recall targets without statistical training, what happens if a deployment ships with bad defaults, or who validates a tenant's threshold change before it goes live. A misconfigured T_high of 0.1 will auto-associate everything; no guardrail is named. The decision log's "clarified" resolution is "tenant policy" — that is the punt, not the resolution.
Fix: specify the score domain, safe-default initial values, the calibration protocol against the evaluation dataset, and the guardrail on threshold changes (review queue, audit event, ramp limits).
critical

C4. "Fail closed" is repeated 20+ times but has multiple silent escape hatches

examples lines 116, 154, 472, 476, 595, 597, 716, 768, 771, 1109, 1184
NFR15 allows non-security-sensitive invalid transitions to silently mutate state when audit is down — who decides which is which? NFR22 + line 771: risk classification can't run during AI provider outage, so approval routing can't run, so the "approval-required" risk class collapses to "human guesses without classifier." Line 476 implicitly authorizes non-risky actions to proceed without audit; "risky" is behaviorally defined, so a wrongly-classified action can write project state with no audit. The phrase is used as a token, not a contract.
Fix: enumerate every code path that can write durable state. Define "fail closed" at each one as an invariant (not a behavioral test). Close the NFR15 "security-sensitive" carve-out.
critical

C5. Cross-surface parity is enforced by aspiration, not by an invariant

lines 161–167; FR81–FR86; lines 723–728
UI/CLI/MCP "expose the same core governed operations" with "equivalent authorization outcomes, state transitions, audit behavior, and redaction semantics" — enforcement is "contract tests" + "automated parity tests." Parity is a quality the system has, not an invariant the architecture forbids violating. The first time CLI gains a feature UI lacks (or vice versa), parity drifts and tests catch some fraction. For a security-critical surface, "we'll test for parity" ≠ "we cannot construct a non-parity code path."
Fix: require a single shared command pipeline at the architectural layer that all three surfaces invoke. Parity becomes a structural property, not a test outcome.
critical

C6. "Single release" with all eight journeys is unbuildable on the named team

line 847; lines 851–863
Singular frontend, singular CLI/MCP, singular security engineer. The release must deliver 8 user journeys + system journey, 27 commands, 14 queries, 9 lifecycle states with transitions, 3 first-class surfaces with parity, WCAG 2.2 AA, full audit reconstructability, RPO ≤ 15 min / RTO ≤ 4 hrs, seeded evaluation datasets, and pilot with 4 consecutive weeks. No team-load reconciliation anywhere. The decision log claims "MVP sequencing within the single release" was addressed, but sequencing-within-a-release ≠ cutting scope. This is a 6–12 person-year backlog packaged as one release.
Fix: reconcile team to scope or scope to team. Grow the team to match the named bar, or shrink the release to what the named team can ship with margin.

Adversarial review — High findings (11)

review-adversarial-general.md

Eleven High findings — the load-bearing decoration pattern. Magic numbers without derivation, "tenant policy" as universal escape hatch, AI risk classifier described as a capability with no implementation, "allowlisted commands" with no allowlist, evaluation dataset nobody owns, idempotency promised across heterogeneous operations with no key contract, approval fatigue acknowledged but mitigation hand-waved, lifecycle terminal states that are not terminal, accessibility bar that one frontend engineer cannot meet, no admin/debug bypass colliding with tenant-admin operational dashboards.

high

H1. "Magic constants" appear with no derivation

lines 176–180, 1172, 1196–1199, 1221, 1240–1241
Pilot thresholds, cache staleness, p95 latencies, page sizes, RPO/RTO, projection rebuild — every number is a "default" tenant policy can override (A4). A default with no derivation is a guess wearing a number.
Fix: for each named threshold, either cite the baseline measurement / user research / throughput model that produced it, or label it explicitly as a starter value to be calibrated in the first pilot increment.
high

H2. "Tenant policy" is the universal escape hatch

A4–A6 lines 1154–1156; NFR9, NFR23; many others
Confidence thresholds, AI provider telemetry/retention/region, audit retention, low-risk AI permission, residency, performance baselines, notification routing, retry policy, rate limits, accessibility thresholds, consent rules, RBAC restrictions — all deferred to tenant policy with no master list and no schema. Without a policy contract: admins configure an undocumented surface, security can't validate it's closed under safe states, tests can't enumerate combinations, and "tenant policy" becomes the place every unresolved decision hides.
Fix: author a Tenant Policy Schema as a first-class artifact. Every "tenant policy" reference resolves to a key with allowed values and safe defaults. Put it under change control.
high

H3. Risk classification is a system capability without naming the classifier

lines 1056–1063; FR39 line 1071
FR39 says the system "can classify AI action requests by risk." Heuristic? Tags? LLM? Static allowlist? The risk table includes "expose file content in generated output" — determining whether an action exposes file content requires reasoning about non-deterministic model output. The entire approval gate depends on this classifier being correct. The decision log does not record this as resolved.
Fix: name the classifier mechanism, its error rate as a first-class risk, the fallback for misclassification, and the audit chain when classification disagrees with reviewer action.
high

H4. "Allowlisted commands" is the load-bearing security control with no allowlist

lines 199, 205, 211, 226, 502, 883; A8 line 1158
"Allowlist of project collaboration commands" appears repeatedly as the safety boundary for AI execution. The PRD does not name a single command in the allowlist. A8 records it as an assumption. The 27-command catalog (lines 647–673) contains the ones an AI would invoke — so either the allowlist is the whole catalog (concept decorative) or a subset (unspecified). Acceptance tests cannot be written against an unspecified subset.
Fix: enumerate the MVP allowlist explicitly. State the criteria for adding/removing entries. Make the allowlist a versioned artifact under change control.
high

H5. The "evaluation dataset" is load-bearing and nobody owns it

A9 line 1159; lines 141, 170–172, 1139
Dataset basis for precision/recall (C2), pilot validation, regression history (FR92), and NFR50's "100% audit field presence." Owner of A9 is "QA / Product" — shared ownership means nobody owns it. No spec for cardinality, label taxonomy, source provenance, redaction, refresh cadence, drift handling, or adversarial-example protocol. NFR50's "100%" is a tautology and precision/recall targets are unfalsifiable.
Fix: single named owner. Sampling frame, target size, label taxonomy, refresh cadence, adversarial-example protocol all written before pilot starts.
high

H6. "Audit completeness" is invoked as a metric but never defined

lines 159, 162, 466, 795; NFR50 line 1231
Field-presence ≠ completeness. NFR50's "100% required field presence" on the evaluation dataset is a field-presence test, not a completeness test, and measures the test corpus, not production.
Fix: define audit completeness as a production observable. "Fraction of state-mutating operations whose audit chain reconstructs the operation end-to-end" is one workable definition; pick one and instrument it.
high

H7. Idempotency promised across heterogeneous operations with no key contract

NFR13 line 1182; FR90 line 1137; line 698
Mailbox intake, attachment capture, association decisions, approvals, command execution, outbound communication, notifications, audit projection — each class has different identity semantics. The PRD doesn't say what an idempotency key is composed of, how long the replay window lasts, or what "equivalent inputs" means when a duplicate approval comes in with a different actor at a different time.
Fix: per operation class, define key composition, replay window, equivalence rule, and conflict response. Put the resulting contract in the addendum or an architecture appendix.
high

H8. Approval fatigue acknowledged but mitigation is hand-waved

line 547; NFR46 line 1224
"Must prevent approval fatigue by prioritizing, grouping, and suppressing duplicate or low-value notifications according to tenant policy." Prioritization heuristic? Grouping criteria? Suppression policy? The very first time a user has 40 approvals in their queue, they will rubber-stamp them, and the governance promise dies that day.
Fix: design the queue/grouping flow as a first-class FR with concrete grouping criteria (by project, by risk class, by external party) and a per-user notification rate ceiling. Don't leave it as one NFR line.
high

H9. The lifecycle table claims Rejected and Failed are terminal "unless reprocessed" — that is not terminal

lines 380–392
"Yes, unless reprocessed" reduces "terminal" to "currently inactive." A real lifecycle either marks these terminal and forces reprocess to create a new workflow instance with a new ID, or admits they are non-terminal and models the reprocess transition. The PRD does both at once.
Fix: pick one. Recommended: terminal states are terminal; reprocess creates a new workflow instance with a new ID and an audit link to the predecessor.
high

H10. WCAG 2.2 AA + screen-reader + keyboard review on one frontend engineer

NFR60 line 1247; team list line 847
Ambiguous-association UI alone (multi-candidate ranked list with evidence snippets, confidence bands, reject/defer/correct/escalate actions, audit trail, redaction) is a multi-month accessibility effort. One frontend engineer. Either the bar is theater or the team is wrong; both cannot be true.
Fix: resolve via C6 (team/scope reconciliation). Either commit external accessibility consultancy, or narrow NFR60 to the increment-1 surfaces with explicit deferrals for the rest.
high

H11. "No admin/debug bypass" + required tenant-admin operational dashboards is unworkable

line 694; FR53, FR67–FR75
Tenant admins must operate mailbox health, unresolved-party queues, ambiguous-association queues, approval queues, retry failures, duplicate suppression, authorization failures, audit projection. Reviewing "authorization failures" without an authorization-bypass surface means admins see "user X failed to access resource Y" without being able to see resource Y. Fine in principle but creates a complex admin permission model the PRD does not describe.
Fix: design the tenant-admin permission model explicitly — what an admin can see vs. operate on, with which audit obligations. Likely warrants its own FR group.
