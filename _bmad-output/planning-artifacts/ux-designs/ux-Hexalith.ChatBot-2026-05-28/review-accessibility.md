# Accessibility Review — Hexalith.ChatBot

## Overall verdict — thin

The pair contains a strong June 2026 accessibility foundation, but it is no longer a complete WCAG 2.2 AA implementation contract for the current product. Keyboard/focus basics, landmarks, disabled explanations, error summaries, touch targets, forced-colors, reduced motion, localization expansion, and redaction-safe off-surface actions are unusually concrete. However, the current PRD has added load-bearing conversation classifications, source-versus-AI provenance, evidence freshness, and correction-propagation states that the final spines do not model; the newer governed chat surface also lacks safe screen-reader behavior for incremental output.

No finding below says that Fluent UI or FrontComposer is inaccessible. The problem is that inheritance cannot supply product semantics: it cannot decide what an AI summary is, when evidence expiry blocks approval, which correction state is active, or which asynchronous change deserves announcement. A downstream implementer can build the older surface set accessibly from this pair, but cannot implement the current governed workflows without consulting other documents and inventing accessibility behavior.

Severity counts: **critical 0 · high 5 · medium 4 · low 0**.

## Scope and strengths

This review assessed `DESIGN.md` and `EXPERIENCE.md` as the downstream contract, checked all four resolving frontmatter sources, and compared the pair with the current Hexalith UX baseline and the binding UX package index/addenda. The lens covered WCAG 2.2 AA keyboard and focus behavior, landmarks, live regions and observed updates, disabled affordances, status/error communication, responsive/touch behavior, forced colors and non-color meaning, reduced motion, localization, redacted export/read-aloud behavior, and state/flow accessibility.

Strong commitments already present include:

- The keyboard model requires equivalent labelled controls, unique names for repeated landmarks, focus landing/return for dialogs, stable stream focus, safe Escape behavior, and reachable disabled reasons (`EXPERIENCE.md:150-172`).
- The state-to-feedback matrix distinguishes user-triggered from observed changes, prevents historical content announcements, specifies `aria-busy`, error-summary focus, announcement politeness, and background-update behavior (`EXPERIENCE.md:123-139`).
- Disabled approval controls must use focusable `aria-disabled="true"` with a reason or an adjacent focusable explanation; tooltip-only explanations are rejected (`EXPERIENCE.md:80,170-172`).
- Existing errors and blocked states have persistent inline explanations, safe next actions, focus recovery, and redaction-safe language (`EXPERIENCE.md:131-138,205-213`).
- Touch sizing and responsive fallback are testable: 44×44 CSS px for touch-primary actions where layout allows, WCAG 2.2's 24×24-or-spacing floor for compact controls, and no compact-only destructive/approval controls on phone or tablet (`EXPERIENCE.md:201,232-244`).
- Contrast targets cover normal text, status pairs, non-text UI, links, and focus indicators; dark mode and forced-colors preserve meaning through text/icon/border rather than fill alone (`DESIGN.md:153-166`).
- Reduced motion suppresses shimmer, row movement, streaming animation, and non-essential transitions; progress retains a textual equivalent and background updates do not force-scroll (`EXPERIENCE.md:183-188,200`).
- English/French expansion, locale-aware formatting, non-concatenated accessible names, and critical-column retention are explicit (`EXPERIENCE.md:224-230`).
- Export, copy, download-transcript, read-aloud, and other off-surface affordances must reuse visual redaction and communicate that redaction to screen-reader users (`EXPERIENCE.md:202-203`).

## Findings

### Critical (0)

No critical finding. The inherited component system and existing behavioral floor prevent the pair from being broken wholesale.

### High (5)

- **[high] The final spines have drifted behind their live sources and split the accessibility contract across unreferenced peers.** Both files still say `updated: 2026-06-05` while resolving to a PRD that now contains the approved first-class chat surface, ten named UI surfaces, newer component affordances, and later state requirements (`DESIGN.md:4-11`; `EXPERIENCE.md:3-10`; PRD `prd.md:317,524-537,1194-1201,1324-1325,1441`). The binding package index now warns that reading one file is insufficient and adds three supplemental UX contracts, including a conformance addendum changed again on 2026-08-26 (`index.md:8-18`; `implementation-conformance-addendum-2026-07-17.md:34-56`). That contradicts the spine pair's role as the extractable design/experience contract and makes accessibility behavior depend on discovery order. *Fix:* run an Update pass that refreshes both dates, reconciles the current PRD surface inventory, and distills every binding accessibility delta from the indexed elaborations/addendum into the appropriate DESIGN component and EXPERIENCE component/state/interaction rows. Cite the package index or supplemental inputs in frontmatter for provenance, but do not leave required behavior only in those side documents.

- **[high] Source evidence and AI-generated summaries are not programmatically distinguished as required.** The current PRD requires the label `AI summary`, model/version/timestamp/source-ID provenance before the generated content, source evidence shown by default, and an opt-in disclosure for the summary with non-color distinction (`prd.md:1198-1201`; NFR64 at `prd.md:1469-1472`). The pair offers an actor badge, generic evidence drawer, and AI proposal panel, but no visual component or behavioral pattern for an AI summary versus authoritative source evidence (`DESIGN.md:217-223`; `EXPERIENCE.md:73-81,174-180,198`). A screen-reader user can therefore hear generated interpretation without first hearing that it is AI-generated or how to reach its source. *Fix:* add paired `Source evidence` and `AI summary` components to both spines. Require accessible section headings, provenance before summary content in DOM/reading order, a keyboard-operable disclosure whose expanded state is announced, source evidence expanded by default, focus preservation on toggle, and text/structure—not color alone—to carry the distinction.

- **[high] Evidence freshness and the `evidence-expired` approval block are absent from the component and state contracts.** The current PRD requires every evidence reference to expose timestamp plus `fresh` / `stale` / `expired`, forbids approval against expired evidence, and requires a visible `evidence-expired` disabled reason (`prd.md:1441`). The existing Evidence chip only summarizes a reason and the state model includes generic stale filters/dependency degradation, not per-evidence freshness or its safety transition (`EXPERIENCE.md:76,101,115-120,125-139`). DESIGN defines information/warning semantics but no freshness component or state appearance (`DESIGN.md:77-84,146-166`). *Fix:* add an evidence-freshness chip/pattern to both spines, including visible text, timestamp association, accessible name/description, forced-colors treatment, and light/dark contrast. Add `fresh`, `stale`, and `expired` states to AI Action Review and evidence-bearing surfaces. When open evidence expires, announce the transition once, preserve review focus, make Approve `aria-disabled` with the associated `evidence-expired` reason, and route an attempted submission to the focused error summary.

- **[high] `Correcting` and `Correction-delayed` are missing as canonical accessible states.** The spine jumps from corrected association to generic projection-pending or degraded treatment (`EXPERIENCE.md:98,103,107,114-120,207-213`), but the source requires `Correcting` while derived stores invalidate, progress plus estimated completion, prohibition of AI use, and `Correction-delayed` with owner, next safe action, and incident significance (`prd.md:450-451,1324-1325`). Generic partial/degraded handling does not tell implementers what must be exposed to assistive technology or when the AI affordance becomes unavailable. *Fix:* add both named states to the state and per-surface tables. Specify visible and programmatic state labels; determinate `progressbar` semantics only when a meaningful value exists, otherwise textual indeterminate status; one deduplicated polite transition announcement; estimated completion; owner and safe next action for delay; and an accessible disabled reason on AI actions until correction completes. Preserve focus and selection when progress updates.

- **[high] Incremental AI output has no bounded screen-reader announcement policy.** The new interaction correctly supplies stable keyboard-reachable Stop/Cancel, polite `Response stopped`, focus return, reduced motion, and no forced scrolling (`EXPERIENCE.md:151,181,183-188`), but it never says whether streaming token/chunk mutations are live. The general instruction to announce only user-relevant changes does not prevent an implementation from putting the progressively changing response inside `aria-live`, which can repeatedly interrupt reading, nor does it define start/completion/error behavior for a user waiting on the response (`EXPERIENCE.md:127-139,181,194-200`; `epic10-chat-surface-elaboration.md:37-47`). *Fix:* keep the streamed response container out of a live region (`aria-live="off"`), expose regular document semantics for reading it, and use a separate deduplicated status region for only `Generating`, `Response complete`, `Response stopped`, and generation failure. Announce each transition once, never per token/poll; distinguish the current user's generation from observed updates; preserve focus and scroll position; and retain the existing Stop/Cancel focus-return rule.

### Medium (4)

- **[medium] The informational/actionable classification and detailed “why” affordance have no local accessible component behavior.** The PRD requires every email to carry a text classification, actionable items to expose detected intent plus review/capture/dismiss, and the “why” panel to expose signal class, matched value, confidence/band, actor, timestamp, and correction links (`prd.md:1194-1201`). Actor, Evidence chip, and Evidence drawer rows are too generic to define the badge/message relationship or disclosure reading order (`EXPERIENCE.md:73-78`). *Fix:* add a classification badge and association-explanation pattern to both spines. Require `informational` / `actionable` text in the message's accessible description, associate detected intent and next action with the message, make the “Why this project?” disclosure keyboard-operable with announced expanded state and focus return, and structure its facts as labelled data. Do not announce classification changes for off-screen/observed rows; announce a changed current item once.

- **[medium] English/French localization omits language metadata and mixed-language content behavior.** Expansion, formatting, and string-composition rules are strong, but nothing requires the page language or language of parts (`EXPERIENCE.md:224-230`). This product displays external email, attachment metadata, AI output, and quoted source material that may differ from the selected UI language; without `lang`, screen readers can pronounce content using the wrong voice even when every label is translated. *Fix:* require the root/page `lang` to follow the selected UI locale and apply `lang` to known-language message bodies, AI summaries, and quoted source passages when they differ. Persist the locale across navigation, preserve stable machine codes without misleading language tagging, and include EN/FR screen-reader review in the per-surface acceptance evidence.

- **[medium] Focus visibility is specified for contrast and order, but not for WCAG 2.2 Focus Not Obscured.** The product uses persistent navigation, project headers, drawers/sheets, side panels, dialogs, and potentially sticky dense-grid headers (`DESIGN.md:164,180-190`; `EXPERIENCE.md:167-172,232-244`). A correctly ordered and high-contrast focus indicator can still sit behind sticky chrome or an opened non-modal panel. *Fix:* add a focus-visibility rule requiring the focused control to remain at least partially unobscured by author-created content at every breakpoint, including after programmatic focus moves. Define scroll margins for persistent/sticky chrome, test focus at 200% and 400% zoom, and allow scrolling only to reveal the focused target—not to force users away from conversation/audit history.

- **[medium] The newer Association Review radiogroup/decision-bar behavior is not defined in the spine.** The binding addendum now declares the candidate radiogroup and safe-next-action decision bar a single primary workflow outside the accordion (`implementation-conformance-addendum-2026-07-17.md:34-44`), while the spine says only “candidate selected” and “fully keyboard-operable” (`EXPERIENCE.md:75,95-96,115,199`). This leaves selection, navigation, validation, and commit behavior to inference. *Fix:* add an Association candidate group behavioral row: one named radiogroup; one Tab stop with arrow-key movement and announced position/count; selection must not commit the association; confidence/evidence referenced from each option; selected project repeated in the decision bar's accessible description; and Confirm without a candidate moves focus to the existing error summary. Preserve selected candidate and group focus when evidence refreshes unless expiry makes it invalid.

### Low (0)

No low-severity finding. Remaining issues materially affect current downstream implementation or AA conformance rather than polish.
