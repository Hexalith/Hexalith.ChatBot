# Governance & Safety Review — Hexalith.ChatBot

## Overall verdict

**Needs revision, with a strong safety foundation.** No critical issue was found, and the approved six-class mandatory-human-approval rule is explicit, non-downgradable, and backed by pre-execution revalidation. Four high-severity ambiguities still make the in-review pair unsafe as a final downstream contract: batch approval is broader than the current source permits, admin queue operations do not enforce the latest Project-authority boundary, one parity row can reveal suppressed candidates, and correction does not clearly distinguish pre-commit invalidation failure from post-commit propagation.

Finding counts: **critical 0 · high 4 · medium 6 · low 1**.

## Strengths

- The user-approved rule is preserved: all six AI-mediated boundary effects require human approval, policy cannot downgrade them, mixed requests inherit the stricter disposition, and execution revalidates authority, evidence, policy, allowlist, effects, revision, idempotency, and audit readiness (`.memlog.md:5-7`; `DESIGN.md:213-216`; `EXPERIENCE.md:122-132, 358-382`).
- Association fails closed to `NeedsReview` for every non-auto-association outcome, exposes only actor-safe candidates, never commits radiogroup selection, and blocks decisions on expired evidence (`EXPERIENCE.md:33-34, 91-96, 140-141, 174, 285-295`).
- Evidence freshness is a first-class, per-reference contract with timestamped `fresh` / `stale` / `expired` states, non-color presentation, announced expiry, and explained-unavailable approval/confirmation (`DESIGN.md:179-182`; `EXPERIENCE.md:89-92, 141, 175, 188`).
- Denials are consistently existence-neutral and retain precise causes only in authorized audit evidence (`DESIGN.md:201, 216`; `EXPERIENCE.md:63-75, 111, 127, 193, 344`).
- Sender authenticity/authority, durable idempotency, replay isolation, and UI/CLI/MCP outcome parity are substantially specified (`EXPERIENCE.md:154-167, 207-231`).
- Retention/export and redacted support-bundle behavior preserves authorization, redaction, and explicit human confirmation; AI outage keeps non-AI workflows available (`EXPERIENCE.md:109-110, 147-148, 253, 346-356, 382`).

## Findings by severity

### Critical

None.

### High

- **Batch approval permits effect classes and comparison criteria that the current PRD explicitly forbids.** The spine allows a batch when requester, command, Project, authority, input shape, policy, effect set, and freshness match (`EXPERIENCE.md:203`). The source additionally requires identical recipients, files, content digest, sender authority, tool target, approval revision, and expected resource revision, and prohibits one-click batching for irreversible, external-send, file-exposing, external-tool, and on-behalf actions (`../../prds/prd-Hexalith.ChatBot-2026-05-28/prd.md:1535-1540`). *Fix:* keep the six-class human-approval rule and narrow batch behavior to the complete frozen-field comparison; explicitly exclude the prohibited effect classes. Each included item must remain individually visible, authorized, revision-checked, decided through its own `decision_slot_id`, and atomically audited.

- **Admin queue operations do not enforce the latest per-item Project-authority boundary.** S10 and the interaction rule offer claim/assign/retry/requeue/quarantine/dismiss “at queue scope,” while Flow 5 says aggregate operations can occur without project detail (`EXPERIENCE.md:53, 179, 205, 325-330`). Current FR75c permits an admin without Project authority only to pause/resume a mailbox, client, or opaque queue partition and request investigation; per-item retry/requeue/quarantine/dismiss requires current Project authority plus requester-authority, revision, policy, and audit revalidation (`../../prds/prd-Hexalith.ChatBot-2026-05-28/prd.md:1391-1397`). The older supplemental gate still carries the superseded broad wording (`m1-m2-surface-elaboration.md:37-39`). *Fix:* split aggregate partition controls from per-item controls, show their different scopes, and gate every per-item action on current Project authority and the full revalidation set.

- **The parity matrix can disclose that forbidden candidates exist.** Candidate Review promises the same “suppressed unsafe set” across UI, CLI, and MCP (`EXPERIENCE.md:214`), contradicting the component rules that unsafe candidates never render and blocked states never confirm a resource (`EXPERIENCE.md:95, 111`). The source forbids unauthorized project/candidate detail in any surface (`../../prds/prd-Hexalith.ChatBot-2026-05-28/prd.md:1361-1362, 1469-1470`). *Fix:* require equivalent omission/redaction semantics, not an equivalent suppressed set. No surface may receive or expose suppressed identities, evidence, ordering, or cardinality; authorized audit may retain the precise decision under its own access rules.

- **Correction commit timing is ambiguous when the invalidation queue is unavailable.** Flow 4 says the correction commits and enters `Correcting`, while the state table also includes “invalidation dependency failed” without saying whether any correction committed (`EXPERIENCE.md:176, 313-319`). The fail-closed contract requires invalidation-queue and canonical-audit readiness before the correction write; otherwise no correction state commits (`../../prds/prd-Hexalith.ChatBot-2026-05-28/prd.md:1478-1494`). *Fix:* define a pre-commit failure state that leaves the predecessor authoritative and offers safe retry/escalation. Reserve `Correcting` and `Correction-delayed` for a successfully committed correction whose downstream acknowledgements are pending, with affected AI context blocked throughout.

### Medium

- **The approval rule is correctly conservative but is described as temporary and its actor scope is too broad.** Both current normative sources now make all six effects structurally non-downgradable for AI actions (`../../prds/prd-Hexalith.ChatBot-2026-05-28/prd.md:1330-1336, 1355-1356`; `../../prds/prd-Hexalith.ChatBot-2026-05-28/addendum.md:38-47`), yet the spine still says “interim” and “until upstream reconciliation” (`EXPERIENCE.md:32, 130`; `DESIGN.md:215`). Conversely, “any project-state mutation” can be read as requiring this AI approval flow for a direct authorized human write, despite the composer supporting human messages through the governed command spine (`EXPERIENCE.md:86`; `epic10-chat-surface-elaboration.md:18-21`). *Fix:* make the rule permanent for AI-mediated actions/proposals, preserve all six classes without downgrade, and state that direct human commands remain governed and policy-checked but do not enter the AI-proposal approval flow merely because they write state.

- **Task-intent failure and version terminology drift from the now-separated contracts.** `Task intent review` exposes a “detector/kernel version,” but the addendum says `TaskIntentDetector`, `AssociationScorer`, and `ActionRiskClassifier` are independently versioned and do not share a kernel. It also requires `detector-unavailable` to enter authorized review without invoking the action-risk classifier (`EXPERIENCE.md:93, 142, 173`; `../../prds/prd-Hexalith.ChatBot-2026-05-28/addendum.md:18-20, 28-43`). *Fix:* use `detector_version` only; add `detector-unavailable` / `NeedsReview` behavior and explicitly prevent risk-classifier invocation until an authorized task intent exists.

- **The bounded-admin model omits the audit obligation for every admin action.** Policy activation and queue mutations mention an audit link/record, but dashboard reads above the aggregation threshold, rejected policy changes, mailbox administration, and admin assignment are not universally covered (`EXPERIENCE.md:102-103, 177, 205, 321-332`). FR75g requires every admin action—including qualifying read-only dashboard access—to emit an audit event, while FR75a bars service clients and AI actors from admin assignment (`../../prds/prd-Hexalith.ChatBot-2026-05-28/prd.md:1391-1397`). *Fix:* add one invariant to Tenant Administration and Operational Dashboards: every allowed or rejected admin operation records actor, scope, affected opaque items, outcome, and timestamp; no service client or AI actor can assign admin roles or mutate policy.

- **Audit provenance does not define identity-evolution fallback or label human annotations as non-authoritative.** The timeline reconstructs actors, decisions, policy, correction, replay, redaction, and outcome, but says nothing about unresolved successor IDs or the evidentiary status of appended rationale (`EXPERIENCE.md:107, 180, 313-317, 350-356`). `IdentityEvolved` is explicitly non-binding; until producer acceptance, the product preserves original IDs, rejects operations whose current identity cannot be resolved, and routes reconciliation to authorized review (`../../prds/prd-Hexalith.ChatBot-2026-05-28/addendum.md:154-160`). Human annotations cannot alter decisions or repair missing canonical audit completeness (`../../prds/prd-Hexalith.ChatBot-2026-05-28/prd.md:1365-1368`). *Fix:* show original ID plus unresolved-current-identity status and safe review path; label notes/rationale as appended, non-authoritative annotations distinct from canonical decision evidence.

- **Operational item diagnostics are not runbook-complete.** Shared operation status, Queue row, and the SLO dashboard cover operation identity, state, owner, retries, reason, and correlation, but no single per-item pattern requires tenant ID, mailbox ID, workflow item ID, and last transition with actor/from-state (`EXPERIENCE.md:104-106, 179`). NFR44 requires all of those fields for sampled runbook readiness (`../../prds/prd-Hexalith.ChatBot-2026-05-28/prd.md:1533`). *Fix:* define an authorized diagnostic disclosure reached from Queue row/Shared operation status; include the complete NFR44 field set while applying bounded-admin redaction to business detail.

- **Parity does not clearly separate surface exposure from the AI-invocable allowlist.** The matrix correctly shares outcomes, but “approved-command execution” through MCP can be read as making every parity operation AI-invocable (`EXPERIENCE.md:207-224`). The source separates product operation catalog, per-surface exposure, and the deny-by-default AI allowlist; MCP exposure never extends AI authority (`../../prds/prd-Hexalith.ChatBot-2026-05-28/addendum.md:58-73`; `../../prds/prd-Hexalith.ChatBot-2026-05-28/prd.md:1408-1414`). *Fix:* make the Cross-surface Attribution / Command Surface Reference show these three distinct memberships and state that parity governs equivalent outcomes only after actor/surface authorization succeeds.

### Low

- **The SLO surface should distinguish qualification backlog from a published catalog.** The spine safely marks missing support as `unsupported`, but its names and flow can still read as a published SLO dashboard (`DESIGN.md:196`; `EXPERIENCE.md:51, 106, 179, 328`). The addendum says the catalog is not publishable until A11 provides every target, error budget, live signal, route, and burn test; `unsupported-pending-a11` blocks readiness (`../../prds/prd-Hexalith.ChatBot-2026-05-28/addendum.md:189-249`). *Fix:* label the pre-A11 view “SLO qualification backlog”; promote it to “published SLO catalog” only when every required dimension passes.

## Consistency notes

- Preserve the six-class mandatory-human-approval decision. It is recorded in `.memlog.md:6`, implemented consistently in `DESIGN.md:215` and `EXPERIENCE.md:125, 130, 377`, and now agrees with the current PRD/addendum. The finding above removes obsolete temporariness and clarifies actor scope; it does not weaken the rule.
- One upstream conflict remains around an indeterminate classifier: the addendum routes it fail-closed to review (`addendum.md:46`), while PRD NFR15a lists classifier indeterminacy as an AI-proposal write blocker (`prd.md:1487`). The binding UX resolution—reviewable `approval-required` proposal only when every other authorization/support/audit precondition succeeds, otherwise `denied`/`unsupported`—is internally consistent and should be preserved (`EXPERIENCE.md:33, 126-128, 378`).
- Below-`T_low` association, strict/paranoid authenticity, durable replay/conflict outcomes, evidence freshness, sender-authority revalidation, retention/export/support-bundle redaction, and AI-outage continuity all align with the current addendum (`EXPERIENCE.md:34, 141, 148, 154-167, 226-231, 253, 382`).
- The supplemental M1/M2 gate predates the stricter current FR75c admin boundary. Treat its S10 retry/requeue/quarantine/dismiss wording (`m1-m2-surface-elaboration.md:39`) as superseded where it conflicts with the current PRD.
- The pair intentionally has no mockups, wireframes, or imports, and explicitly makes the spines authoritative (`EXPERIENCE.md:36`); this creates no governance/safety gap.
