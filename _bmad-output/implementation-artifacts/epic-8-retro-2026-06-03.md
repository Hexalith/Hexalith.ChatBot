- **Always-on OpenTelemetry emission** for seven FR94 operation classes via a single dedicated `"Hexalith.ChatBot"` meter — four latency histograms (ingestion, association, approval, command-execution), two counters (retry-exhausted, duplicate-suppressed), one observable audit-lag gauge — plus a `chatbot.telemetry.emission_failures` gap-detection meta-counter, all non-blocking (`SafeEmit`) and wired into the `ServiceDefaults` always-on metrics pipeline.
- **Published SLO catalog and error budgets** — `OperatingBaselineCatalog.Published` with 13 SLOs (the 12 NFR42a metrics + the NFR26 operation-identity SLO), each carrying target, measurement window, error budget, alert threshold, and calibration source, with a fail-safe `ErrorBudgetBurnEvaluator.FromHealth` that emits coarse burn (`within-budget|approaching|exhausted|unknown`) and an addendum drift-guard test.
- **Tenant-safe alert wiring** — five pure NFR43 default evaluators (audit-lag breach, retry exhaustion, approval-queue age ≥ 2 business days, subscription expiry, authorization-failure spike) behind a fail-closed `OperationalAlertWiringCoordinator` that writes pre-commit audit before delivering through `INotificationSink`, with a shared `OperationalAlertPayload` carrying only scope/owner-role/next-action/reason-code safe tokens.
- **Degraded-state operability and runbook diagnostics** — a `DependencyScopeResolver` isolating degraded dependencies to the narrowest of seven scope levels (workflow-item → tenant), a metadata-only `DegradedDependencyIncident` (NFR41, 5-minute detection budget), a four-element degraded dashboard surface (NFR42), and runbook-real per-item `OperationalQueueDiagnostics` (NFR44) with a deterministic completeness validator that mechanically rejects the legacy stub values it replaced.

## What Went Well

- **Fail-safe / no-fabrication doctrine became the spine of the epic.** Story 8.1's two MEDIUM findings were both fabrication defects (a false "reaches the spine via `IChatBotClient`" claim and fabricated `Degraded`/`Failed` health). The corrective — *prefer no-data over fabricated health* — then drove every later story: 8.2's audit-lag gauge emits nothing when the checkpoint source is unavailable, 8.3 carries `Unknown` burn on 11 of 13 SLOs and `calibration-pending` targets rather than fabricated `0.1%`, 8.4's evaluators suppress on `Healthy`/`Unknown`, and 8.5's resolver returns `(Unknown, "scope:unknown")` and its factory returns `null` for healthy input.
- **Always-on OpenTelemetry emission landed exactly as the architecture prescribed.** A single dedicated `"Hexalith.ChatBot"` meter (mirroring the `ChatBotActivitySourceName` precedent), seven FR94 instruments, non-blocking `SafeEmit`, and a `chatbot.telemetry.emission_failures` gap-detection meta-counter, registered into the always-on `WithMetrics` pipeline in `ServiceDefaults`.
- **Metadata-only + safe-token validation generalized cleanly across every new payload.** One `IsSafeToken`/marker-ban posture (ASCII alnum + `.-_:@|`, banning `secret`/`password`/`bearer`/`token`/`exception`/`.txt`/`.json`/`.xml`) was applied uniformly to telemetry dimensions, SLO tokens, alert payloads, degraded incidents, and runbook diagnostics. Serialization tests assert no secret sentinels leak on any surface. NFR2/NFR42 upheld end-to-end.
- **Cardinality was treated as a first-class constraint.** Operation-class is fixed per metric method (no free-form tags); telemetry only ever emits `tenant` + `operation-class` dimensions; correlation rides the active `Activity`/trace exemplar per `ChatBotCorrelationMiddleware` rather than becoming a metric label — one decision that avoids both metric-cardinality blowup and NFR2 leakage.
- **Quality trajectory improved measurably across the epic.** 8.1: 2 MEDIUM. 8.2: 1 HIGH + 2 MEDIUM. 8.3: 0 HIGH/MEDIUM (2 LOW). 8.4: 0 HIGH (2 MEDIUM). 8.5: 0 HIGH (1 MEDIUM). HIGH findings vanished after the 8.2 try/finally completeness fix, and later stories explicitly cited and pre-empted the 7.5/8.1 lessons (count-vs-enum status, non-deterministic hashing, File-List honesty) in their own Dev Notes.
- **Define-once / reuse held.** The published SLO catalog (8.3) became the single source of truth the alert layer (8.4) consumes by `MetricName` reference rather than re-deriving thresholds — the same architectural win as Epic 7's `GovernedOperationAggregate`. Authorization reused the existing `OperationalDashboardReadPolicy` → `AdminQueueSummaryReadPolicy` → `AdminAuthorityEvaluator` chain on every read; the alert coordinator mirrored `ReviewerBacklogAlertCoordinator`'s fail-closed audit-then-deliver discipline.
- **The 8.2 completeness fix was a genuine correctness catch.** Command-execution/ingestion latency was first recorded only immediately before `return`, so a throwing `BuildPlanAsync`/`SubmitCommandAsync` emitted no measurement — violating AC1's "success **or** failure." Wrapping the dispatch body in `try/finally` (mirroring the approval/association seams) fixed it, and a mutation-verified test now proves it.
- **8.5 made stub regression mechanically impossible.** The runbook completeness validator explicitly rejects the legacy stub prefixes (`correlation:`, `tenant:current`, `last-transition:`) it replaced, so a future regression to placeholder diagnostics is caught by a test rather than silently accepted as "safe-looking."
- **`ChatBotMessageCodes.All` reflection (8.5)** lets incident and runbook validators test reason-code membership against the live FR77 catalog instead of a hand-copied subset that could drift.

## Challenges

- **Bookkeeping drift was the single most recurring defect — exactly the Epic 7 carry-forward.** Stale debug-log test counts appeared in 8.2 (counts corrected post-review), 8.3 (289/1011 → 298/1018), 8.4 (1059 → 1066), and 8.5 (328/1087 → 339/1088). File List omissions recurred in 8.2 (`ChatBotOperationClassesTests.cs`), 8.4 (three test files), and 8.5 (`DependencyScopeKindTests.cs`, `ApprovalPriorityScorerTests.cs`). Every instance was a documentation-only auto-fix, but they recurred in four of five stories. The reconciliation checkpoint (Epic 7 action item #4) *caught* them every time — it did not *prevent* them. Detection control, not prevention control.
- **The 8.2 HIGH finding (latency only on success path)** was a real telemetry-completeness bug: measurement was missing on throw paths. Paired with a MEDIUM verification-gap where the `AddMeter` test did not actually exercise `AddMeter` (removing the registration would not have failed the test) — fixed with an in-memory metric-reader test that is mutation-verified.
- **The biggest systemic gap: Epic 7's deferred control-state/rate-limit read-side projections were NOT materialized in Epic 8** — despite being Epic 7 retro action items #1 (Winston) and #2 (Amelia), and despite the README explicitly promising them "expected in Epic 8." All five Epic 8 stories confirm these projections and the periodic runtime trigger for the 7.6–7.11 notification/escalation/throttle/backlog/rubber-stamp evaluators remain unwired. The inert-control-floor condition from Epic 7 persists unchanged.
- **Epic 8's own surfaces are largely not live-wired either.** There is no dashboard read endpoint on `IChatBotClient` (the UI assembles a fail-safe placeholder with all six views `Unknown`); no real per-tenant audit-checkpoint feed (the lag gauge emits nothing under the `UnavailableAuditProjectionLagSource` default); no runtime scheduler for the `OperationalAlertWiringCoordinator` (8.4) or the weekly 100-item runbook sampler (8.5); and the AI-outcome health source is unwired. Epic 8 delivered the emission, contract, projector, and policy layers plus the read-only surfaces — consistent with "emit always, visualize later" — but a future story must bind the read path and the runtime triggers before any of it is operator-visible at runtime.
- **Deferred-runtime debt is now compounding.** Epic 7 deferred control-state projections + evaluator triggers; Epic 8 deferred them *again* and added its own dashboard-read-path, alert-coordinator-trigger, audit-checkpoint-feed, and weekly-sampler deferrals on top. The "wire the runtime" work is now a cross-epic backlog that no single story owns.
- **A few accepted limitations were documented honestly rather than over-engineered.** 8.5's AC8 mailbox-family conditional requiredness is not expressible at the `RunbookDiagnosticCompletenessValidator` seam (no family discriminator in the signature), and the incident factory can emit a structurally-invalid `ScopeKind.Unknown` incident on all-empty scope (the validator is the gate and no runtime caller is wired yet). Both were left as-is to avoid untested behavior changes.

## Key Insights

1. *"Emit structured signal always; visualize later"* is now realized as a **layered build**: emission (8.2) and contracts/projectors/policies (8.1/8.3/8.5) are load-bearing and tested; the live read path and runtime triggers are deliberately deferred. This keeps the audit/contract surface small but means the observability layer — like Epic 7's control floor — is currently inert at runtime.
2. Fail-safe *"prefer no-data over fabricated health"* is a **safety property, not a UX nicety**: a fabricated `Healthy` during a real outage is strictly worse than `Unknown`. Story 8.1's two MEDIUM findings were both fabrication defects, and the doctrine that emerged from fixing them governed every subsequent story.
3. A single metadata-only / safe-token posture generalizes across telemetry dimensions, SLO tokens, alert payloads, incident records, and runbook diagnostics. Applying one `IsSafeToken`/marker-ban validator at every new payload boundary kept NFR2/NFR42 intact while observability breadth widened — the same "one mechanism, many surfaces" economy seen with the governed-operation aggregate.
4. **Cardinality is a design axis to decide once.** Fixing operation-class per method and routing correlation through trace exemplars (not metric labels) resolves metric-cardinality blowup and NFR2 leakage in a single decision rather than story-by-story.
5. A **published SLO catalog as single source of truth** lets the alert layer consume thresholds by metric-name reference instead of re-deriving them — define once, reuse downstream.
6. The recurring failure mode is unchanged from Epic 7: **bookkeeping (test counts, File Lists), not domain logic.** Epic 7's reconciliation checkpoint reliably *detected* these but did not *prevent* recurrence. A detection control left to manual discipline will keep failing four times in five; the next improvement must be a mechanical prevention gate.
7. **Deferred-runtime debt compounds across epics and needs an owner.** Two consecutive epics have shipped correct, tested logic whose runtime activation was deferred. The next epic that claims a "production observable" (Epic 9's audit-completeness, story 9.2) will be the one that finally requires the runtime loop to exist — so the wiring should be a first-class story, not another deferral.
