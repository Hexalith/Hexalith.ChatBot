## What Went Well

- The `GovernedOperationAggregate` + `GovernedOperationState` engine (Story 7.2) became the reusable spine for the entire back half of the epic. Disable/quarantine cells reused the same submit→approve handlers, lifecycle transitions, and audit-ref shape rather than re-implementing per subject.
- Distinct-approver (two-person rule) enforcement was defended in depth: gateway `ParticipantAuthorizationStage` validator + `AcceptedCommandDispatcher` guard + aggregate re-check, all asserting `RequesterRef != ApproverRef` and `RequesterActorId != envelope.UserId`.
- The command allowlist was consistently widened **last** in every control-floor story — after validation, authorization, audit, and tests — which kept the M0 safety floor intact while M1 breadth landed.
- Audit stayed metadata-only across the epic. Redaction tests assert no `@`/`secret`/`oauth`/`bearer`/`fingerprint`/`project-`/mailbox-content leakage on every governed operation.
- The two action-shapes were kept honest: disable/quarantine carry a `StateTransition` and a terminal/await-admin catalog entry; rate-limit is a single-actor bounded knob with budget/window audit refs and a transient `retry-later` catalog entry. Fail-safe rate bounds always fall back to the cap and never raise.
- Self-lockout was explicitly prevented: the command-capability cell (7.21) exempts the FR74 governance commands themselves (`Fr74GovernanceCommandTypes`) so a tenant can never disable its own reversal path.
- Floating-point comparison defects were proactively avoided by Story 7.11 onward (integer arithmetic `count × 100 > pct × total` instead of `double` percentage compares).
- Submodule gitlink hygiene improved measurably across the epic: from blocked auto-restores and one false "reset" claim early on (7.6–7.7) to proactive non-recursive `git submodule update -- <path>` resets and explicit `git submodule status` verification from 7.8/7.12 onward.

## Challenges

- **Submodule gitlink pointer drift** was the single most recurring environment defect (`Hexalith.Tenants`, `Hexalith.EventStore`, `Hexalith.Parties`, `Hexalith.FrontComposer`). Story 7.6 shipped undocumented bumps; Story 7.7's completion note falsely claimed the drift was reset before the reviewer caught and actually reset it. This validated the existing memory guidance to run a submodule guard before commit.
- **Stale debug-log test counts** were the most frequent review finding — nearly every story from 7.6 to 7.27 recorded a Server/Workers/Contracts test total a few off from the re-run actual (e.g. 7.7 588→592, 7.14 27→30 Workers, 7.27 937→938). Always a documentation-only auto-fix, but persistent.
- **File List omissions** recurred (`AcceptedCommandDispatcherTests.cs`, `GovernedOperationAggregateTests.cs`, UI E2E/localization files), a standing Medium finding that the changed-file reconciliation checkpoint is meant to catch.
- **JSON enum-default deserialization bypass**: omitted enum `kind` fields deserialized to a valid default that passed authorization (7.2 policy schema version, 7.3 mailbox routing/freshness). Fixed by explicit `Unknown` defaults rejected at the gateway.
- **Validated-but-not-applied** logic surfaced twice as HIGH findings: `ComplianceAuditReadPolicy.Search` validated query filters but ignored them (7.4); `AdminQueueSummaryProjector` validated a `PageToken` but didn't apply it, repeating page 1 (7.5). Both fixed.
- **Non-deterministic fingerprints**: Story 7.5 used `GetHashCode()` for filter fingerprints (process-dependent); replaced with canonical SHA-256, after which the `sha256:` token discipline became a guardrail.
- **Overstated/unwired seams** had to be reclassified down to honest scaffolding in review: `BatchDecisionEvidenceRefs` (7.8) and `ServiceClientRateLimitObservation` (7.17) were declared richer than the wired commands actually carried.

## Key Insights

1. A single governed-operation aggregate with a submit→approve two-person pattern scales to a whole matrix of subject×action governance controls. The win was refusing to invent per-subject mechanisms.
2. Order of operations is a safety property: widen the command allowlist **last**, after validation/authorization/audit/tests, so breadth never precedes the floor that constrains it.
3. Distinct-approver enforcement must be defended at every layer that could be reached independently (gateway, dispatcher, aggregate), not only at the UI or a single stage.
4. Enforcement seams legitimately differ per subject, and that divergence must be documented, not hidden: worker intake (mailbox), grant validator (service-client/AI-actor, actor-type-gated), top-of-`ParticipantAuthorizationStage` actor-agnostic (command-capability), and send seam (outbound-channel).
5. Fixed governance constants vs. tunable schema knobs is a deliberate design axis. Throttle ceilings and backlog thresholds became closed-bounded knobs; rubber-stamp constants (5s/15%/7d) were intentionally **not** made tunable.
6. Most M1 administration breadth can ride the existing generic command-submission transport with metadata-only server reads — no new public HTTP shapes — which keeps the contract surface small and the audit target narrow.
7. The recurring failure modes this epic were bookkeeping (test counts, File Lists, submodule pointers) and validated-but-not-applied logic, not governance design. Review reinforcement on reconciliation pays off more than new process.

## Significant Discoveries

- The aggregate `epic-7` sprint-status row lagged story reality: all 27 stories were `done` while the epic row remained `in-progress` until this retrospective. The same lag exists on `epic-6`, which has no retrospective despite Epic 7 being complete.
- Most Epic 7 administration breadth (queues, notification routing, escalation, throttling, backlog, rubber-stamp — 7.5–7.11) added **no new public OpenAPI endpoints/schemas**. It rides the existing generic command-submission transport with metadata-only server reads; the generated client and OpenAPI checksum were intentionally unchanged. Only Stories 7.1–7.4 and the 15 control-floor cells (7.12–7.26) added public command schemas.
- Several deliberate divergences from the literal epics.md/architecture plan were made and accepted in review: no `AdminScope.Security`/`SecurityEngineer` role (the persona maps to `AdminScope.Policy`; security-engineer sign-off is a checked-in `.decision-log.md` artifact, not a runtime role); notification/escalation persistence used generic command dispatch rather than dedicated `*Events` types; `ai-action.low-risk-allowed` became a per-action-class map rather than a global boolean; service-client governance authority gates on `HasHumanTenantAdmin` rather than a new finer scope.
- Command-capability control is a distinct per-tenant plane — explicitly **not** a per-tenant mutation of the static `ChatBotSpineCommandAllowlist` and **not** the Epic-5 per-grant `AllowedCommandNames`.
- Allowlist v1 + lifecycle completion (7.27) shipped with **no wire-contract change**: v1 metadata and version constants are server-internal, `CurrentVersion` stays at the M0 safe floor, and v1 is opt-in via the two-person `allowlist.version-pin` knob. `Skipped` was already on the wire; 7.27 re-wired live duplicate-suppression off a hard-coded `"Received->Skipped"` magic string to a guard-resolved transition.
