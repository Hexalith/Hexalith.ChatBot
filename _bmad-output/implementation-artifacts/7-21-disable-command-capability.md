# Story 7.21: Disable command capability

Status: done

<!-- Validation: create-story checklist applied 2026-06-02. -->

## Story

As an authorized **security engineer** (a human admin holding the policy scope, under a two-person rule),
I want to disable a misbehaving **command capability** for a tenant,
so that unsafe command execution can be stopped by policy — **every actor's attempt to submit that command type (human, service client, or AI actor) fails closed at the command-admission pipeline with a catalogued reason** — while every prior execution and audit record stays intact and reconstructable, and safe recovery guidance is shown.

## Acceptance Criteria

1. Given a command capability producing unsafe or invalid outcomes, when an authorized **human policy admin** (the "security engineer" persona) proposes a **disable** and a **second** authorized human policy admin approves it (FR75d two-person rule), then the command capability transitions to a durable **Disabled** governance control state and **future submissions of that command type are removed from admitted execution for the tenant and fail closed** at the command-admission pipeline with a catalogued reason, while **unrelated command capabilities and unrelated tenants continue normally** (isolation, NFR30). The disable is a security-sensitive FR74 governance control — **not** a tenant-policy knob and **not** the static `ChatBotSpineCommandAllowlist` (which is a global, code-level fail-closed allowlist, never tenant-mutable) — so it MUST go through the same submit→second-person-approve flow established for the Story 7.18 AI-actor disable (`SubmitAiActorDisable`→`ApproveAiActorDisable`) and Story 7.15 service-client disable; a single-actor disable never takes effect. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.21`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75d`; `_bmad-output/implementation-artifacts/7-18-disable-ai-actor.md`; `src/Hexalith.ChatBot.Server/Operations/GovernedOperationAggregate.cs`]

2. Given the disable proposal and approval, when authorization runs, then the operation is permitted only for a **human policy administrator** — gate on **`AdminAuthorityEvaluator.HasHumanAdminScope(actor.Principal, AdminScope.Policy)`**. There is **no dedicated `AdminScope.Security`/`AdminRole.SecurityEngineer`** in the model; the epic's "security engineer" persona maps to the **policy** scope (command-capability / command-allowlist governance is a security-sensitive policy concern — the same scope that gates `SubmitTenantPolicyChange`, the AI-actor controls 7.18–7.20, and forward-references the Story 7.27 command-allowlist work). A `tenant-admin` still qualifies because `AdminScopes.ScopesForRole(TenantAdmin)` returns the full scope set (FR75a union) — so this is **not** a relaxation. The operation is **denied for service clients and AI actors** even when they carry admin-looking claims (the human-actor gate inside `HasHumanAdminScope`/`IsHumanActor`), and denied for non-policy human scopes (`mailbox-admin`/`compliance-admin`/`operations-admin`-only). The approving admin MUST be a **different person** from the proposer: both `RequesterRef != ApproverRef` (Ordinal safe-token compare) and `RequesterActorId != approver envelope UserId` are enforced — at the gateway validation stage, the accepted-command dispatcher, **and** re-checked in the aggregate, mirroring `IsValidAiActorDisableApproval`, `AcceptedCommandDispatcher`'s distinct-approver guard, and `GovernedOperationAggregate.Handle(ApproveAiActorDisable)`. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.21`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75a`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75d`; `src/Hexalith.ChatBot.Server/Governance/Admin/AdminAuthorityEvaluator.cs:10`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ParticipantAuthorizationStage.cs:135`]

3. Given the disable is applied (approval committed), when it is recorded, then the operation records — with **no skip-audit path** (FR74, FR75g, NFR15a) — the **actor** (admin identity / actor type), **scope used** (`admin-scope:policy`), **subject** (the safe command-capability ref — the disabled command type name), **reason** (documented justification reason code), **old state** (`Active`), **new state** (`Disabled`), **policy snapshot id**, and **timestamp**, via a metadata-only `AuditEnvelope` whose `StateTransition` is `"Active->Disabled"`. The audit is written through the existing fail-closed pre-commit seam (`IAuditWriter.RecordPreCommitAsync` via `CommandGateway`): when the pre-commit audit is unavailable, **no durable disable state is written and no admission-blocking side effect occurs** (fail closed), reusing the disable/`CommandGateway` audit-unavailable behavior. No admin role bypasses NFR15a/NFR50a. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.21`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75g`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR15a`; `src/Hexalith.ChatBot.Server/Audit/AuditEnvelopeFactory.cs`; `src/Hexalith.ChatBot.Server/Gateway/CommandGateway.cs`]

4. Given a command capability is Disabled for a tenant, when **any actor** (human, service client, or AI actor) submits a command **of that disabled type** for that tenant, then the authorization stage **fails closed before admission**: `ParticipantAuthorizationStage.AuthorizeAsync` returns `ChatBotAuthorizationResult.Denied("command_capability_disabled")` for the disabled command type, **before** the service-client grant validation, the per-command admin-scope checks, and the downstream spine-allowlist / risk / approval gates — so no command of the disabled type is admitted and no restricted work is performed. This is the **key divergence from the 7.12/7.15/7.18 cells**: the subject is a **command type**, not an actor or a worker source, so enforcement must cover **all actor types** and therefore lives in the **actor-agnostic authorization stage** (`ParticipantAuthorizationStage`, which runs for every actor and has both the command type and the authenticated tenant binding) — **not** in `ServiceClientGrantValidator` (which only runs for `service`/`ai` actors and would miss human submissions) and **not** in a worker. A submission of any **other (still-Active)** command type for the same tenant, or the same command type for a **different** tenant, is unaffected (isolation). The new `command_capability_disabled` reason is **distinct from** `command_not_allowlisted` (the global static spine-allowlist refusal), `service_client_grant_under_scoped` (the per-grant allowlist), and every actor-control reason (`service_client_disabled`, `ai_actor_disabled`, etc.). [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.21`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ParticipantAuthorizationStage.cs:36`; `src/Hexalith.ChatBot.Server/Gateway/ChatBotAuthorizationReasonCodes.cs:12`; `src/Hexalith.ChatBot.Server/Gateway/ChatBotSpineCommandAllowlist.cs`]

5. Given a command capability is disabled, when its prior activity is inspected, then **all previously recorded commands, events, audit envelopes, proposals, associations, files, approvals, conversation content, and workflow items that originated from that command type remain visible, intact, and fully reconstructable** — disable affects **only future admission**, never already-committed records or their audit trails (NFR17 visible/recoverable states; FR75c admins cannot mutate project-level records). Disable is reversible by a future re-enable flow; this story does not delete or rewrite any prior record. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR17`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75c`; `_bmad-output/implementation-artifacts/7-18-disable-ai-actor.md`]

6. Given an actor encounters a disabled command capability (admin viewing status, or an admission blocked), when guidance is surfaced, then **safe recovery guidance** is shown from the **finite message catalog** — a safe headline (≤ 80 chars), a one-line reason from a finite set, a next-action pointing to the responsible role (re-enable is a policy-admin/two-person action), and a `disabled-action` reason — using `ChatBotMessageCatalog` / `ChatBotMessageCodes` / `ChatBotDisabledActionReasons`, never raw error text. No surface names an unauthorized project/file/party/mailbox-content/audit detail (NFR2); EN/FR via existing localization; stable machine tokens (reason codes, state tokens, correlation ids, command type names) stay untranslated. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.21`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR76`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR2`; `src/Hexalith.ChatBot.Contracts/Messages/ChatBotMessageCatalog.cs`]

7. Given the disable subject and audit refs are metadata, when the proposal/approval/disabled events and the audit envelope are serialized, then they carry **only safe, finite tokens** — the safe command-capability ref (the command type name, a finite identifier), `admin-operation:command-capability-disable` / `admin-scope:policy`, the reason code, old/new state tokens, policy-snapshot id, correlation id, UTC timestamp — and **never** credentials, OAuth grant fingerprints, bearer tokens, secrets, model prompts/completions, raw claims/headers, delegated-user PII, mailbox/project/proposal/evidence content, or raw GUIDs that are not already safe identifiers (NFR2, NFR4, NFR5). The subject is identified by its command type name via `AuditMetadata.SafeOptionalToken` / `IsSafeStableIdentifier`. Tenant scope comes **only** from the authenticated gateway binding — never from the command body. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR2`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR4`; `src/Hexalith.ChatBot.Server/Audit/AuditMetadata.cs`]

8. Given public commands, queries, DTOs, or generated clients change for the disable proposal/approval, when the contract surface is updated, then the OpenAPI contract spine (`hexalith.chatbot.v1.yaml`) is updated **first** (two new commands `SubmitCommandCapabilityDisable`/`ApproveCommandCapabilityDisable` modelled on the `SubmitAiActorDisable`/`ApproveAiActorDisable` schemas, plus a `CommandCapabilityControlState` enum mirroring `AiActorControlState` — slotted after the AI-actor-control schemas), `HexalithChatBotClient.g.cs` is **regenerated** (never hand-edited), the generated-client checksum (`tests/fixtures/hexalith-chatbot-generated-client.sha256`) is refreshed, and contract/client parity tests prove schema parity — exactly as Stories 7.2/7.3/7.12–7.20 did. The new command types are added to `ChatBotSpineCommandAllowlist` **only after** validation, authorization, audit, and tests are in place (fail-closed; never widen the allowlist first). Given acceptance coverage runs, then tests prove: a single-actor disable never takes effect (proposal alone does not block admission); a distinct second human policy-admin applies the disable; `RequesterRef == ApproverRef` and `RequesterActorId == approver UserId` are both rejected (gateway, dispatcher, **and** aggregate); service clients and AI actors are denied for both proposal and approval even with admin-looking claims; a non-policy human scope (mailbox/compliance/operations-only) is denied while a policy-admin **and** a tenant-admin (union) are allowed; a disabled command capability fails closed at `ParticipantAuthorizationStage` with `command_capability_disabled` for a **human**, a **service** actor, **and** an **AI** actor (all-actor coverage) **before** grant validation / admin-scope checks / spine allowlist, while a sibling Active command type and the same command type under a different tenant are unaffected (isolation); the disable does not mutate existing committed/audit records; the disable audit envelope carries actor/scope/subject/reason/old-state/new-state/policy-snapshot/timestamp with `StateTransition "Active->Disabled"`, `admin-scope:policy`, and **no** credential/OAuth-fingerprint/prompt/`@`/`secret`/project leakage; audit-unavailable → no durable disable + no admission-blocking side effect (fail closed); the FR74 governance commands themselves cannot be disabled (self-lockout guard); and OpenAPI/client/checksum parity holds. ### Scope Boundaries

- Story 7.21 is the **tenth** cell of the FR74 enforcement series (7.12–7.26: five subject classes — mailbox / service-client / AI-actor / **command-capability** / outbound — × three actions — disable / quarantine / rate-limit) and the **first command-capability cell**. Disable (this story) and quarantine (7.22) are **security-sensitive** admin operations gated by the **FR75d two-person rule**; rate-limit (7.23) is a standard policy mutation. **Do not** implement quarantine, rate-limit, any other subject class, a future re-enable/release flow, or the Story 7.27 command-allowlist-v1 / full-lifecycle work here. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`; `_bmad-output/planning-artifacts/epics.md#Story 7.27`]
- **This story is a structural mirror of Story 7.18 (disable AI actor), retargeted from the AI-actor subject to the command-capability subject, with one major divergence (read this first):**
  1. **The subject is a command TYPE, not an actor.** "Disable" removes a command capability from admitted execution **for every actor of a tenant** (human, service client, AI actor). So the enforcement seam is **not** `ServiceClientGrantValidator` (it runs only for `service`/`ai` actors — `RequiresGrant` is false for humans, who short-circuit to `Allowed`, so a human submission of the disabled command would slip through). The enforcement must live in the **actor-agnostic `ParticipantAuthorizationStage.AuthorizeAsync`**, which runs for **all** actor types and has both `submission.Request.CommandType` and the authenticated `tenantBinding`. Place the disabled-capability check at the **top** of `AuthorizeAsync` (after the guards at line 45, before the grant-validator call at line 47) so it fails closed first with the precise `command_capability_disabled` reason. **Rejected alternatives:** a `ServiceClientGrantValidator` branch (misses humans), per-tenant mutation of the static `ChatBotSpineCommandAllowlist` (it is a global, code-level, never-tenant-mutable hard boundary), or a worker check (commands flow through the gateway, not a worker).
- **Authorization scope = policy-admin.** There is **no** `AdminScope.Security` / `AdminRole.SecurityEngineer` in the model (confirmed: `AdminScope` = {SeeOnly, Operate, Policy, Mailbox, Compliance, AuditObligation}; `AdminRole` = {TenantAdmin, MailboxAdmin, PolicyAdmin, ComplianceAdmin, OperationsAdmin}). The epic's "security engineer" persona maps to the **policy** scope — command-capability / command-allowlist governance is a security-sensitive policy concern (the PRD failure-mode table for "Allowlist mutation" expects "actor … security engineer (or admin in production)", and `AdminScope.Policy` already gates the security-sensitive `SubmitTenantPolicyChange` and the AI-actor controls 7.18–7.20). Gate on **`HasHumanAdminScope(actor.Principal, AdminScope.Policy)`**. A `tenant-admin` still passes via the FR75a scope union (`AdminScopes.ScopesForRole(TenantAdmin)` returns all scopes) — **not** a relaxation. **Rejected alternatives:** a new `AdminScope.Security` (scope-creep; `Policy` already governs security-sensitive mutations) and `HasHumanTenantAdmin` (too coarse; ignores the named persona and the finer Policy scope).
- **Same as 7.18 (preserve the two-person machinery):** submit→second-person-approve; a single-actor disable only ever produces a pending approval. Distinct approver enforced **three times** (gateway validator, accepted-command dispatcher, aggregate re-check), `RequesterRef != ApproverRef` Ordinal AND `RequesterActorId != envelope.UserId`. Control state via the fixed FR74 path, never a tenant knob or the static spine allowlist. Terminal catalog guidance (`request-access` + `disabled-action`), not transient.
- **Self-lockout guard (new for this cell):** because the subject is a command type, an admin could in principle disable the FR74 governance commands themselves (`SubmitCommandCapabilityDisable`/`ApproveCommandCapabilityDisable`, and the other control commands) and lock the tenant out of governing/reversing. State this guard explicitly.

The subject (command type name) and all audit refs are **metadata-only, safe tokens** (NFR2); credentials, OAuth grant fingerprints, model prompts/completions, and delegated-user PII never appear (NFR4/NFR5).

### What "command capability" means here, and where it is blocked

- A **command capability** is a first-party governed command **type** that the tenant may submit through the command gateway (the universe is the `ChatBotSpineCommandAllowlist.AllowedCommandTypes`). "Disable a command capability" = mark that command type **Disabled for the tenant** so its future submissions fail closed — distinct from the three existing allowlist-like concepts:
  - **`ChatBotSpineCommandAllowlist`** (`src/Hexalith.ChatBot.Server/Gateway/ChatBotSpineCommandAllowlist.cs`): a **global, static, all-tenant, code-level** fail-closed boundary checked in `CommandGateway.SubmitAsync` (reason `command_not_allowlisted`). It is **never** tenant-mutable — do not touch it as the disable mechanism. The new control plane is **per-tenant** and orthogonal.
  - **`ServiceClientGrant.AllowedCommandNames`** (Epic 5): a **per-grant** scope checked in `ServiceClientGrantValidator` for `service`/`ai` actors only (reason `service_client_grant_under_scoped`). It does not cover human submissions, so it is not the seam.
  - **The actor control planes** (`ServiceClientControlState`/`AiActorControlState`): disable an **actor**, not a command type.
- The command flows through the gateway pipeline in this order (per `CommandGatewayServiceCollectionExtensions` + `CommandGateway.SubmitAsync`): **(1) Authentication** (`ClaimsAuthenticationStage`) → **(2) Tenant binding** (`ClaimsTenantBindingStage`) → **(3) Authorization** (`ParticipantAuthorizationStage`, which first calls `ServiceClientGrantValidator`) → **(4) Spine allowlist** (`ChatBotSpineCommandAllowlist`, in `CommandGateway`) → **(5) Risk** → **(6) Approval gate** (`AiActionApprovalGate`). The disabled-capability check belongs at the **start of stage 3** (before the grant validator and before the per-command admin-scope branches), so it covers all actor types and fails closed before any downstream work.
