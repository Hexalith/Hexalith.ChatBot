# Story 7.16: Quarantine service client

Status: done

<!-- Validation: create-story checklist applied 2026-06-02. -->

## Story

As an authorized administrator,
I want to quarantine a misbehaving service client under a two-person rule,
so that a suspect automation is contained while evidence is reviewed — its future commands and queries are routed to a quarantined (contained-for-review) state and fail closed at the admission pipeline with safe next-action guidance — while every prior audit record stays reconstructable.

## Acceptance Criteria

1. Given a service client under investigation, when an authorized human admin proposes a **quarantine** and a **second** authorized human admin approves it (FR75d two-person rule), then the service client transitions to a durable **Quarantined** governance control state and **future commands and queries from that service client are routed to a quarantine (contained-for-review) state and fail closed** at the command/query admission pipeline, while **unrelated service clients and other actors continue normally** (isolation, NFR30/NFR58). The quarantine is a security-sensitive FR74 governance control — **not** the Epic 5 Keycloak-sourced grant lifecycle (`ServiceClientGrant.IsRevoked`/`ExpiresAt`) — so it MUST go through the same submit→second-person-approve flow established for the Story 7.15 service-client disable (`SubmitServiceClientDisable`→`ApproveServiceClientDisable`) and the Story 7.13 mailbox-source quarantine (`SubmitMailboxSourceQuarantine`→`ApproveMailboxSourceQuarantine`); a single-actor quarantine never takes effect. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.16`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75d`; `_bmad-output/implementation-artifacts/7-15-disable-service-client.md`; `src/Hexalith.ChatBot.Server/Operations/GovernedOperationAggregate.cs:243`]

2. Given the quarantine proposal and approval, when authorization runs, then the operation is permitted only for a **human tenant administrator** (service-client governance is a TenantAdmin responsibility per the RBAC Matrix — there is no finer service-client admin scope), and is **denied for service clients and AI actors** even when they carry tenant-admin-looking claims, exactly as `AdminAuthorityEvaluator.HasHumanTenantAdmin(principal)` already gates `SubmitServiceClientDisable`/`ApproveServiceClientDisable`. The approving admin MUST be a **different person** from the proposer: both `RequesterRef != ApproverRef` (Ordinal safe-token compare) and `RequesterActorId != approver envelope UserId` are enforced — at the gateway validation stage, the accepted-command dispatcher, **and** re-checked in the aggregate, mirroring `IsValidServiceClientDisableApproval`, `AcceptedCommandDispatcher`'s distinct-approver guard, and `GovernedOperationAggregate.Handle(ApproveServiceClientDisable)`. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75a`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75d`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md` (RBAC Matrix — TenantAdmin owns service-client grants); `src/Hexalith.ChatBot.Server/Governance/Admin/AdminAuthorityEvaluator.cs`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ParticipantAuthorizationStage.cs:118`; `src/Hexalith.ChatBot.Server/Gateway/Stages/AcceptedCommandDispatcher.cs:227`]

3. Given the quarantine is applied (approval committed), when it is recorded, then the operation records — with **no skip-audit path** (FR74, FR75g, NFR15a) — the **actor** (approver identity / actor type), **scope used** (`admin-scope:tenant-admin`), **subject** (the safe service-client ref / `ServiceClientId`), **reason** (documented justification reason code), **old state** (`Active`), **new state** (`Quarantined`), **policy snapshot id**, and **timestamp**, via a metadata-only `AuditEnvelope` whose `StateTransition` is `"Active->Quarantined"`. The audit is written through the existing fail-closed pre-commit seam (`IAuditWriter.RecordPreCommitAsync` via `CommandGateway`): when the pre-commit audit is unavailable, **no durable quarantine state is written and no admission-routing side effect occurs** (fail closed), reusing the disable/`CommandGateway` audit-unavailable behavior. The `tenant-admin` role does **not** bypass NFR15a/NFR50a. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.16`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75g`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR15a`; `src/Hexalith.ChatBot.Server/Audit/AuditEnvelopeFactory.cs:1443`; `src/Hexalith.ChatBot.Server/Gateway/CommandGateway.cs`]

4. Given a service client is Quarantined, when that service client submits **any command** (and, where service-client query admission is wired, any query), then the authorization stage **fails closed before admission** — `ServiceClientGrantValidator` (which already runs only for `service`/`ai` actor types) returns `ChatBotAuthorizationResult.Denied("service_client_quarantined")` **before** the grant scope/allowlist checks and before any durable work — so no command from the quarantined client is dispatched and no restricted data is returned. The quarantine check sits **beside** the existing disabled-state check (after `IsRevoked`/`ExpiresAt`, before scope/allowlist). A command from any **other (still-Active)** service client for the same tenant is unaffected (isolation). The new `service_client_quarantined` reason is **distinct from** the Story 7.15 `service_client_disabled` (the same two-person governance family, different control state) and from the Epic 5 `service_client_grant_revoked` (Keycloak grant revocation). [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.16`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ServiceClientGrantValidator.cs:73`; `src/Hexalith.ChatBot.Server/Gateway/ChatBotAuthorizationReasonCodes.cs:33`; `src/Hexalith.ChatBot.Contracts/Identities/ServiceClientGrant.cs`]

5. Given a service client is quarantined, when its prior activity is inspected, then **all previously recorded commands, audit envelopes, and workflow items that originated from that client remain visible, intact, and fully reconstructable** — quarantine affects **only future admission**, never already-committed records, associations, files, approvals, conversation content, or their audit trails (NFR17 visible/recoverable states; FR75c admins cannot mutate project-level records). Quarantine is reversible by a future release/re-activate flow; this story does not delete or rewrite any prior record. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR17`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75c`; `_bmad-output/implementation-artifacts/7-15-disable-service-client.md`]

6. Given an actor encounters a quarantined service client (admin viewing status, or an admission routed to quarantine), when guidance is surfaced, then **safe recovery guidance** is shown from the **finite message catalog** — a safe headline (≤ 80 chars), a one-line reason from a finite set conveying "contained for review", a next-action pointing to the responsible role (review/release is a tenant-admin/two-person action), and a `disabled-action` reason — using `ChatBotMessageCatalog` / `ChatBotMessageCodes` / `ChatBotDisabledActionReasons`, never raw error text. The guidance conveys that the automation is contained while evidence is reviewed and never names an unauthorized project/file/party/mailbox-content/audit detail (NFR2); EN/FR via existing localization; stable machine tokens (reason codes, state tokens, correlation ids) stay untranslated. ## Dev Notes

### Scope Boundaries

- Story 7.16 is the **fifth** cell of the FR74 enforcement series (7.12–7.26: five subject classes — mailbox / service-client / AI-actor / command-capability / outbound — × three actions — disable / quarantine / rate-limit). It implements exactly **one** cell: **service client × quarantine**. Disable (7.15) and quarantine (this story) are **security-sensitive** admin operations gated by the **FR75d two-person rule**; rate-limit (7.17) is a standard policy mutation. **Do not** implement rate-limit, any other subject class, or a future quarantine-release/re-activate flow here. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`]
- **Quarantine ≈ Disable at the service-client admission seam — the one meaningful semantic difference.** For a service client there is **no intake worker** (unlike the mailbox cells); admission is enforced at `ServiceClientGrantValidator` inside the Authorization stage, which already runs only for `service`/`ai` actor types. Both disable (7.15) and quarantine (this story) **fail closed before admission** — they block future commands/queries before any durable work. The epic frames quarantine as "new work routed to a quarantined state with safe next-action guidance": for a service client, "new work" = new commands/queries, and "routed to quarantined" = fail closed at admission with a **distinct reason code, state token, lifecycle transition, and safe next-action guidance** (`quarantined` / "contained for review" vs `disabled` / "blocked until re-enabled"). There is **no** intake-routing branch and **no** worker change in this story — that is the key structural difference from the 7.13 mailbox quarantine.
- **Distinct from the Epic 5 grant lifecycle.** Service clients already have `ServiceClientGrant.IsRevoked` + `ExpiresAt`, but these are **Keycloak-claims-sourced** (`ClaimsServiceClientGrantResolver`) — externally owned grant signals returning `service_client_grant_revoked`/`service_client_grant_expired`. The FR74 quarantine is a **separate, ChatBot-domain, two-person governance control state** with a **new** `service_client_quarantined` reason code. Do **not** route quarantine through `IsRevoked` (it cannot carry the two-person justification and is owned outside the ChatBot domain) — this is the exact analog of the 7.15 "do not overload `IsRevoked`" decision.
- **Authorization scope = tenant-admin, not a subject-specific admin scope.** As in 7.15, there is **no** service-client `AdminScope` in the enum (`{SeeOnly, Operate, Policy, Mailbox, Compliance, AuditObligation}`), and the RBAC Matrix assigns service-client grant governance to **TenantAdmin**. Gate on `AdminAuthorityEvaluator.HasHumanTenantAdmin`. Do **not** add a new `AdminScope` value or reuse `Operate` (FR75c `Operate` is queue-item ops — retry/requeue/quarantine/dismiss — not identity/grant governance). Note: the queue-item `AdminQueueOperation.Quarantine` token is **unrelated** to this FR74 service-client control state — do not conflate.
- **Two-person rule (FR75d).** The quarantine requires submit→second-person-approve; a single-actor quarantine only ever produces a pending approval. Distinct approver is enforced **three times** (gateway validator, accepted-command dispatcher, aggregate re-check), exactly as 7.15 does.
- Quarantine affects **future admission only**. It must never delete, rewrite, or hide already-committed commands, audit envelopes, associations, files, approvals, or conversation content (NFR17, FR75c). It is reversible by a future release flow (out of scope here).
- Tenant identity is always from the **authenticated gateway binding**, never the command body. The subject (service client) and all audit refs are **metadata-only, safe tokens** (NFR2); credentials, OAuth grant fingerprints, and delegated-user PII never appear (NFR4/NFR5).
