# Story 9.9: Deletion and erasure workflow

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a compliance administrator,
I want deletion and erasure workflows that preserve audit defensibility,
so that GDPR obligations are met without mutating immutable audit history.

## Acceptance Criteria

1. **An authorized deletion or erasure run resolves each data class along the NFR49a path — projection-tombstone and key-shred where applicable — and never mutates the audit chain (NFR49a, architecture cross-cutting #13).**
   **Given** an authorized deletion or erasure request naming one or more ChatBot-owned data classes,
   **When** the workflow runs,
   **Then** for **each** requested data class it consults the canonical **Story 9.7 `DataClassInventoryCatalog.Published`** classification and decides a per-class **action** keyed off the class's `DeletionBehavior`: `key-shred` ⇒ `crypto-shredded`; `projection-tombstone` ⇒ `tombstoned`; `hard-delete` ⇒ `hard-deleted`; `retain-immutable` ⇒ `retained` (the class is never destroyed — reason `worm-retained`). The audit chain itself is **never** mutated — `audit-records` (`retain-immutable` in the seed) always resolves to `retained`; erasure that touches audit history is the **append-redaction + crypto-shred + projection-tombstone** path of the **existing Story 9.1 `AuditRedactionService`**, never a chain edit. The run is **correlation-stamped** (`CorrelationId` + `PolicySnapshotId`).
   - **Reuse the Story 9.7 inventory + the Story 9.1 erasure seam as single sources of truth; do NOT re-declare either.** The deletion-behavior dimension already exists (`DataClassDeletionBehaviors` `{ key-shred, projection-tombstone, hard-delete, retain-immutable }`) and the seed catalog already classifies every class. The workflow **reads** `DataClassInventoryCatalog.Published` (or the inventory carried in the request's referenced snapshot) — it must not fork a second deletion-behavior set, a second class-id set, or a second redaction-sensitivity set. The audit-chain erasure mechanism (append redaction record → `IKmsRedactionKeyStore.Shred` → `IRedactionProjectionStore.Tombstone`) **already exists** in `AuditRedactionService` (Story 9.1) and is DI-wired — consume it; do **not** build a second crypto-shred/tombstone path. Requested class ids are validated `⊆ ComplianceRetentionClassIds.All` (the extended 13-member canonical set).
   - **Closed, bounded token sets (each value an `AuditMetadata`-safe token).** Define: **action** `DeletionErasureClassActions` `{ crypto-shredded, tombstoned, hard-deleted, retained }`; **denial/exclusion reason** `DeletionErasureExclusionReasons` `{ worm-retained, unauthorized, not-requested }`; **per-class status** `DeletionErasureClassStatuses` `{ succeeded, failed-retryable, failed-terminal }`; **run status** `DeletionErasureRunStatuses` `{ completed, partial-failure, failed }`; **request mode** `DeletionErasureModes` `{ deletion, erasure }`. Each is a static class with `All` + `Contains`, mirroring `DataClassExportEligibilities`/`TenantExportClassDispositions` line-for-line. Callers select within the set, never invent members.

2. **A non-authorized actor's deletion or erasure request fails closed and is audited (NFR1).**
   **Given** an actor without compliance-admin scope (or a non-human actor — service client / AI actor), or a request whose per-project authority does not cover a requested resource,
   **When** deletion or erasure is requested,
   **Then** the command is **denied at the gateway** (`Denied(AuthorizationDenied)`), writes **no** durable state, destroys **no** data, and the denial is audited; where the actor has compliance scope but lacks per-project authority over a requested resource, the affected class is **`retained`/`unauthorized`** (no destructive action) and the recorded result carries **no** `project:` reference, file/message metadata, or candidate evidence for the hidden resource — indistinguishable from safe-not-found, exactly like the Story 9.3 compliance read surface.
   - **Mirror `ComplianceAuditReadPolicy.HasPerProjectAuthority` and the Story 9.8 `TenantExportAuthorizationPolicy` exactly — do NOT build a third authority path.** Add a server-side `DeletionErasureAuthorizationPolicy` that (a) gates on `AdminAuthorityEvaluator.HasHumanAdminScope(principal, AdminScope.Compliance)` and (b) computes per-project authority from `principal.FindAll(ParticipantAuthorizationStage.ProjectOwnerClaim)` filtered by `AuditMetadata.IsSafeStableIdentifier`, projecting into a **bounded** `DeletionErasureAuthorityView(bool HasComplianceScope, IReadOnlySet<string> AuthorizedProjectRefs)`. The pure `DeletionErasurePlanner.Plan(...)` in `.Contracts` consumes that bounded view (never a `ClaimsPrincipal`). When a project scope ref is not in `AuthorizedProjectRefs`, the planner emits `retained`/`unauthorized` and **drops the project ref** — the bounded reason token `unauthorized` is the only signal, never the resource identity (NFR2). **Destruction is fail-closed: unauthorized never escalates to a destructive action** (an `unauthorized` class is `retained`, never `crypto-shredded`/`tombstoned`/`hard-deleted`).

3. **An erasure never mutates the audit chain: redaction is appended, and nightly chain verification still passes (NFR49, NFR49a).**
   **Given** an erasure (`mode = erasure`) that touches audited subjects,
   **When** processed,
   **Then** the audit chain bytes are **untouched** — erasure of audit history runs strictly through the **existing** `AuditRedactionService.RegisterRedactionAsync` (encrypt original under a fresh per-subject KMS key → store opaque ciphertext → **append** a metadata-only redaction record, the chain grows by one) + `AuditRedactionService.Erase` (`IKmsRedactionKeyStore.Shred` + `IRedactionProjectionStore.Tombstone`); after erasure the `WormAuditChainVerifier` nightly per-tenant verification still verifies end-to-end (Story 9.1 AC2 invariant holds). The workflow itself **adds no new commit-time gate** and **never** deletes or rewrites a chain record.
   - **The erasure-over-WORM mechanism is solved (Story 9.1) — this story orchestrates it, it does not reimplement it.** Reference `AuditRedactionService` (the crypto-shred + append-redaction + tombstone coordinator), `IKmsRedactionKeyStore` (separate-KMS key-shred boundary), `IEncryptedAuditOriginalStore` (opaque ciphertext), `IRedactionProjectionStore` (tombstone → safe-not-found), and `WormAuditChainVerifier` (nightly verification). A contract/server test must assert that an erasure run leaves the chain verifiable (reuse the Story 9.1 `AuditRedactionServiceTests` / `WormAuditChainVerifier` harness).

4. **A deletion that cannot complete for a data class enters a visible retryable or terminal state with reason and next action — no silent partial deletion (NFR17, NFR18).**
   **Given** a deletion/erasure where one or more classes fail,
   **When** the run completes,
   **Then** each class carries a `DeletionErasureClassStatuses` status; the **run status** is `completed` (all actionable classes succeeded), `partial-failure` (some failed), or `failed` (all failed); a failed class is **never silently dropped** — it carries a `failed-retryable` (with `NextRetryAt` / `SafeNextAction`) or `failed-terminal` (with `TerminalReasonCode` / `ManualRecoveryAction`) state and contributes **no** proof entry; and the run is **retryable** under the **stable `DeletionRunId`** (the idempotency key) — a re-submission carrying the same `DeletionRunId` and a matching `SourceVersion` is version-guarded and idempotent (no duplicate destruction), per the two-altitude idempotency floor (Story 1.5) and the retry policy (NFR18).
   - **Reuse `RetryFailurePolicy.Classify` for retryable-vs-terminal — do NOT invent a second retry taxonomy.** A per-class failure reason code is classified via `RetryFailurePolicy.Classify(reasonCode, retryCount, observedAt)`: a retryable decision ⇒ `failed-retryable`; a terminal/exhausted decision ⇒ `failed-terminal`. "No silent partial deletion" is a **schema-level invariant** in `DeletionErasureSchema`: every requested class appears in `ClassResults` exactly once, a non-`succeeded` class contributes **no** proof entry, and the `RunStatus` is consistent with the per-class statuses (a run claiming `completed` with any non-`succeeded` actionable class is rejected).

5. **A completed erasure produces a proof artifact (tombstone + per-store key-shred confirmation) queryable for compliance (NFR53).**
   **Given** a completed erasure,
   **When** the proof is assembled,
   **Then** the run produces a metadata-only `ErasureProofArtifact` carrying, per successfully-erased subject/class: the **tombstone confirmation** (tenant-scoped subject locator + `tombstoned: true`) and the **per-store key-shred confirmation** (the safe KMS key handle + `shredded: true`), plus the `DeletionRunId`, `CorrelationId`, and a deterministic `sha256:` `ProofFingerprint` over the confirmation set — no raw content, no subject PII, only safe tokens. The proof is **queryable for compliance** through the run's audit envelope (the `deletion-proof:`/`erasure-tombstone:`/`erasure-key-shred:` evidence refs of Task 6 make it reconstructable from the chain alone). A class that did not reach `succeeded` contributes **no** proof entry (consistent with AC4 — no partial-proof exposure).

### Cross-cutting requirements that hold for every AC

- **Define-once / reuse — do NOT reinvent.** Consume by reference: the Story 9.7 `DataClassInventoryCatalog.Published` / `DataClassClassification` / **`DataClassDeletionBehaviors`** / `DataClassRedactionSensitivities` and the canonical `ComplianceRetentionClassIds` (extended, 13 members); the **Story 9.1 `AuditRedactionService` + `IKmsRedactionKeyStore` + `IRedactionProjectionStore` + `IEncryptedAuditOriginalStore` + `WormAuditChainVerifier`** (the **one** WORM-safe erasure mechanism); the Story 7.4 `RetentionValidationResult` (the **one** validation-result type) + `ComplianceAdministrationSchema` (`IsSafeComplianceToken`, `IsSafeFingerprint`, `IsUtc`); the Story 9.8 `TenantExport*` shapes as the **structural template** for the governed-command/planner/schema/authority/audit pattern; the `AdminAuthorityEvaluator.HasHumanAdminScope(…, AdminScope.Compliance)` gate; the `ParticipantAuthorizationStage` per-command `Submit…` gating + `IsValid…`/`Read…` pattern; the `ComplianceAuditReadPolicy.HasPerProjectAuthority` per-project no-leak pattern; the `ChatBotSpineCommandAllowlist`; `RetryFailurePolicy.Classify`/`RetryPolicyDecision` (the **one** retry taxonomy); the `AuditEnvelopeFactory.SourceEvidenceRefs` per-command block + `PolicyEvidenceRefs`/`SafeObjectArrayRefs`/`SafeRefArray` helpers. **Do not** build a second authority path, a second crypto-shred/tombstone mechanism, a second policy-snapshot record, a second retry taxonomy, a second class-id/behavior set, or a second validation-result type.
- **Fail-closed + audit-everything floor (NFR1, NFR15a, FR75f, FR75g).** `SubmitDeletionErasureRequest` is a **destructive** state-writing path: it routes through the one CommandGateway spine (`auth → authorize → … → pre-commit-audit → execute → post-commit-audit`); on non-compliance scope, non-human actor, invalid command, or audit-writer-down it returns a typed rejection, destroys **nothing**, and writes **no** durable state. No deletion/erasure path skips audit. Destruction is the most dangerous operation in the system — bias every ambiguous case toward `retained`.
- **WORM / two-phase audit untouched (D4, NFR49, NFR49a, architecture #13).** This story emits its own audit through the **existing** pre-/post-commit path and never adds a commit-time gate; the **only** way it touches audit history is the existing `AuditRedactionService` append-redaction + crypto-shred + tombstone path. `audit-records` (`retain-immutable`) is **always** `retained` — never `crypto-shredded`/`tombstoned`/`hard-deleted` as a class action. The chain grows or stays; it never shrinks or mutates.
- **Metadata-only / no-leak (NFR2, NFR42, NFR45).** Every emitted token (run id, class ids, actions, exclusion reasons, key handles, subject locators, fingerprints, scope refs) is an `AuditMetadata`-safe bounded token; fingerprints are `sha256:` digests; an `unauthorized` exclusion never carries the hidden project/file/message ref. Extend the no-leak + cross-tenant serialization suites to every new type.
- **Boundary (NetArchTest-enforced).** New `.Server` internals (the authorization policy, any failure classifier, the auth-stage validator/reader) stay `internal` to `.Server`; the shared contracts (`DeletionErasure*` records, `SubmitDeletionErasureRequest`, the closed-set token classes, `DeletionErasureSchema`, `DeletionErasurePlanner`, `ErasureProofArtifact`) live in `.Contracts` exactly like `TenantExportContracts.cs` and carry no server/gateway/`ClaimsPrincipal` dependency. No `.UI`/`.Cli`/`.Mcp` references a `.Server.Gateway` type.
- **Inert-control-floor honesty.** This story ships the **deletion/erasure governed command + the deletion-behavior-aware/authority-bounded action decision (plan) + per-class success/failure model + stable-run-id idempotent retryability + the no-silent-partial-deletion schema invariant + the `ErasureProofArtifact` model + NFR45/NFR50 audit recording + reuse of the Story 9.1 audit-chain erasure seam + validation + tests + ADR** — the governed *decision/recording/proof* layer that makes "GDPR obligations met without mutating immutable audit history" real. **Deferred** (state explicitly in Completion Notes): the live S-tagged deletion/erasure UI surface, and the storage-layer **destruction runtime** that actually reaches into each non-audit derived store (vector indexes, embedding/cache stores, attachment folders, projection stores) and crypto-shreds/tombstones/hard-deletes its bytes — **except** the audit-chain erasure path, which is **not** deferred because Story 9.1's `AuditRedactionService` already implements it and this story wires the workflow to it. Never let "the per-store destruction runtime isn't wired for non-audit stores" read as "deletion is unbounded/untraceable" — the request **is** governed, the plan **is** behavior/authority bounded, the audit-chain erasure **is** real, and the run **is** audited with a proof artifact.

## Dev Notes

### What this story actually changes (and what already exists)

Story 9.9 makes the ChatBot's **deletion and erasure governed, deletion-behavior-aware, authority-bounded, and audit-defensible**: an authorized compliance-admin submits `SubmitDeletionErasureRequest`, and a pure `DeletionErasurePlanner` decides — per requested data class — whether the action is `crypto-shredded`, `tombstoned`, `hard-deleted`, or `retained`, keying off the **Story 9.7 `DataClassInventoryCatalog.Published`** `DeletionBehavior` classification and the requester's per-project authority, then records the run (requester, scope, classes, actions, proof, correlation, outcome) through the **existing** audit-commit spine. The **erasure-over-audit-chain mechanism already exists** (Story 9.1 `AuditRedactionService`: append redaction record → KMS key-shred → projection tombstone, chain stays verifiable) — this story **orchestrates it**, it does not reimplement it. It is the **direct sibling of Story 9.8 export** and the **second consumer of the Story 9.7 inventory** (9.7's "so that" was literally "before export **or deletion** workflows use them"). Like 9.4–9.8, it is **almost entirely additive contracts + a pure decision engine + a governed-command + gateway-gating + audit-evidence story built on mature seams** — reuse, do not reinvent.

**The single most important framing for the dev agent:** there are **four** structural templates to mirror, and a reviewer will diff against them line-for-line:
1. **`SubmitTenantExportRequest` (Story 9.8)** — the governed compliance command shape, the allowlist line, the `ParticipantAuthorizationStage` gating block + `IsValid…`/`Read…`, the `AuditEnvelopeFactory` evidence block, the closed-set token classes, the pure planner + schema, the `TenantExportAuthorizationPolicy`. `SubmitDeletionErasureRequest` is the structural twin (export → destruction). **This is the closest template — read `9-8-tenant-export-workflow.md` and `TenantExportContracts.cs` first.**
2. **`AuditRedactionService` (Story 9.1)** — the WORM-safe erasure mechanism (crypto-shred + append-redaction + projection-tombstone, chain stays verifiable). **Consume it — never build a second.**
3. **`ComplianceAuditReadPolicy.HasPerProjectAuthority` (Story 9.3) / `TenantExportAuthorizationPolicy` (Story 9.8)** — the per-project, no-leak authority evaluation. `DeletionErasureAuthorizationPolicy` mirrors them.
4. **`RetryFailurePolicy.Classify` (NFR18)** — the one retry taxonomy for `failed-retryable` vs `failed-terminal`.

The genuinely **new** value is the `DeletionErasurePlanner` decision engine (deletion-behavior → action, authority → `retained`/`unauthorized` with **destruction biased fail-closed**, WORM-class absolute), its `DeletionErasureSchema` invariants (behavior-vs-action, no-silent-partial, proof), and the `ErasureProofArtifact` model.
