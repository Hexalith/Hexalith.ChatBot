# Story 7.17: Rate-limit service client

Status: done

<!-- Validation: create-story checklist applied 2026-06-02. -->

## Story

As an authorized administrator,
I want to rate-limit a service client through a single-actor, schema-bounded policy mutation,
so that automation cannot consume disproportionate command capacity — **command admission** enforces the bounded per-window limit and returns a typed, redacted rate-limit response when the client exceeds it, while unrelated service clients and tenants keep their own independent budgets and are protected from degradation where isolation is possible.

## Acceptance Criteria

1. Given a service client exceeding quota or rate thresholds, when an authorized **human tenant-admin** configures a rate limit, then a durable per-service-client rate-limit budget is recorded and **command admission applies the bounded limit** to that client's commands. This is a **standard, single-actor policy mutation** — explicitly **NOT** the Story 7.15/7.16 FR75d two-person control: FR74's decomposition guidance states "disable and quarantine are security-sensitive admin operations (per FR75d two-person rule); **rate-limit is a standard policy mutation**." So the command follows the **single-actor** authorization shape of the Story 7.14 `SubmitMailboxSourceRateLimit` (one authority check, no approver), **not** the submit→second-person-approve flow of `SubmitServiceClientDisable`/`SubmitServiceClientQuarantine`; there is **no** `Approve…` counterpart, **no** distinct-approver guard, **no** `AcceptedCommandDispatcher` branch, and **no** `ServiceClientControlState`/lifecycle transition (rate-limit is a *parameter*, not a control state). [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.17`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`; `_bmad-output/implementation-artifacts/7-14-rate-limit-mailbox-source.md`; `src/Hexalith.ChatBot.Contracts/Commands/MailboxSourceControlContracts.cs:118`]

2. Given the rate-limit value, when it is validated, then it is **bounded by the Tenant Policy Schema** (FR75): the configured per-window command budget is accepted only within a declared, closed, non-negative min/max range, and an out-of-range / wrong-type / undeclared value is **rejected with a safe reason code** (and, at the enforcement seam, falls back to safe defaults — never silently raising the cap). Mirror the closed `MailboxRateLimitBounds` discipline from Story 7.14 (`Minimum`/`Maximum`/`SafeDefaults`/`IsWithinBounds`, itself mirroring Story 7.9 `NotificationThrottleCeilings`) — a tenant cannot introduce a new window dimension or a custom formula. The bound is a Standard (non-security-sensitive) knob, so no two-person rule applies. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75`; `src/Hexalith.ChatBot.Contracts/Commands/MailboxRateLimitBounds.cs:14`; `src/Hexalith.ChatBot.Contracts/Commands/NotificationThrottleCeilings.cs:16`]

3. Given authorization runs, when the command is evaluated, then it is permitted only for a **human tenant administrator** (service-client governance is a TenantAdmin responsibility per the RBAC Matrix — there is no finer service-client admin scope, and there is no mailbox/policy/compliance/operations scope for it) and is **denied for service clients and AI actors** even when they carry tenant-admin-looking claims, exactly as `AdminAuthorityEvaluator.HasHumanTenantAdmin(principal)` already gates `SubmitServiceClientDisable`/`SubmitServiceClientQuarantine`. There is **no** second-person/distinct-approver requirement for rate-limit; a single authorized human tenant-admin applies it. Denial uses `ChatBotAuthorizationReasonCodes.AuthorizationDenied`. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75a`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md` (RBAC Matrix — TenantAdmin owns service-client grants); `src/Hexalith.ChatBot.Server/Governance/Admin/AdminAuthorityEvaluator.cs:35`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ParticipantAuthorizationStage.cs:118`]

4. Given the rate limit is applied (committed), when it is recorded, then the operation records — with **no skip-audit path** (FR74, FR75g, NFR15a) — the **actor** (requester identity / actor type), **scope used** (`admin-scope:tenant-admin`), **subject** (the safe service-client ref / `ServiceClientId`), **reason** (documented justification reason code), **old state** (the prior budget / `unlimited`), **new state** (the new bounded budget), **window token**, **policy snapshot id**, and **timestamp**, via the metadata-only `AuditEnvelope`. There is **no** `StateTransition` ref (rate-limit is not a lifecycle transition — old/new "state" are budgets). The audit is written through the existing fail-closed pre-commit seam (`IAuditWriter.RecordPreCommitAsync` via `CommandGateway`): when the pre-commit audit is unavailable, **no durable rate-limit state is written and no enforcement side effect occurs** (fail closed), reusing the disable/`CommandGateway` audit-unavailable behavior. The `tenant-admin` role does **not** bypass NFR15a/NFR50a. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.17`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75g`; `src/Hexalith.ChatBot.Server/Audit/AuditEnvelopeFactory.cs:1598`; `src/Hexalith.ChatBot.Server/Gateway/CommandGateway.cs`]

5. Given a service client has a rate-limit budget configured, when that client submits a command and its recent **admitted-command** count in the trailing rolling window has reached the effective budget, then **command admission enforces the limit at `ServiceClientGrantValidator`** — returning `ChatBotAuthorizationResult.Denied(ChatBotAuthorizationReasonCodes.ServiceClientRateLimited)` (a typed, redacted rate-limit response) so the over-budget command is **not dispatched and no restricted data is returned**. This check sits **after** the disable/quarantine control-state blocks **and after** the grant scope/allowlist checks — i.e. it is the **final admission gate**, so only otherwise-fully-admissible commands count against the budget and a disabled/quarantined/expired/revoked/over-/under-scoped command keeps its own precise reason code (rate-limit never masks a security denial). When the client is **under** budget the command is admitted normally. The trailing-window count is computed with the established clock-injected window math (`NotificationThrottleEvaluator.CountInTrailingWindow`: server-measured UTC age, never client/item-supplied time), keyed per-`(tenant × service-client)`. `ServiceClientGrantValidator` already runs only for `service`/`ai` actor types and already has `ISystemClock` injected. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.17`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ServiceClientGrantValidator.cs:73`; `src/Hexalith.ChatBot.Server/Notifications/NotificationThrottleEvaluator.cs:63`]

6. Given rate-limiting is in effect, when queue/capacity impact is observed, then admission **exposes capacity-impact metrics** — at minimum the effective budget, the observed trailing-window admitted-command count, and whether this command was denied (throttled) for the source — carried as safe, finite integer tokens at the audit/observable seam (mirror the Story 7.14 `MailboxRateLimitObservation` / Story 7.9 `NotificationThrottleOutcome` shape: integer/rational arithmetic, never floats). Rate-limiting **protects unrelated tenants/service-clients from degradation where isolation is possible** (NFR30, NFR18): each service client's budget and trailing-window counter are **independent**, so throttling a noisy client never throttles or starves a sibling client or another tenant. Full operational-dashboard wiring is Epic 8 and is out of scope here — this story exposes the metric at the audit/observable seam only. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.17`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR30`; `src/Hexalith.ChatBot.Workers/Mailbox/MailboxRateLimitState.cs:57`]

7. Given a command is denied for a rate-limited service client, when guidance is surfaced, then **safe recovery guidance** is shown from the **finite message catalog** — a safe headline (≤ 80 chars), a one-line reason conveying "command capacity temporarily limited to protect other automation; retry shortly", a next-action of **`retry-later`** (transient, **not** `request-access` — the client is not disabled or quarantined), and a **transient** `dependency-degraded` reason (**not** `disabled-action`) — using `ChatBotMessageCatalog` / `ChatBotMessageCodes` / `ChatBotMessageNextActions` / `ChatBotDisabledActionReasons`, never raw error text. This matches the Story 7.14 mailbox-rate-limit catalog choice and is deliberately distinct from the terminal `service_client_disabled`/`service_client_quarantined` entries. The guidance never names an unauthorized project/file/party/mailbox-content/audit detail (NFR2); EN/FR via existing localization; stable machine tokens (reason codes, state tokens, correlation ids) stay untranslated. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR76`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR2`; `src/Hexalith.ChatBot.Contracts/Messages/ChatBotMessageCatalog.cs:441`; `src/Hexalith.ChatBot.Contracts/Messages/ChatBotMessageNextActions.cs`; `src/Hexalith.ChatBot.Contracts/Messages/ChatBotDisabledActionReasons.cs`]

8. Given the rate-limit subject and audit refs are metadata, when the command and audit envelope are serialized, then they carry **only safe, finite tokens** — the safe service-client ref (`ServiceClientId`), `admin-operation:service-client-rate-limit` / `admin-scope:tenant-admin`, the reason code, old/new budget values, the window token, policy-snapshot id, correlation id, UTC timestamp — and **never** service-client credentials, OAuth grant fingerprints, bearer tokens, secrets, raw claims/headers, delegated-user PII, mailbox/project/proposal/evidence content, or raw GUIDs that are not already safe identifiers (NFR2, NFR4, NFR5). The subject is identified by its existing safe id (`ServiceClientGrant.ServiceClientId` via `AuditMetadata.SafeOptionalToken` / `IsSafeStableIdentifier`). Tenant scope comes **only** from the authenticated gateway binding — never from the command body. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR2`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR4`; `src/Hexalith.ChatBot.Server/Audit/AuditMetadata.cs`; `src/Hexalith.ChatBot.Contracts/Commands/ServiceClientControlContracts.cs`]

## Dev Notes

### Scope Boundaries

- Story 7.17 is the **sixth** cell of the FR74 enforcement series (7.12–7.26: five subject classes — mailbox / service-client / AI-actor / command-capability / outbound — × three actions — disable / quarantine / rate-limit). It implements exactly **one** cell: **service client × rate-limit**. Disable (7.15) and quarantine (7.16) are **security-sensitive** admin operations gated by the **FR75d two-person rule**; **rate-limit (this story) is a standard, single-actor policy mutation** bounded by the Tenant Policy Schema. **Do not** implement any other subject class, the disable/quarantine actions, or a future rate-limit-release/reset flow here. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`]
- **This story is a cross-product: take the 7.14 single-actor rate-limit pattern and apply it to the 7.15/7.16 service-client subject + admission seam.** Read 7.14 (mailbox rate-limit) for the *single-actor command / bounds / window / direct-activation aggregate / audit-without-StateTransition / transient catalog / no-dispatcher-branch / no-lifecycle-transition* shape, and 7.15/7.16 (service-client disable/quarantine) for the *service-client subject + `HasHumanTenantAdmin` authority + `ServiceClientGrantValidator` admission seam + read-side deferral*. The result is the **only** cell that is both single-actor **and** enforced at command admission.
- **The three meaningful divergences from the 7.14 mailbox-rate-limit template — read these first:**
  1. **Subject + authority.** Subject is a **service client** (`ServiceClientRef`/`ServiceClientId`), and authorization is **`HasHumanTenantAdmin`** (service-client governance is a TenantAdmin responsibility — there is **no** service-client `AdminScope` and **no** `AdminScope.Mailbox` for it), exactly as 7.15/7.16 gate the service-client disable/quarantine. 7.14 used `HasHumanAdminScope(AdminScope.Mailbox)` — **do not** reuse a mailbox scope here.
  2. **Enforced at command admission, not a worker.** Service clients have **no** intake worker. The epic AC says "command admission enforces the limit and returns typed, redacted rate-limit responses." Enforcement therefore lives in **`ServiceClientGrantValidator`** (which already runs only for `service`/`ai` actors and already has `ISystemClock` injected), as a `Denied("service_client_rate_limited")` return — **not** in any worker. There is **no** `GraphMailboxIntakeWorker` analog and **no** Workers-project change in this story. This is the single biggest structural difference from 7.14.
  3. **Counting admitted commands at the seam (final gate).** The trailing-window count is over **admitted commands** for the `(tenant × service-client)`, and the check is the **last** admission gate (after scope/allowlist) so it never masks a security denial. The durable read-side (budget projection + admitted-command history incremented on success) is **deferred** like 7.14/7.15/7.16; the seam is implemented and unit-tested in isolation via injected fakes.
- **Same as 7.14 (do not reintroduce the two-person machinery):** single-actor — **no** `Approve…` command, **no** pending-approval event/dictionary, **no** `AcceptedCommandDispatcher` branch/distinct-approver guard, **no** aggregate distinct-approver re-check. **Not** a control state / lifecycle transition — **no** `ServiceClientControlState`/`LifecycleStates`/`LifecycleTransitionValidator`/`CommandSubmissionLifecycleTransitionGuard` change; "old state"/"new state" in the audit = old budget / new budget. **Transient** catalog guidance (`retry-later` + `dependency-degraded`), not the terminal `request-access` + `disabled-action`.
- **Bounded by the Tenant Policy Schema (FR75).** The budget value is accepted only within a declared closed range. Reuse the `MailboxRateLimitBounds` discipline (Story 7.14): `Minimum`/`Maximum`/`SafeDefaults`/`IsWithinBounds`, out-of-bounds → safe default (= maximum), never raise the cap. A tenant cannot add a new window dimension or a custom formula.
- **Isolation (NFR30/NFR18).** Each service client has an independent budget + trailing-window counter. Throttling a noisy client must never throttle a sibling client or another tenant. Tenant identity is always from the **authenticated gateway binding**, never the command body. The subject and all audit refs are **metadata-only, safe tokens** (NFR2).
- Rate-limit affects **future command admission only**. It must never delete, rewrite, or hide already-committed commands, audit envelopes, associations, files, approvals, conversation content, or their audit trails (NFR17, FR75c).

### Architecture Guardrails

- Contracts (command, bounds record, window enum) → `src/Hexalith.ChatBot.Contracts`. Aggregate handler/state/event → `src/Hexalith.ChatBot.Server/Operations` + `src/Hexalith.ChatBot.Server/Governance/ServiceClient`. Authorization + the admission rate-limit seam + the two read-side seam interfaces → `Gateway/Stages` + `Governance/Admin`. Audit refs → `src/Hexalith.ChatBot.Server/Audit`. **No** Workers-project change (this is the key structural difference from the 7.14 mailbox rate-limit). No new top-level project.
- Use records/enums/finite tokens, never delimited strings or ad-hoc dictionaries, for state/role/scope/reason/budget. Budget/window arithmetic is integer/rational (never float). Window age is server-measured UTC against the injected `ISystemClock` — never client/item-supplied time. Use Ordinal string comparison for all ref/id equality. No `GetHashCode()` fingerprints for identity.
- Tenant id from authenticated binding only. Deny-by-default on missing/ambiguous/invalid admin role/scope claims; unknown roles imply no access.
- The rate-limit budget is a **Tenant-Policy-Schema-bounded knob**, not a free-form value; out-of-bounds → safe default, never raise the cap.
- Every committed rate-limit mutation is preceded by a fail-closed pre-commit audit; on audit-unavailable, no durable/observable side effect. No state-write that bypasses audit. Never expose service-client credentials, OAuth grant fingerprints, or delegated-user PII in any event/envelope/log (NFR4/NFR5).

### Completion Notes List

Story 7.17 = the **single-actor rate-limit** template (7.14) retargeted onto the **service-client subject + admission seam** (7.15/7.16). Variances decided (per Project Structure Notes):

1. **Single-actor command** — `SubmitServiceClientRateLimit` mirrors `SubmitMailboxSourceRateLimit` field-for-field (substituting `ServiceClientRef`); **no** `Approve…` counterpart, **no** `ApproverRef`, **no** `ServiceClientControlState` old/new-state fields. "Old/new state" are the per-window budgets.
2. **Bounds** — `ServiceClientRateLimitBounds`: `Minimum = 0`, `Maximum = 10000`, `SafeDefaults = Maximum` (10000 commands/rolling-hour — higher than the mailbox 1000 because command automation is legitimately higher-volume; finite enough to bound a runaway client). Out-of-bounds → `SafeDefaults` (the cap), never raises.
3. **Dedicated schema version** — `ServiceClientRateLimitSchemaVersions.V1 = "service-client-rate-limit-schema.v1"` (not `ServiceClientControlSchemaVersions.V1`), because the rate-limit shape diverges from the disable/quarantine control commands.
4. **Authority = `HasHumanTenantAdmin`** — service-client governance is a TenantAdmin responsibility; there is no service-client `AdminScope` and no mailbox scope for it. Service/AI actors denied via the human-actor gate inside `HasHumanTenantAdmin`. Single actor, no second-person/distinct-approver requirement.
5. **Enforcement = `ServiceClientGrantValidator` final admission gate** — placed **after** control-state, grant-lifecycle (expired/revoked), tenant/surface, over-scoped, and under-scoped(allowlist) checks and immediately before the terminal `Allowed(...)` return. Window math reuses `NotificationThrottleEvaluator.CountInTrailingWindow` (Server-side `public static`; server-measured UTC age against the injected `ISystemClock` — never client/item-supplied time).
6. **Catalog guidance = transient** — `ServiceClientRateLimited` entry uses `RetryLater` + `DependencyDegraded` (not `RequestAccess` + `DisabledAction`), deliberately distinct from the terminal `service_client_disabled`/`service_client_quarantined` entries.
