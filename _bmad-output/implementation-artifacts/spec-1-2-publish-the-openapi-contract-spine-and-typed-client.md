## Intent

**Problem:** The existing OpenAPI 3.1 spine and client cover submission and status, but callers cannot reuse an identity for retries. Accepted results omit retry/prior-outcome facts, server DTOs duplicate the contract, and current checks cannot prove generated or serialized parity.

**Approach:** Complete the contract and typed Client additively; make generation, exposure, serialization, and safe-outcome checks fail on drift.

## Boundaries & Constraints

**Always:** Keep OpenAPI 3.1 authoritative for touched HTTP routes/DTOs/errors. Retain typed `IChatBotCommand` submission, cancellation, correlation, and existing callers; accept caller-stable `commandId` for replay. Preserve status identity as `taskId ?? commandId`. Use camelCase, UTC `DateTimeOffset`, declared IDs, opaque cursors, and versioned safe codes. Emit metadata-only, existence-neutral outcomes. Keep exposure and authorization separate and deny-by-default.

**Never:** Hand-edit NSwag output, create competing wire DTOs, trust client tenant claims, weaken gateway/idempotency/audit rules, edit sibling submodules, or claim runtime parity or release readiness from fixtures.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
| --- | --- | --- | --- |
| Submit | Typed command, stable command ULID, correlation, cancellation | Request retains identity; response gives canonical status ID, state, reason, retry eligibility, optional prior outcome | Invalid ULID fails before transport |
| Replay | Same command and ULID | Same identity and stored outcome representation | Conflicting reuse yields safe versioned problem |
| Status/read | Authorized operation or page | Safe status; opaque cursor; UTC time | Unknown/unauthorized resources remain existence-neutral |

- OpenAPI 3.1 now declares authoritative accepted, prior-outcome, status, and safe-problem fields with exact request media and origin rules. NSwag output was regenerated and independently compared byte for byte; the generated SHA-256 fixture is `8d5161ef151fd82866150ab1cbd9ed81472b955a4e740951910e42f37f83f4f3`. The typed facade retains `SubmitAsync` and adds caller-stable `SubmitWithCommandIdAsync` with pre-transport ULID validation.
- The HTTP boundary validates declared metadata and allowlisted specialized payloads, including null collection elements, dictionaries, init-only members, and nested casing/duplicate keys, before admission. Generated contract types serialize accepted and metadata-only versioned problem responses; examples are checked against their OpenAPI schemas.
- Both coarse stores reserve tenant-scoped caller IDs and preserve specialized domain deduplication. Dapr uses first-write identity ownership plus a domain shadow receipt; it keeps pending ownership across expiry, checks failed cleanup, repairs partial outcome writes, and returns a retryable safe 503 while a committed outcome is unresolved. A retained tenant-scoped post-commit audit envelope can automatically restore an outcome on same-ID retry after a Dapr store instance is replaced; the replay-intent queue also carries the safe outcome for operator reconciliation. Controlled concurrency and failure tests assert one dispatch.
- Workflow status uses UTC timestamps and an injected clock, updates catalog-backed reasons and actions, and clears the due retry flag before a new resolution attempt. GET tests cover before/at due and recovery. The runtime conformance oracle derives accepted, replay, conflict, denied, and workflow status results from production paths.
- The registered audit-history reader, WORM store, and replay queue are currently in memory. Recovery after a process restart requires deployment-provided durable audit retention; no real Dapr sidecar test ran. These limits prevent a release-readiness claim from the fake-backed tests.
- Review loop 6 adds camel-case generated transport serialization, enum dictionary-key rejection, pending legacy reservation handling, reservation-ID fenced Dapr cleanup, expiry-safe shadow-receipt replay, and full safe-field conformance checks. A fallback audit write that fails now emits `post_commit_evidence_unavailable` in the operator alert and process-local replay intent. A failed fallback still has no verified durable recovery evidence; the queue has no live consumer, and transient abort cleanup can leave a reservation. Those recovery tasks remain open under AD-2's atomic mutation target.
- Pre-upgrade generic Dapr records remain body-keyed and lack a caller-ID index. Preserve unchanged-body replay; retroactive changed-body conflict detection requires a separate migration policy.
