# Story 7.15: Disable service client

Status: done

<!-- Validation: create-story checklist applied 2026-06-02. -->

## Story

As an authorized administrator,
I want to disable a misbehaving service client under a two-person rule,
so that a compromised or invalid automation loses access immediately — its future commands and queries fail closed at the admission pipeline — while every prior audit record stays reconstructable and safe recovery guidance is shown.

## Acceptance Criteria

1. Given a service client producing unsafe or policy-violating activity, when an authorized human admin proposes a **disable** and a **second** authorized human admin approves it (FR75d two-person rule), then the service client transitions to a durable **Disabled** governance control state and **future commands and queries from that service client fail closed** at the command/query admission pipeline, while **unrelated service clients and other actors continue normally** (isolation, NFR30/NFR58). The disable is a security-sensitive FR74 governance control — **not** the Epic 5 Keycloak-sourced grant lifecycle (`ServiceClientGrant.IsRevoked`/`ExpiresAt`) — so it MUST go through the same submit→second-person-approve flow established for security-sensitive tenant policy mutations and the Story 7.12 mailbox-source disable (`SubmitMailboxSourceDisable`→`ApproveMailboxSourceDisable`); a single-actor disable never takes effect. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.15`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75d`; `_bmad-output/implementation-artifacts/7-12-disable-mailbox-source.md`; `src/Hexalith.ChatBot.Server/Operations/GovernedOperationAggregate.cs`]

2. Given the disable proposal and approval, when authorization runs, then the operation is permitted only for a **human tenant administrator** (service-client governance is a TenantAdmin responsibility per the RBAC Matrix — there is no finer service-client admin scope), and is **denied for service clients and AI actors** even when they carry tenant-admin-looking claims, exactly as `AdminAuthorityEvaluator.HasHumanTenantAdmin(principal)` / `HasHumanAdminScope` already enforce human-only admin authority. The approving admin MUST be a **different person** from the proposer: both `RequesterRef != ApproverRef` (Ordinal safe-token compare) and `RequesterActorId != approver envelope UserId` are enforced — at the gateway validation stage, the accepted-command dispatcher, **and** re-checked in the aggregate, mirroring `IsValidMailboxSourceDisableApproval`, `AcceptedCommandDispatcher`'s distinct-approver guard, and `GovernedOperationAggregate.Handle(ApproveMailboxSourceDisable)`. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75a`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75d`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md` (RBAC Matrix — TenantAdmin owns service-client grants); `src/Hexalith.ChatBot.Server/Governance/Admin/AdminAuthorityEvaluator.cs`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ParticipantAuthorizationStage.cs`]

3. Given the disable is applied (approval committed), when it is recorded, then the operation records — with **no skip-audit path** (FR74, FR75g, NFR15a) — the **actor** (admin identity / actor type), **scope used** (`admin-scope:tenant-admin`), **subject** (the safe service-client ref / `ServiceClientId`), **reason** (documented justification reason code), **old state** (`Active`), **new state** (`Disabled`), **policy snapshot id**, and **timestamp**, via a metadata-only `AuditEnvelope` whose `StateTransition` is `"Active->Disabled"`. The audit is written through the existing fail-closed pre-commit seam (`IAuditWriter.RecordPreCommitAsync` via `CommandGateway`): when the pre-commit audit is unavailable, **no durable disable state is written and no admission-blocking side effect occurs** (fail closed), reusing the disable/`CommandGateway` audit-unavailable behavior. The `tenant-admin` role does **not** bypass NFR15a/NFR50a. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.15`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75g`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR15a`; `src/Hexalith.ChatBot.Server/Audit/AuditEnvelopeFactory.cs`; `src/Hexalith.ChatBot.Server/Gateway/CommandGateway.cs`]

4. Given a service client is Disabled, when that service client submits **any command** (and, where service-client query admission is wired, any query), then the authorization stage **fails closed before admission** — `ServiceClientGrantValidator` (which already runs only for `service`/`ai` actor types) returns `ChatBotAuthorizationResult.Denied("service_client_disabled")` **before** the grant scope/allowlist checks and before any durable work — so no command from the disabled client is dispatched and no restricted data is returned. A command from any **other (still-Active)** service client for the same tenant is unaffected (isolation). The new `service_client_disabled` reason is **distinct from** the Epic 5 `service_client_grant_revoked` (Keycloak grant revocation) — it reflects the FR74 two-person governance control, not the externally-sourced grant flag. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.15`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ServiceClientGrantValidator.cs`; `src/Hexalith.ChatBot.Server/Gateway/ChatBotAuthorizationReasonCodes.cs`; `src/Hexalith.ChatBot.Contracts/Identities/ServiceClientGrant.cs`]

5. Given a service client is disabled, when its prior activity is inspected, then **all previously recorded commands, audit envelopes, and workflow items that originated from that client remain visible, intact, and fully reconstructable** — disable affects **only future admission**, never already-committed records, associations, files, approvals, conversation content, or their audit trails (NFR17 visible/recoverable states; FR75c admins cannot mutate project-level records). Disable is reversible by a future re-enable flow; this story does not delete or rewrite any prior record. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR17`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75c`; `_bmad-output/implementation-artifacts/7-1-tenant-admin-permission-model-and-bounded-scopes.md`]

6. Given an actor encounters a disabled service client (admin viewing status, or an admission blocked), when guidance is surfaced, then **safe recovery guidance** is shown from the **finite message catalog** — a safe headline (≤ 80 chars), a one-line reason from a finite set, a next-action pointing to the responsible role (re-enable is a tenant-admin/two-person action), and a `disabled-action` reason — using `ChatBotMessageCatalog` / `ChatBotMessageCodes` / `ChatBotDisabledActionReasons`, never raw error text. No surface names an unauthorized project/file/party/mailbox-content/audit detail (NFR2); EN/FR via existing localization; stable machine tokens (reason codes, state tokens, correlation ids) stay untranslated. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.15`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR76`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR2`; `src/Hexalith.ChatBot.Contracts/Messages/ChatBotMessageCatalog.cs:427`]

## Dev Notes

### Scope Boundaries

- Story 7.15 is the **fourth** cell of the FR74 enforcement series (7.12–7.26: five subject classes — mailbox / service-client / AI-actor / command-capability / outbound — × three actions — disable / quarantine / rate-limit). It implements exactly **one** cell: **service client × disable**. Disable (this story) and quarantine (7.16) are **security-sensitive** admin operations gated by the **FR75d two-person rule**; rate-limit (7.17) is a standard policy mutation. **Do not** implement quarantine, rate-limit, any other subject class, or a future re-enable/release flow here. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`]
- **The three meaningful divergences from the 7.12 mailbox-source-disable template — read these first:**
  1. **Subject = service client, enforced at the *admission/authorization stage*, not the mailbox worker.** The Story 7.12 disable blocks intake in `GraphMailboxIntakeWorker` (a worker pre-fetch branch). The service-client disable blocks **commands and queries** at the command/query admission pipeline — specifically `ServiceClientGrantValidator` inside the Authorization stage, which already runs only for `service`/`ai` actor types. There is **no** mailbox-worker change in this story.
  2. **Distinct from the Epic 5 grant lifecycle.** Service clients already have `ServiceClientGrant.IsRevoked` + `ExpiresAt`, but these are **Keycloak-claims-sourced** (`ClaimsServiceClientGrantResolver`) — externally owned grant signals returning `service_client_grant_revoked`/`service_client_grant_expired`. The FR74 disable is a **separate, ChatBot-domain, two-person governance control state** with a **new** `service_client_disabled` reason code. Do **not** route disable through `IsRevoked` (it cannot carry the two-person justification and is owned outside the ChatBot domain) — this is the exact analog of the Story 7.12 "do not overload `MonitoredMailboxPattern.IsEnabled`" decision.
  3. **Authorization scope = tenant-admin, not a subject-specific admin scope.** Mailbox cells used `AdminScope.Mailbox` (mailbox-admin governs mailbox config). There is **no** service-client `AdminScope` in the enum (`{SeeOnly, Operate, Policy, Mailbox, Compliance, AuditObligation}`), and the RBAC Matrix assigns service-client grant governance to **TenantAdmin**. Gate on `AdminAuthorityEvaluator.HasHumanTenantAdmin`. Do **not** add a new `AdminScope` value or reuse `Operate` (FR75c `Operate` is queue-item ops — retry/requeue/quarantine/dismiss — not identity/grant governance).
- **Two-person rule (FR75d).** The disable requires submit→second-person-approve; a single-actor disable only ever produces a pending approval. Distinct approver is enforced **three times** (gateway validator, accepted-command dispatcher, aggregate re-check), exactly as 7.12 does.
- The disable affects **future admission only**. It must never delete, rewrite, or hide already-committed commands, audit envelopes, associations, files, approvals, or conversation content (NFR17, FR75c). It is reversible by a future re-enable flow (out of scope here).
- Tenant identity is always from the **authenticated gateway binding**, never the command body. The subject (service client) and all audit refs are **metadata-only, safe tokens** (NFR2); credentials, OAuth grant fingerprints, and delegated-user PII never appear (NFR4/NFR5).
