# Story 7.9: Notification throttling and digest rollup

Status: done

<!-- Validation: create-story checklist applied 2026-06-02. -->

## Story

As a reviewer,
I want per-user notification ceilings with digest rollup,
so that I am alerted to what needs my attention without being overwhelmed by notification volume.

## Acceptance Criteria

1. Given per-recipient notifications are produced for a `(tenant × recipient)` pair, when the count delivered as **immediate push** in the trailing rolling windows would exceed the ceiling, then delivery is capped at **≤ 8 per rolling 60 minutes AND ≤ 30 per rolling 24 hours** (NFR46), measured server-side in UTC via `ISystemClock` against the recipient's own delivery history (never client/item-supplied time, never a per-process wall clock). Both windows are enforced simultaneously: a recipient at the hourly ceiling is throttled even if under the daily ceiling, and vice-versa. The throttle decision is deterministic and pure given the injected clock and the recipient's prior delivery timestamps. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR46`; `_bmad-output/planning-artifacts/epics.md#Story 7.9`; `src/Hexalith.ChatBot.Server/Audit/ISystemClock.cs`; `src/Hexalith.ChatBot.Server/Notifications/INotificationSink.cs`]
2. Given the per-recipient ceiling is reached, when further notifications for that recipient are produced within the window, then each overflow notification is **not dropped** — it is **rolled up into a pending digest** for that `(tenant × recipient)`, preserving the item identity reference, state class, scope, queue reference, reason code, and a safe next-action affordance for each rolled-up entry, so no attention-needed signal is silently lost. A throttled notification produces a digest entry, never a discarded event. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR46`; `_bmad-output/planning-artifacts/epics.md#Story 7.9`; `src/Hexalith.ChatBot.Server/Notifications/NotificationDelivery.cs`; `src/Hexalith.ChatBot.Server/Notifications/NotificationStateEvent.cs`]
3. Given a digest is produced and delivered, when it reaches a recipient, then each rolled-up entry preserves **item identity (safe item ref), scope, state class, and next action** but exposes **no restricted detail** — for any entry the recipient lacks per-resource authority over, the entry is the metadata-only/redacted form (`NotificationContentVisibility.MetadataRedacted`), indistinguishable from safe-not-found, with no project name, evidence, mailbox content, recipient PII beyond safe refs, audit reason detail, provider payload, prompt, command body, claim, header, token, or secret (NFR46, NFR2). The digest reuses the existing per-resource authority + visibility path from the routing resolver; it never becomes a covert channel that reveals what the immediate push would have redacted. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR46`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR2`; `src/Hexalith.ChatBot.Server/Notifications/NotificationRoutingResolver.cs`; `src/Hexalith.ChatBot.Server/Notifications/NotificationContentVisibility.cs`]
4. Given throttling is enforced, when the rolling-window counters and digest membership are computed, then they are keyed strictly by `(tenant-ref-from-authenticated-binding × recipient-ref)` — the tenant comes from the authenticated gateway binding, never from item refs, channel config, recipient-supplied data, or correlation ids — and one tenant's or recipient's notification volume can never throttle, suppress, or leak into another's digest. Counters and digest state are metadata-only (timestamps + safe refs), carry no restricted content, and a redacted-from-`B` item is never visible in `A`'s counters or digest. [Source: `_bmad-output/planning-artifacts/architecture.md#API & Communication Patterns`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR2`; `src/Hexalith.ChatBot.Server/Notifications/NotificationRoutingResolver.cs`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ParticipantAuthorizationStage.cs`]
5. Given the per-user ceiling is configurable, when a tenant administrator tunes it, then the ceiling is adjustable only through a **closed, schema-bounded** Tenant Policy knob whose values are bounded **at or below the NFR46 governance maximums (hourly ≤ 8, daily ≤ 30)** — a tenant may **lower** the ceiling but can never raise it above the NFR46 maximum, introduce a new window dimension, or supply a free-form expression. Out-of-range (including above-maximum), wrong-type, NaN/Infinity, or undeclared values are rejected with the existing safe reason codes and the evaluator falls back to declared safe defaults (8/hr, 30/day = the NFR46 maximums). If implemented as fixed governance constants instead of a knob, the constants equal 8/hr and 30/day and this is stated in completion notes. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR46`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75d`; `src/Hexalith.ChatBot.Contracts/Commands/TenantPolicyContracts.cs`; `_bmad-output/implementation-artifacts/7-8-approval-queue-prioritization-and-grouping.md#Completion Notes List`]
6. Given a notification delivery decision is made (immediate push, throttle-to-digest, or digest send), when the pre-commit audit for that delivery is unavailable, then the delivery **fails closed** — no durable/observable delivery side effect occurs and no counter is advanced for a delivery that was not audited (so a fail-closed event cannot silently exhaust a recipient's ceiling). When audit succeeds, the envelope carries **metadata-only refs** (tenant ref, recipient ref, state class, channel, scope, throttle decision token e.g. `delivered`/`throttled`/`digest`, window-counter snapshot e.g. `hour:n` `day:n`, rolled-up-count, reason code, correlation id, UTC timestamp) — never project content, evidence, file metadata, audit reason detail, provider payloads, prompts, command bodies, recipient PII beyond safe refs, claims, headers, tokens, or secrets. This reuses the established per-delivery fail-closed audit pattern from escalation (Story 7.7). [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR15a`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75g`; `src/Hexalith.ChatBot.Server/Audit/AuditEnvelopeFactory.cs`; `src/Hexalith.ChatBot.Server/Notifications/EscalationEvaluationCoordinator.cs`]

Any configuration surface reuses the governed config-editor pattern (no raw JSON, no hover-only critical actions, no new design system, no infinite scroll); the digest, if rendered, is a read-only summary-safe list where unauthorized entries are indistinguishable from not-found. ## Dev Notes

### Scope Boundaries

- Story 7.9 implements exactly **one** NFR46 mechanism: the **per-user notification ceiling (≤ 8/hr, ≤ 30/day) with digest rollup** of the overflow. It is the third NFR46 anti-fatigue mechanism, layered on top of the notification delivery seam shipped by Story 7.6 and the clock-injected evaluator/coordinator pattern shipped by Story 7.7.
- It builds directly on **Story 7.6** (the metadata-only `INotificationSink`/`NotificationDelivery`/`NotificationStateEvent`/`NotificationContentVisibility` seam and `NotificationRoutingResolver` audience + redaction path) and **Story 7.7** (the pure, clock-injected `EscalationPolicyEvaluator` and the `EscalationEvaluationCoordinator` evaluate → per-event fail-closed audit → deliver pattern). **Reuse those; do not fork the delivery seam, the authority/redaction path, or the audit pattern.**
- It does NOT implement the other NFR46 mechanisms, which are separate stories: prioritization + grouping = Story 7.8 (done); **reviewer-backlog alerting (> 25 open items)** = Story 7.10; **the rubber-stamp-rate observable (> 15% rolling-7-day, < 5s approvals) and median/p95 time-in-queue dashboards** = Story 7.11 / Epic 8 (M2). Do not implement backlog alerts or the rubber-stamp observable here — but keep throttle/digest shaped so 7.10–7.11 can layer on them.
- Throttling/digest is a **server-side delivery-pipeline concern**, not a user-submitted command and not a new approval authority. The only mutation that may be exposed is tuning the ceiling, and only via the existing `SubmitTenantPolicyChange` path if a knob is chosen.
- Throttling/digest must never become a covert channel for project content, evidence, file metadata, mailbox content, audit reasons, recipient PII, or provider/AI payloads. A digest must never reveal what the immediate push would have redacted (NFR2).
- The **runtime delivery caller / periodic binding is deferred** (consistent with Story 7.6's deferred FR72 delivery caller and Story 7.7's deferred escalation runtime). This story provides the deterministic throttle engine, the digest producer, the counter store seam, and the coordinator wiring — not an always-on `BackgroundService`.

The throttle/digest flow reuses this exact discipline; additionally, **a fail-closed (unaudited) delivery must not advance the recipient's counter** so it cannot silently exhaust the ceiling.

### Architecture Guardrails

- New throttle/digest engine, counter store, and coordinator land in `src/Hexalith.ChatBot.Server/Notifications/` (beside the routing/escalation engines). Any ceiling-knob contract lands in `src/Hexalith.ChatBot.Contracts` (Commands/Enums); audit refs in `src/Hexalith.ChatBot.Server/Audit`; UI (only if in scope) in `src/Hexalith.ChatBot.UI`. No new top-level projects expected.
- Every delivery decision (immediate push, throttle-to-digest, digest send) is preceded by a pre-commit audit; on audit-unavailable it fails closed with no durable/observable side effect and no counter advance. No direct-to-sink delivery that bypasses audit.
- **Tenant id comes from the authenticated gateway binding** (carried on `NotificationStateEvent.TenantRef`/`NotificationDelivery.TenantRef`); recipient/item/queue refs, channel config, weights/ceilings, route/query params, and correlation ids are comparison/keying inputs only. Counters/digest are keyed `(tenant × recipient)` after binding.
- **Time/windows are server-side UTC via `ISystemClock`** (`now − deliveryTimestamp`, count within trailing window). The evaluator must be pure and clock-injected so exactly-at-ceiling and window-edge boundaries are unit-testable; tenant-local formatting only at presentation boundaries.
- The ceiling model is **closed** (two fixed window dimensions, bounded ≤ NFR46 cap), never a tenant-supplied expression or new dimension.
- Counters/digest state are metadata-only (timestamps + safe refs). No restricted content enters the throttle/digest path; a redacted-from-`B` item is never visible in `A`'s state.
- NFR46's ceiling is a **hard governance cap**: hourly ≤ 8, daily ≤ 30. A tenant knob can only lower it.
