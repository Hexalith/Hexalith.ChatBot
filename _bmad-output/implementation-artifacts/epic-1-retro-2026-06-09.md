## What Went Well

- The walking skeleton forced the safety floor into executable code before feature work. Story 1.9 made gateway, audit, idempotency, projection, and UI outcome visible together.
- Review pressure improved the story records and implementation. Recurring review fixes corrected stale file lists, overbroad claims, missing negative assertions, and sandbox-specific validation notes.
- The command boundary stayed narrow. Adapters construct typed commands through `IChatBotClient.SubmitAsync(...)`; governance interfaces remain server-internal.
- The DAPR topology was made explicit in implementation and then folded back into planning docs: EventStore actor/status store `statestore`, ChatBot derived state store `chatbot-statestore`, Redis pub/sub `chatbot-pubsub`, and local/production access-control split.
- Accessibility, localization, live-region, responsive, redaction, and cognitive-load constraints were encoded as reusable UI contracts rather than delayed until feature screens.

## Challenges

- Runtime topology details were discovered through implementation, not fully captured in the first planning pass. The specific component names, IPv4 Redis endpoint, proxyless sidecar channel, and local mTLS-off ACL behavior all had to be learned from code and validation.
- Test execution in this sandbox needed a documented alternative path. `dotnet test` can fail when VSTest opens a denied socket, so story evidence standardized around compiled xUnit v3 binaries.
- Story files repeatedly needed documentation hygiene after implementation: status, file list, review findings, and validation evidence were easy to drift.
- The lifecycle state `Skipped` became an M0 contract reality earlier than some planning language originally implied. That has since been reconciled in PRD and epics.

## Key Lessons

1. End-to-end safety claims need durable-state inspection, audit checks, and negative assertions, not only HTTP acceptance.
2. Runtime topology learnings should be promoted into architecture and README immediately after implementation.
3. Local development security exceptions must be named as local-only and paired with production conformance posture.
4. Story records are part of the engineering system; stale File Lists and validation notes create real downstream risk.
5. Cross-surface parity is strongest when adapter code has no authority to replicate gateway stages.
