# Story 7.27: Command allowlist v1 and full lifecycle completion

Status: done

<!-- Validation: create-story checklist applied 2026-06-03. -->

## Story

As a **security engineer** (the epic's "security engineer" persona — note there is **no** `AdminScope.Security` / `AdminRole.SecurityEngineer`; runtime authority for any policy mutation maps to the **policy** scope, and "security-engineer sign-off" is a **checked-in governance artifact**, not a runtime role),
I want the **versioned AI-action command allowlist promoted from v0/M0 to v1** — the full AI-invocable governed-command catalog minus tenant `disallowed-for-AI` commands, each carrying per-command metadata (effect surface, authority class, default risk, idempotency contract), under explicit version-increment change control with security-engineer sign-off recorded in `.decision-log.md` — **and** the canonical workflow **lifecycle state machine completed** (the `Skipped` terminal triggers for duplicate-suppression / out-of-scope-mailbox wired into the transition matrix, the full state-transition matrix audited closed, and isolation enforcement proven uniform across the CLI / MCP / service-client actor types),
so that **M1 governance breadth lands without weakening the M0 safety floor** — the AI can still invoke only allowlisted commands at the pinned version (fail-closed), every workflow item moves only through legal states, and no surface (CLI/MCP/service-client) can bypass isolation that a human or AI actor is subject to.

This story is **integrative, not a new FR74 isolation cell**: it does not add a `Submit…/Approve…` governance command. Part A (allowlist v1) is internal allowlist configuration + per-command metadata + a decision-log governance entry; Part B (lifecycle completion) is transition-matrix wiring + cross-actor-type isolation verification and gap-fill. Most of the work is **extending existing seams and proving invariants**, not building new ones.

### Cross-actor isolation — what "extend to CLI/MCP/service-client" means

The nine actor types include CLI client and MCP client. In code, CLI/MCP are **`ServiceClientClass`** values (`cli-automation`, `mcp-tool`) that flow through the **service-client** subject plane via `ServiceClientGrantValidator` (per-actor disable/quarantine/rate-limit, branched on the `chatbot:actor-type` claim), while command-capability / mailbox / outbound isolation is actor-agnostic at `ParticipantAuthorizationStage`.
