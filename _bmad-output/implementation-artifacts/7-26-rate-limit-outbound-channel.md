# Story 7.26: Rate-limit outbound channel

Status: done

<!-- Validation: create-story checklist applied 2026-06-03. -->

## Story

As an authorized **policy administrator** (the epic's "policy administrator" persona — there is no security-engineer scope; it maps to the policy scope) acting through a **single-actor, schema-bounded policy mutation**,
I want to rate-limit an **outbound channel** (the governed external-send path, identified by its safe `AdapterRef`) for a tenant,
so that external communication volume stays within tenant policy — **the outbound send seam applies the bounded per-window send budget to that channel for the tenant, and once the trailing-window admitted-send count reaches the budget every further approved send through that channel fails closed before the external adapter call with a typed, transient, redacted rate-limit response** — while unrelated outbound channels and unrelated tenants keep their own independent budgets and are protected from degradation where isolation is possible, and every prior draft / approval / send / audit record stays intact and inspectable.

## Acceptance Criteria

1. Given an outbound channel exceeding tenant thresholds, when an authorized **human policy administrator** configures a rate limit, then a durable per-`(tenant × outbound-channel)` rate-limit budget is recorded and **the outbound send seam applies the bounded limit** to that channel's future approved sends. This is a **standard, single-actor policy mutation** — explicitly **NOT** the Story 7.24/7.25 FR75d two-person control: FR74's decomposition states "disable and quarantine are security-sensitive admin operations (per FR75d two-person rule); **rate-limit is a standard policy mutation**." So the command follows the **single-actor** shape of `SubmitCommandCapabilityRateLimit` (Story 7.23) / `SubmitAiActorRateLimit` (Story 7.20) / `SubmitServiceClientRateLimit` (Story 7.17) / `SubmitMailboxSourceRateLimit` (Story 7.14) — one authority check, no approver — **not** the submit→second-person-approve flow of `SubmitOutboundChannelDisable`/`SubmitOutboundChannelQuarantine`. There is **no** `Approve…` counterpart, **no** distinct-approver guard, and **no** `OutboundChannelControlState`/lifecycle transition (rate-limit is a *parameter*, not a control state). [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.26`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`; `_bmad-output/implementation-artifacts/7-23-rate-limit-command-capability.md`; `_bmad-output/implementation-artifacts/7-25-quarantine-outbound-channel.md`]

2. Given the rate-limit value, when it is validated, then it is **bounded by the Tenant Policy Schema** (FR75): the configured per-window send budget is accepted only within a declared, closed, non-negative min/max range, and an out-of-range / wrong-type / undeclared value is **rejected with a safe reason code** (and, at the enforcement seam, falls back to safe defaults — never silently raising the cap). Mirror the closed `MailboxRateLimitBounds` / `CommandCapabilityRateLimitBounds` discipline (`Minimum`/`Maximum`/`SafeDefaults`/`IsWithinBounds`) — a tenant cannot introduce a new window dimension or a custom formula. The bound is a Standard (non-security-sensitive) knob, so no two-person rule applies. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75`; `src/Hexalith.ChatBot.Contracts/Commands/MailboxRateLimitBounds.cs`; `src/Hexalith.ChatBot.Contracts/Commands/CommandCapabilityRateLimitBounds.cs`]

3. Given authorization runs, when the configure command is evaluated, then it is permitted only for a **human policy administrator** — gate on **`AdminAuthorityEvaluator.HasHumanAdminScope(actor.Principal, AdminScope.Policy)`** (outbound-channel governance is a security-sensitive policy concern — the same scope that gates `SubmitTenantPolicyChange`, the Story 7.24 outbound-channel disable, and the Story 7.25 quarantine; the epic's "policy administrator" persona maps to the **policy** scope — there is **no** `AdminScope.Security`/`AdminRole.SecurityEngineer`). A `tenant-admin` still qualifies because `AdminScopes.ScopesForRole(TenantAdmin)` returns the full scope set (FR75a union) — so this is **not** a relaxation. The operation is **denied for service clients and AI actors** even when they carry admin-looking claims (the human-actor gate inside `HasHumanAdminScope`/`IsHumanActor`), and denied for non-policy human scopes (`mailbox-admin`/`compliance-admin`/`operations-admin`-only). There is **no** second-person/distinct-approver requirement; a single authorized human policy-admin applies it. Denial of the governance command itself uses `ChatBotAuthorizationReasonCodes.AuthorizationDenied`. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.26`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75a`; `src/Hexalith.ChatBot.Server/Governance/Admin/AdminAuthorityEvaluator.cs`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ParticipantAuthorizationStage.cs`]

4. Given the rate limit is applied (committed), when it is recorded, then the operation records — with **no skip-audit path** (FR74, FR75g, NFR15a) — the **actor** (requester identity / actor type), **scope used** (`admin-scope:policy`), **subject** (the safe outbound-channel ref — e.g. `adapter:mailbox-outbound`), **reason** (documented justification reason code), **old state** (the prior budget / `unlimited`), **new state** (the new bounded budget), **window token**, **policy snapshot id**, and **timestamp**, via the metadata-only `AuditEnvelope`. There is **no** `StateTransition` ref (rate-limit is not a lifecycle transition — old/new "state" are budgets). The audit is written through the existing fail-closed pre-commit seam (`IAuditWriter.RecordPreCommitAsync` via `CommandGateway`): when the pre-commit audit is unavailable, **no durable rate-limit state is written and no enforcement side effect occurs** (fail closed), reusing the disable/quarantine `CommandGateway` audit-unavailable behavior. No admin role bypasses NFR15a/NFR50a. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.26`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75g`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR15a`; `src/Hexalith.ChatBot.Server/Audit/AuditEnvelopeFactory.cs`; `src/Hexalith.ChatBot.Server/Gateway/CommandGateway.cs`]

5. Given an outbound channel has a rate-limit budget configured for a tenant, when an `ExecuteApprovedOutboundDraft` send targeting **that channel** (keyed by the safe `AdapterRef`) is dispatched for that tenant and the recent **admitted-send** count in the trailing rolling window has reached the effective budget, then the **send fails closed at the outbound send seam before any external dispatch** — in `AcceptedCommandDispatcher`'s `ExecuteApprovedOutboundDraft` branch the rate-limit check runs **before `IOutboundMailboxSender.SendAsync`** (`AcceptedCommandDispatcher.cs:768`), **after** the existing Disabled/Quarantined control-state switch (`:746–762`), and short-circuits the adapter — producing a fail-closed send-rejected outcome with the finite reason `outbound_channel_rate_limited`, so **no message is sent to the outbound adapter and no external communication leaves the boundary while over budget**. This is the **key divergence from the actor/command-capability rate-limit cells (7.14/7.17/7.20/7.23)**: the subject is an **outbound channel**, and the only place its `AdapterRef` and the authenticated `TenantBinding` meet immediately before the external adapter call is the **send seam in the dispatcher** — **not** `ServiceClientGrantValidator` (per-actor, misses human sends) and **not** the `ParticipantAuthorizationStage` admission gate (where 7.23 enforced its command-type subject). The dispatcher **already holds an injected `ISystemClock`** (`AcceptedCommandDispatcher.cs:31`) and already reads the control state once at this seam (`:746`), so the rate-limit reuses the established clock-injected window math (`NotificationThrottleEvaluator.CountInTrailingWindow`: server-measured UTC age, never client/item-supplied time), keyed per-`(tenant × outbound-channel)`. The check is placed **as the last gate of the send seam** — only after the Disabled/Quarantined control-state switch returns "Active" (`controlledAdapterStatus is null`) — so a disabled/quarantined channel keeps its precise control-state reason (rate-limit never masks a control-state denial). The new send-rejected reason reuses the existing `AdapterStatus != "sent"` → `RejectOutboundSend(...)` path in `GovernedOperationAggregate.Handle(ExecuteApprovedOutboundDraft)` (`:1351`): the dispatcher sets a **distinct** non-`"sent"` `AdapterStatus` token (`"rate-limited"`) which the aggregate maps to `outbound_channel_rate_limited` **beside** the existing `"blocked"` → `outbound_channel_disabled` (`:1336`) and `"quarantined"` → `outbound_channel_quarantined` (`:1346`) mappings. A send targeting any **other (un-throttled)** channel for the same tenant, or the same channel for a **different** tenant, is unaffected (isolation). When the channel is **under** budget the send proceeds normally to `SendAsync`. The new `outbound_channel_rate_limited` reason is **distinct from** `outbound_channel_disabled`, `outbound_channel_quarantined`, `outbound_adapter_unavailable` (the adapter-not-configured/unreachable case), `adapter_not_approved_mode`, `command_capability_rate_limited`, and every actor-rate-limit reason (`ai_actor_rate_limited`, `service_client_rate_limited`, `mailbox_source_rate_limited`). [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.26`; `src/Hexalith.ChatBot.Server/Gateway/Stages/AcceptedCommandDispatcher.cs:712`; `src/Hexalith.ChatBot.Server/Adapters/Mailbox/IOutboundMailboxSender.cs`; `src/Hexalith.ChatBot.Server/Operations/GovernedOperationAggregate.cs:1336`; `src/Hexalith.ChatBot.Server/Notifications/NotificationThrottleEvaluator.cs:63`]

6. Given rate-limiting is in effect, when capacity impact is observed, then admission **exposes capacity-impact metrics that surface the throttling/backlog effect** — at minimum the effective budget, the observed trailing-window admitted-send count, and whether this send was throttled for the channel — carried as safe, finite integer tokens at the audit/observable seam (mirror the `AiActorRateLimitObservation` / `CommandCapabilityRateLimitObservation` shape: integer/rational arithmetic, never floats). Rate-limiting **protects unrelated tenants/channels from degradation where isolation is possible** (NFR30, NFR18): each channel's budget and trailing-window counter are **independent**, so throttling a noisy outbound channel never throttles a sibling channel or another tenant. Full operational-dashboard wiring is Epic 8 and is out of scope here — this story exposes the metric at the audit/observable seam only. **"Returns typed status to the requester and operator queue"** (the epic AC phrase) is satisfied by the fail-closed send-rejected outcome's reason code + the catalog guidance + the audit metric refs, consistent with the 7.12–7.25 deferral of an S5 surface. 7. Given a send is rejected for a rate-limited outbound channel, when guidance is surfaced, then **safe recovery guidance** is shown from the **finite message catalog** — a safe headline (≤ 80 chars), a one-line reason conveying "this channel's send capacity is temporarily limited to keep external volume within tenant policy; retry shortly", a next-action of **`retry-later`** (transient, **not** `request-access` — the channel is not disabled or quarantined), and a **transient** `dependency-degraded` reason (**not** `disabled-action`) — using `ChatBotMessageCatalog` / `ChatBotMessageCodes` / `ChatBotMessageNextActions` / `ChatBotDisabledActionReasons`, never raw error text. The guidance never names an unauthorized project/file/party/mailbox-content/recipient/audit detail (NFR2); EN/FR via existing localization; stable machine tokens (reason codes, window tokens, correlation ids, channel refs) stay untranslated. ## Dev Notes

### Scope Boundaries

- Story 7.26 is the **fifteenth and final** cell of the FR74 enforcement series (7.12–7.26: five subject classes — mailbox / service-client / AI-actor / command-capability / **outbound** — × three actions — disable / quarantine / rate-limit) and the **third (final) outbound-channel cell**. It implements exactly **one** cell: **outbound channel × rate-limit**. Disable (7.24) and quarantine (7.25) were **security-sensitive** admin operations gated by the **FR75d two-person rule**; **rate-limit (this story) is a standard, single-actor policy mutation** bounded by the Tenant Policy Schema. **Do not** implement any other subject class, the disable/quarantine actions, a future rate-limit-release/reset flow, or the Story 7.27 command-allowlist-v1 / full-lifecycle work here. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`; `_bmad-output/planning-artifacts/epics.md#Story 7.27`]
- **This story is a cross-product: take the 7.23 single-actor rate-limit pattern and apply it to the 7.24/7.25 outbound-channel subject + outbound send-seam enforcement.** Read 7.23 (rate-limit command capability, commit `fb2b570`) for the *single-actor command / bounds / window / dedicated schema-version / direct-activation aggregate / audit-without-StateTransition / transient catalog / no-approver / no-lifecycle-transition / dedicated read-side providers* shape, and 7.24/7.25 (outbound-channel disable/quarantine, commits `2c3f597`/`298b34b`) for the *outbound-channel subject (the safe `AdapterRef`) + `HasHumanAdminScope(AdminScope.Policy)` authority + **outbound send-seam enforcement in `AcceptedCommandDispatcher.ExecuteApprovedOutboundDraft`** + no-self-lockout + read-side deferral*. The result is the outbound-channel cell that is both single-actor **and** enforced at the send seam.
- **The two meaningful divergences — read these first:**
  1. **Enforcement seam is the outbound SEND seam (`AcceptedCommandDispatcher.ExecuteApprovedOutboundDraft`), not an admission stage (the 7.24/7.25 wrinkle, NOT the 7.23 one).** For the command-capability rate-limit (7.23) the subject was a command *type* admitted for any actor, so enforcement lived in the actor-agnostic `ParticipantAuthorizationStage` (which had no clock and needed one injected). For the **outbound-channel** subject the budget keys on a channel whose `AdapterRef` only meets the authenticated `TenantBinding` at the **send seam**, immediately before `IOutboundMailboxSender.SendAsync` — exactly where 7.24/7.25 enforce the Disabled/Quarantined control state. **The dispatcher already holds an injected `ISystemClock`** (`AcceptedCommandDispatcher.cs:31`) and already reads the control state once at this seam, so this story injects only the two new dedicated providers (no clock injection). **Rejected:** a `ServiceClientGrantValidator` branch (per-actor, misses human sends — same reason 7.24/7.25 gave) or a `ParticipantAuthorizationStage` admission gate (the channel ref is on the `ExecuteApprovedOutboundDraft` body; keep the block adjacent to the adapter call so "no external send" is provably local).
  2. **Rate-limit is a parameter, not a control state — the one meaningful semantic difference from 7.24/7.25.** "Outbound communication enforces the limit" = future approved sends through that channel **fail closed at the send seam with a transient, retryable response** (`outbound_channel_rate_limited` / `retry-later` / `dependency-degraded`) once the trailing-window admitted-send count reaches the budget — **not** a hard, terminal control state. So **no** `OutboundChannelControlState` value, **no** `LifecycleStates`/`LifecycleTransitionValidator`/`CommandSubmissionLifecycleTransitionGuard` change, **no** `Approve…` command, **no** pending-approval event/dictionary, **no** `AcceptedCommandDispatcher` distinct-approver branch. "Old/new state" in the audit = old budget / new budget; there is **no** `StateTransition` ref.
- **Mechanism note — the reason is a refusal string, not an authorization reason code.** Because enforcement is at the send seam, the new `outbound_channel_rate_limited` reason is a refusal-reason **string literal** set in `GovernedOperationAggregate`'s `RejectOutboundSend` (beside `outbound_channel_disabled`/`outbound_channel_quarantined`), **NOT** a `ChatBotAuthorizationReasonCodes` constant (that is how the actor/command-capability rate-limit cells worked, because they denied at an admission stage via `ChatBotAuthorizationResult.Denied(…)`). Do **not** add it to `ChatBotAuthorizationReasonCodes`. (It **is** added to `ChatBotMessageCodes` for the catalog entry.)
- **Authorization scope = policy-admin** (same as 7.20–7.25). There is **no** `AdminScope.Security` / `AdminRole.SecurityEngineer`; the epic's "policy administrator" persona maps to the security-sensitive **policy** scope. Gate on **`HasHumanAdminScope(actor.Principal, AdminScope.Policy)`**. A `tenant-admin` still passes via the FR75a scope union — **not** a relaxation. Single actor — do **not** add a second-person requirement the epic does not impose. **Rejected:** a new `AdminScope.Security` (scope-creep) and `HasHumanTenantAdmin` (too coarse).
- **No self-lockout guard (the divergence from 7.23, carried from 7.24/7.25).** Because the subject is a **channel** (not a governance command type), rate-limiting it cannot lock out governance — so there is **no** `Fr74GovernanceCommandTypes` membership check on the subject and the new command name is **not** added to that set. (7.23 *did* add its rate-limit command to that set because its subject is a command type; 7.26 does not, mirroring the 7.24/7.25 outbound divergence.)
- **Bounded by the Tenant Policy Schema (FR75).** The budget value is accepted only within a declared closed range. Reuse the `MailboxRateLimitBounds`/`CommandCapabilityRateLimitBounds` discipline: `Minimum`/`Maximum`/`SafeDefaults`/`IsWithinBounds`, out-of-bounds → safe default (= maximum), never raise the cap. A tenant cannot add a new window dimension or a custom formula.
- **Isolation (NFR30/NFR18).** Each outbound channel has an independent budget + trailing-window counter keyed per-`(tenant × outbound-channel)`. Throttling a noisy channel must never throttle a sibling channel or another tenant. Tenant identity is always from the **authenticated gateway binding**, never the command body. The subject (channel ref) and all audit refs are **metadata-only, safe tokens** (NFR2); recipient/sender addresses, message content, credentials, OAuth grant fingerprints, model prompts/completions, and delegated-user PII never appear (NFR4/NFR5).
- Rate-limit affects **future sends only**. It must never delete, rewrite, or hide already-committed drafts, approval requests/decisions, send outcomes, conversation content, or their audit trails (NFR17, FR75c). It does **not** block `CreateOutboundDraft`, `RequestOutboundSendApproval`, or `DecideOutboundApproval` (drafts/approvals stay inspectable) — it throttles **only the send/execute step** through the channel. It is reversible by a future release/reset flow (out of scope here).

### What "outbound channel" means here, and where it is rate-limited

- An **outbound channel** is the governed external-send path through which an approved outbound draft leaves the project boundary. In M0/M1 the single outbound channel is the **M365 mailbox outbound adapter**, identified by the safe `AdapterRef` token `adapter:mailbox-outbound` (set on `ExecuteApprovedOutboundDraft.AdapterRef` and `OutboundMailboxSendResult.AdapterRef`). "Rate-limit an outbound channel" = record a per-`(tenant × channel)` send budget so its future approved sends are throttled (fail closed transiently) once the trailing-window admitted-send count reaches the budget — distinct from the Epic 6 **authority** controls (`SenderAuthorityClass`/`OutboundSendAuthorityEvaluator`/`OutboundDraftAuthorityEvaluator`), the global static `ChatBotSpineCommandAllowlist` (never tenant-mutable; only append the one new governance command name), and from the 7.24/7.25 `Disabled`/`Quarantined` control states (same subject class, a *parameter* not a control state).
- The outbound flow is a four-step governed pipeline: **(1) `CreateOutboundDraft`** → **(2) `RequestOutboundSendApproval`** → **(3) `DecideOutboundApproval`** → **(4) `ExecuteApprovedOutboundDraft`** (the send, where `IOutboundMailboxSender.SendAsync` performs the external dispatch via the `AcceptedCommandDispatcher`). The outbound-channel rate-limit belongs at **step 4, before `SendAsync`**, as the **last gate of the send seam** (after the Disabled/Quarantined control-state switch), so it throttles the external send while steps 1–3 (drafts/approvals) stay inspectable and a disabled/quarantined channel keeps its precise control-state reason.
