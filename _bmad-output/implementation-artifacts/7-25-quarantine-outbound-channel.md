# Story 7.25: Quarantine outbound channel

Status: done

<!-- Validation: create-story checklist applied 2026-06-03. -->

## Story

As an authorized **policy administrator** (a human admin holding the policy scope, under a two-person rule),
I want to quarantine an **outbound channel** for a tenant,
so that risky outbound activity is **held for review** — **every approved outbound send through that channel is routed to manual review and fails closed at the outbound send seam, and no external message leaves the project boundary while quarantined** — while **pending drafts and approvals remain inspectable** and every prior record stays intact and auditable, with safe recovery guidance shown, until the quarantine is cleared.

## Acceptance Criteria

1. Given an outbound channel under investigation, when an authorized **human policy admin** proposes a **quarantine** and a **second** authorized human policy admin approves it (FR75d two-person rule), then the outbound channel transitions to a durable **Quarantined** governance control state and **future approved sends through that channel are routed to manual review / held and fail closed at the outbound send seam** (`AcceptedCommandDispatcher`'s `ExecuteApprovedOutboundDraft` branch) — **no external message is dispatched to the outbound adapter while quarantined** — while **unrelated outbound channels and unrelated tenants continue normally** (isolation, NFR30/NFR18). The quarantine is a security-sensitive FR74 governance control — **not** the Epic 6 outbound draft/approval authority path — so it MUST go through the same submit→second-person-approve flow established for the Story 7.24 outbound-channel disable (`SubmitOutboundChannelDisable`→`ApproveOutboundChannelDisable`) and the Story 7.22 command-capability quarantine (`SubmitCommandCapabilityQuarantine`→`ApproveCommandCapabilityQuarantine`); a single-actor quarantine never takes effect. 2. Given the quarantine proposal and approval, when authorization runs, then the operation is permitted only for a **human policy administrator** — gate on **`AdminAuthorityEvaluator.HasHumanAdminScope(actor.Principal, AdminScope.Policy)`** (outbound-channel governance is a security-sensitive policy concern — the same scope that gates `SubmitTenantPolicyChange` and the Story 7.18–7.24 actor / command-capability / outbound-channel controls; the epic's persona is "policy administrator"). There is **no** `AdminScope.Security`/`AdminRole.SecurityEngineer`. A `tenant-admin` still qualifies because `AdminScopes.ScopesForRole(TenantAdmin)` returns the full scope set (FR75a union) — so this is **not** a relaxation. The operation is **denied for service clients and AI actors** even when they carry admin-looking claims (the human-actor gate inside `HasHumanAdminScope`/`IsHumanActor`), and denied for non-policy human scopes (`mailbox-admin`/`compliance-admin`/`operations-admin`-only). The approving admin MUST be a **different person** from the proposer: both `RequesterRef != ApproverRef` (Ordinal safe-token compare) and `RequesterActorId != approver envelope UserId` are enforced — at the gateway validation stage, the accepted-command dispatcher, **and** re-checked in the aggregate, mirroring `IsValidOutboundChannelDisableApproval`, `AcceptedCommandDispatcher`'s distinct-approver guard (`:334`), and `GovernedOperationAggregate.Handle(ApproveOutboundChannelDisable)`. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.25`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75a`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75d`; `src/Hexalith.ChatBot.Server/Governance/Admin/AdminAuthorityEvaluator.cs`; `src/Hexalith.ChatBot.Server/Gateway/Stages/AcceptedCommandDispatcher.cs:334`]

3. Given the quarantine is applied (approval committed), when it is recorded, then the operation records — with **no skip-audit path** (FR74, FR75g, NFR15a) — the **actor** (admin identity / actor type), **scope used** (`admin-scope:policy`), **subject** (the safe outbound-channel ref — e.g. `adapter:mailbox-outbound`), **reason** (documented justification reason code), **old state** (`Active`), **new state** (`Quarantined`), **policy snapshot id**, and **timestamp**, via a metadata-only `AuditEnvelope` whose `StateTransition` is `"Active->Quarantined"`. The audit is written through the existing fail-closed pre-commit seam (`IAuditWriter.RecordPreCommitAsync` via `CommandGateway`): when the pre-commit audit is unavailable, **no durable quarantine state is written and no send-blocking side effect occurs** (fail closed), reusing the `CommandGateway` audit-unavailable behavior. No admin role bypasses NFR15a/NFR50a. 4. Given an outbound channel is Quarantined for a tenant, when an `ExecuteApprovedOutboundDraft` send targeting **that channel** (keyed by the safe channel ref `AdapterRef`) is dispatched for that tenant, then the **send fails closed at the outbound send seam before any external dispatch**: in `AcceptedCommandDispatcher`'s `ExecuteApprovedOutboundDraft` branch, the channel-control check runs **before `IOutboundMailboxSender.SendAsync`** (`AcceptedCommandDispatcher.cs:714`) and short-circuits the adapter — producing a fail-closed send-rejected outcome with the finite reason `outbound_channel_quarantined` so **no message is sent to the outbound adapter and no external communication leaves the boundary while quarantined**. This reuses the existing `AdapterStatus != "sent"` → `RejectOutboundSend(...)` path in `GovernedOperationAggregate.Handle(ExecuteApprovedOutboundDraft)` (`:1264`): the dispatcher sets a **distinct** non-`"sent"` `AdapterStatus` token (`"quarantined"`) which the aggregate maps to the `outbound_channel_quarantined` reason **beside** the existing `"blocked"` → `outbound_channel_disabled` mapping (`:1259`). The check **fetches the channel control state once** and switches on it (`Disabled` → `"blocked"`/`outbound_channel_disabled`; `Quarantined` → `"quarantined"`/`outbound_channel_quarantined`) rather than reading the provider twice. As in Story 7.24 the enforcement seam is the **outbound send seam** (not an admission/intake seam) — the only place the channel ref `AdapterRef` and the authenticated `TenantBinding` meet before the external adapter call. A send targeting any **other (still-Active)** channel for the same tenant, or the same channel for a **different** tenant, is unaffected (isolation). The new `outbound_channel_quarantined` reason is **distinct from** `outbound_channel_disabled` (same outbound-channel control family, different control state), `outbound_adapter_unavailable` (the adapter-not-configured/unreachable case), `adapter_not_approved_mode`, `command_capability_quarantined`, and every actor-control reason (`service_client_quarantined`, `ai_actor_quarantined`, etc.). [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.25`; `src/Hexalith.ChatBot.Server/Gateway/Stages/AcceptedCommandDispatcher.cs:704`; `src/Hexalith.ChatBot.Server/Adapters/Mailbox/IOutboundMailboxSender.cs`; `src/Hexalith.ChatBot.Server/Operations/GovernedOperationAggregate.cs:1256`]

5. Given an outbound channel is quarantined, when its prior and pending activity is inspected, then **all previously recorded outbound drafts, approval requests, approval decisions, send outcomes, audit envelopes, and conversation content remain visible, intact, and fully reconstructable**, and **pending drafts/approvals (created or awaiting approval) remain inspectable** — quarantine affects **only future sends**, never already-committed records (`OutboundDraftCreated`, `OutboundApprovalRequested`, `OutboundApprovalDecisionRecorded`, prior `OutboundSendSucceeded`) or their audit trails (NFR17 visible/recoverable states; FR75c admins cannot mutate project-level records). The quarantine does **not** block `CreateOutboundDraft`, `RequestOutboundSendApproval`, or `DecideOutboundApproval` (drafts and approvals stay inspectable) — it holds/blocks **only the send/execute step** through the quarantined channel. Quarantine is reversible by a future release/re-activate flow; this story does not delete or rewrite any prior record. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.25`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR17`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75c`]

6. Given an actor encounters a quarantined outbound channel (admin viewing status, or a send held / blocked), when guidance is surfaced, then **safe recovery guidance** is shown from the **finite message catalog** — a safe headline (≤ 80 chars), a one-line reason from a finite set conveying "held for review", a next-action pointing to the responsible role (review/release is a policy-admin/two-person action), and a `disabled-action` reason — using `ChatBotMessageCatalog` / `ChatBotMessageCodes` / `ChatBotDisabledActionReasons`, never raw error text. The guidance conveys that outbound sending through this channel is paused while evidence is reviewed and is held until a policy administrator reviews and releases it. This matches the **terminal** Story 7.22 `command_capability_quarantined` / Story 7.24 `outbound_channel_disabled` catalog choice (`request-access` + `disabled-action`), **not** a transient rate-limit entry. No surface names an unauthorized project/file/party/mailbox-content/recipient/audit detail (NFR2); EN/FR via existing localization; stable machine tokens (reason codes, state tokens, correlation ids, channel refs) stay untranslated. ### What "outbound channel" means here, and where it is blocked

- An **outbound channel** is the governed external-send path through which an approved outbound draft leaves the project boundary. In M0/M1 the single outbound channel is the **M365 mailbox outbound adapter**, identified by the safe `AdapterRef` token `adapter:mailbox-outbound` (set on `ExecuteApprovedOutboundDraft.AdapterRef` and `OutboundMailboxSendResult.AdapterRef`). "Quarantine an outbound channel" = mark that channel **Quarantined for the tenant** so its future approved sends are held for review / fail closed — distinct from the Epic 6 **authority** controls (`SenderAuthorityClass`/`OutboundSendAuthorityEvaluator` govern *who/what may send*; `OutboundDraftAuthorityEvaluator` governs *who may draft*) and from the global static `ChatBotSpineCommandAllowlist` (never tenant-mutable; only append the two new governance command names). It is the same control plane as the 7.24 `Disabled` state, a different control-state value.

The outbound-channel quarantine belongs at **step 4, before `SendAsync`**, so it holds the external send while steps 1–3 (drafts/approvals) stay inspectable.
