# Story 9.6: Correction-driven vector reindexing

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a security owner,
I want vector, embedding, and prompt-context entries invalidated and rebuilt after correction,
so that M2 derived stores do not preserve stale or misassociated material.

## Acceptance Criteria

1. **A correction that touched material in a derived store triggers `ReindexVectors(tenantId, correctionId, sourceVersion)`, which invalidates and rebuilds the affected entries with idempotent, version-guarded behavior (FR91a, NFR9a, architecture.md:190, 399).**
   **Given** a correction affects material already present in a vector index, embedding store, prompt-context cache, or candidate-ranking cache,
   **When** M2 correction propagation runs,
   **Then** the `vector-reindex` store participates as a real correction-propagation activity (`CorrectionPropagationStoreKeys.VectorReindex`) and `ReindexVectors(tenantId, correctionId, sourceVersion)` **invalidates** every affected entry across the four derived-store classes (Story 9.5 `DerivedStoreClass`) through the Story 9.5 `IDerivedStore` seam and **rebuilds** the corrected entries — keyed by the single-source `DerivedStorePartition.KeyFor` convention, scoped to the tenant partition, **never** by an application-side filter.
   - **`ReindexVectors` is the exact named operation from FR91a/architecture.** Expose `ValueTask<VectorReindexOutcome> ReindexVectorsAsync(string tenantId, string correctionId, long sourceVersion, …)` behind an `IVectorReindexer` seam (the named contract architecture.md:190/399 commits to). The in-memory default operates against the Story 9.5 `IDerivedStore` partition seam; the **live Hexalith.Memories Redis-Vector/FalkorDB reindex binding is the deferred M2 wiring** (see Deferrals) — the seam is built so the live binding is **additive** (a `Memories`-backed `IVectorReindexer` whose partition is `IndexSchemaDefinitions`), not a rewrite.
   - **Idempotent + version-guarded — order-tolerant last-writer-wins.** A reindex carries the correction's `sourceVersion`. A re-delivered or out-of-order correction whose `sourceVersion` is **less than or equal to** the last reindex already applied to a partition is a **no-op** (mirrors `GovernedOperationProjectionHandler`'s `existing.SourceVersion >= notification.SourceVersion ⇒ Ignored`). The version guard lives in one authoritative place — a tenant-partitioned `IVectorReindexLedger` recording the last-applied correction `sourceVersion` per `DerivedStorePartition` — never two drifting checks. Re-running the **same** `(tenantId, correctionId, sourceVersion)` produces the **same** end state (no duplicate entries, no double-invalidation error).
   - **Invalidate means structural removal, not a filter flag.** The Story 9.5 `IDerivedStore` has Put/Get/Enumerate but **no delete op** — the 9.5 Senior Review explicitly flagged this as the M2 follow-up ("the deferred M2 live binding should add a delete seam"). This story adds `ValueTask<bool> InvalidateAsync(DerivedStoreClass cls, string tenantId, string resourceId, CancellationToken)` to `IDerivedStore`/`InMemoryDerivedStore`: it removes the entry from the tenant's partition (returning whether an entry was present), so a stale/misassigned entry is physically gone from the store, not merely hidden. After invalidation, `GetAsync` for that resource yields the safe not-found.
   - **The correction-propagation activity wires the reindexer in.** Add `internal sealed class VectorReindexCorrectionPropagationStoreActivity : ICorrectionPropagationStoreActivity` with `StoreKey => CorrectionPropagationStoreKeys.VectorReindex`, whose `InvalidateAndRebuildAsync` calls `IVectorReindexer.ReindexVectorsAsync(request.TenantId, request.CorrectionId, request.SourceVersion, …)` and maps the `VectorReindexOutcome` onto a `CorrectionPropagationActivityResult` (`"success"` / `"failed"` + reason code). The coordinator runs this activity as part of an **M2 scope** (`CorrectionPropagationStoreKeys.RequiredM2 = RequiredM0 + VectorReindex`); the existing four metadata-only M0 activities are unchanged.

2. **A reindex that exceeds the M2 SLO surfaces `correction-delayed` with owner role, next safe action, and P2 incident linkage (NFR17a).**
   **Given** reindexing exceeds the M2 SLO (p95 ≤ 60 min, incl. vector reindex),
   **When** the corrected item is inspected,
   **Then** it shows `correction-delayed` (lifecycle `LifecycleState.CorrectionDelayed`), the responsible **owner role** (`operations`), the **next safe action** (`escalate-to-operations`), and **P2 incident linkage** per NFR17a — and the delay is recorded **fail-closed audit-then-deliver**: a metadata-only pre-commit audit envelope carrying the **P2 severity** marker is written **before** exactly one `OperatorAlertKind.CorrectionDelayed` alert is emitted.
   - **The M2 SLO is 60 minutes, distinct from M0/M1's 10.** NFR17a: p95 ≤ 10 min (M0/M1, no vector index) **and ≤ 60 min (M2, incl. vector reindex)**. The existing coordinator only knows `M0M1P95Target = 10 min`. Add the M2 target and a **define-once `CorrectionPropagationSlo`** helper holding both targets plus `DeadlineFor(scope, startedAtUtc)` / `IsBreached(deadlineUtc, nowUtc)`; the deadline for a correction whose scope includes `vector-reindex` is the **M2 60-min** target. Never inline a second SLO constant (the 9.4 `ReplayTenantPolicy` / 9.5 `DerivedStorePartition` define-once lesson).
   - **P2 incident linkage is net-new — the current delayed path has neither an audit envelope nor a P2 marker.** Today `DaprCorrectionPropagationCoordinator.MarkDelayedAsync` writes only the `DelayMailboxAssociationCorrectionPropagation` command + a bare `CorrectionDelayed` alert (no pre-commit audit, no severity). Upgrade the delayed path to the 9.1/9.4/9.5 **audit-then-deliver** standard: add `AuditEnvelopeFactory.CorrectionPropagationDelayed(...)` (pre-commit, `Decision: "alert"`, `Worker` surface origin, metadata-only refs, a `correction-propagation-severity:p2` ref token mirroring 9.2's `audit-completeness-severity:p1`), write it **first**, and only on a successful audit write emit the **single** `CorrectionDelayed` alert (now carrying a safe P2 incident locator token in `FirstBreakLocator`). A failed audit write suppresses the alert (fail-closed), never the reverse.
   - **SLO-breach detection is deterministic and testable.** The reindex outcome reports whether it finished within the effective deadline (`VectorReindexOutcome` carries the computed deadline / a `SloBreached` flag derived from `CorrectionPropagationSlo`). When the reindex is unfinished or its elapsed time exceeds the M2 deadline, the coordinator marks `correction-delayed` with reason code `vector_reindex_slo_exceeded`; the in-memory reindex completes promptly, so the breach path is exercised via an injected slow/incomplete `IVectorReindexer` test-double and a controllable `ISystemClock`. A reindex that **throws** is a fail-closed delay signal (`vector_reindex_failed`), never a silent success.

### Cross-cutting requirements that hold for every AC

- **No stale/misassigned material may survive a correction — this is the security property (FR91a, NFR9a, architecture cross-cutting #1).** The whole point of FR91a is that derived stores "do not use stale, misassigned project context": after `ReindexVectors`, the **prior** association's entries are physically invalidated from every derived-store class and only the **corrected** entries remain. Never weaken "invalidate" to a filter flag the read side could forget to apply.
- **Define-once / reuse — do NOT reinvent.** Consume by reference: the Story 9.5 `IDerivedStore`/`DerivedStorePartition`/`DerivedStoreClass`/`DerivedStoreEntry` seam (the reindex operates **through** it — do not build a second derived-store abstraction); the Story 2.8 `ICorrectionPropagationStoreActivity` / `DaprCorrectionPropagationCoordinator` / `CorrectionPropagationStoreKeys` / `CorrectionPropagationActivityRequest`/`Result` seam (the vector-reindex activity plugs into **this**, it is not a parallel coordinator); the order-tolerant version-guard pattern (`GovernedOperationProjectionHandler` `SourceVersion >=` last-writer-wins); the `AuditEnvelopeFactory` + `IAuditWriter.RecordPreCommitAsync` + `IOperatorAlertSink.EmitAsync` audit-then-deliver discipline (`ReplayIsolationBreach`/`DerivedStoreIsolationBreach`/`AuditChainBroken`); `AuditMetadata` safe-token helpers; `CommandGatewayServiceCollectionExtensions` `TryAdd` DI shape; the Hexalith.Memories `IndexSchemaDefinitions` convention as the documented M2 live target. **Reuse `OperatorAlertKind.CorrectionDelayed`** — do not add a new alert kind for the delayed surface.
- **Metadata-only / no-leak floor (NFR2, NFR42).** Derived stores hold the most sensitive material in the system (embeddings, prompt context). Every new emitted token — reindex outcome, ledger key, activity result, delay alert payload, P2 locator — is an `AuditMetadata`-safe bounded token (ASCII alnum + `.-_:@|`). The reindexer records **no** vector floats, embedding values, prompt text, or candidate payloads; rebuilt `DerivedStoreEntry` values stay metadata-only (a safe `ResourceId` + bounded `ContentDigest`/sentinel), exactly as Story 9.5 built them. Extend the Epic 7/8/9 no-leak serialization suites to every new type.
- **Audit two-phase / WORM is untouched (D4, NFR49a).** This story emits audit through the **existing** `AuditEnvelopeFactory` + `IAuditWriter` path; it adds **no** new commit-time gate, never mutates the chain, and does not touch the canonical hash. The reindex + delay records are out-of-band (pre-commit `Decision: "alert"`).
- **Boundary (NetArchTest-enforced).** All new reindex/SLO internals (`IVectorReindexer`/`InMemoryVectorReindexer`/`VectorReindexOutcome`, `IVectorReindexLedger`/in-memory ledger, `VectorReindexCorrectionPropagationStoreActivity`, `CorrectionPropagationSlo`, the new `IDerivedStore.InvalidateAsync`, the new `AuditEnvelopeFactory` factory) are `internal` to `Hexalith.ChatBot.Server`; no `.UI`/`.Cli`/`.Mcp` reference. Extend/mirror the `DerivedStoreIsolationBoundaryFitnessTests` boundary assertion.
- **Inert-control-floor honesty.** The **live Hexalith.Memories Redis-Vector/FalkorDB reindex binding**, the **async/long-running reindex runtime** (the in-memory reindex is synchronous), and the **periodic SLO-deadline sweep trigger** are deferred — the `ReindexVectors` contract, the version-guard ledger, the `IDerivedStore.InvalidateAsync` seam, the correction-propagation wiring, the `CorrectionPropagationSlo` deadline contract, and the P2 audit-then-deliver delay path are the shippable, fully-built-and-tested deliverables. **State the deferrals explicitly in Completion Notes**; never let "the live Memories reindex isn't wired" read as "stale material survives correction" — the invalidation + rebuild + version guard **are** built and tested.

## Dev Notes

### What this story actually changes (and what already exists)

Story 9.6 makes correction propagation **reach the derived stores**: when an association is corrected, the vector/embedding/prompt-context/candidate-ranking entries that referenced the *prior* association are invalidated and the corrected entries rebuilt — idempotently and version-guarded — so M2 derived stores never serve stale, misassigned context (FR91a, NFR9a). It is **new seams wired into two existing mature seams** (Story 2.8 correction propagation + Story 9.5 derived-store partition); the audit/alert/SLO machinery already exists in mature form — **reuse, do not reinvent.**

**The single most important framing for the dev agent:** like Stories 9.1–9.5's inert-control-floor, the **live Hexalith.Memories Redis-Vector/FalkorDB reindex backing is not integrated into the ChatBot today** (architecture.md:190, 399 mark `ReindexVectors` as "stays an M2 activity"; 324–325 mark vector/embedding/prompt-context as "planned via Hexalith.Memories — M2"). So this story ships the **`ReindexVectors` contract + version-guard ledger + the `IDerivedStore.InvalidateAsync` delete seam + the correction-propagation activity wiring + the M2 SLO contract + the P2 audit-then-deliver delay path + tests + ADR**, and **defers** the live Memories binding, the async long-running reindex runtime, and the periodic SLO-deadline sweep. The seam is built so the M2 live binding is **additive** (a Memories-backed `IVectorReindexer` whose partition is `IndexSchemaDefinitions`), never a rewrite. **Do not** pull Hexalith.Memories into the ChatBot DI/AppHost in this story.

**Findings**

- **[MEDIUM · FIXED] Version-guard watermark committed before the reindex was applied (`InMemoryVectorReindexer` + `IVectorReindexLedger`).** The loop called `ledger.TryAdvance(cls, …)` *first* and only then ran `InvalidateAsync`/`PutAsync`. If a partition's invalidate/rebuild threw mid-way (the transient-failure case the deferred live Hexalith.Memories Redis-Vector/FalkorDB binding will hit), that partition's watermark was already advanced, so a redelivery of the same `(tenant, correction, sourceVersion)` hit `TryAdvance ⇒ false` and **skipped the partition**, leaving the prior association's stale entry behind — contradicting AC1's "the last reindex already *applied* to a partition" wording and the FR91a/NFR9a security property. Latent for the shipped synchronous in-memory store (its only throws are deterministic), but a real defect in the seam the live binding inherits. **Fix:** split the ledger into a pure read `ShouldReindex` (used to decide the version-guard skip) and kept `TryAdvance` as the durable commit, invoked only *after* the partition's invalidate+rebuild is applied. Added a regression test (`FlakyDerivedStore` throws once on the first rebuild ⇒ the failed partition stays un-advanced ⇒ redelivery reindexes it rather than skipping) plus two direct `ShouldReindex` ledger tests. Server.Tests 1334 → 1337, 0 failed; all suites green.
- **[LOW · noted, no change] SLO deadline base is per-activity dispatch time, not correction-propagation start.** The coordinator builds the activity request with `clock.UtcNow` as `StartedAtUtc`, so the reindexer's M2 deadline (`startedAt + 60 min`) is measured from when the activity dispatches rather than when the correction propagation began (`request.StartedAtUtc`). Immaterial for the shipped synchronous reindex (which completes immediately and never breaches) and changing it would alter the acknowledgement command's `StartedAtUtc` semantics; the SLO-base should be revisited with the deferred async/long-running reindex runtime.
