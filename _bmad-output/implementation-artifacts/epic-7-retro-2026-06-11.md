## What Went Well

- The `GovernedOperationAggregate` became a reusable governance spine. Policy changes, notification routing, escalation policy, and the control-floor operations all reuse the same command-gateway and audit discipline.
- Distinct-approver enforcement was defended across authorization validation and aggregate/application checks, with repeated story-level review coverage for `RequesterRef` / `ApproverRef` separation.
- The command allowlist was widened only after validation, authorization, audit, and tests were in place, preserving the M0 safety floor while adding M1 breadth.
- Metadata-only behavior stayed consistent across audit refs, problem details, alerts, notification payloads, and story tests.
- The subject-specific enforcement seams were explicitly separated: mailbox intake, service-client grant validation, AI actor validation, actor-agnostic command-capability admission, and outbound send dispatch.
- Later story re-reviews strengthened coverage around redaction, two-person version conventions, pre/post-commit audit phase assertions, and control-floor isolation.
- Current planning docs now carry the key retrospective learning forward: Stories 8.7a/8.7b own durable projection and periodic trigger activation.

## Challenges

- Runtime activation remained deferred. Code still registers `AlwaysActive...ControlStateProvider` and `AlwaysUnlimited...RateLimitProvider` defaults in `CommandGatewayServiceCollectionExtensions`.
- Notification, escalation, throttle, backlog, and rubber-stamp evaluators are implemented and registered, but no periodic production trigger calls them on the wired path.
- Some original implementation notes overstated runtime impact before durable read-side projection existed. The current README and architecture now correct that claim.
- Story bookkeeping drift recurred across Epic 7: debug-log test totals, File List completeness, and submodule pointer hygiene needed repeated review attention.
- JSON/validation edge cases required review reinforcement, especially omitted enum defaults and "validated but not applied" logic.
- The sprint-status timeline is historically noisy: later epics are marked done or partially done while Epic 8 runtime activation stories remain backlog. The documentation now distinguishes story completion from production activation.

## Key Insights

1. A shared submit-approve aggregate scales across governance controls when subject-specific enforcement remains outside the aggregate and close to the actual runtime boundary.
2. "Recorded and audited" is not the same as "active in production." Runtime claims require durable projection, provider replacement, trigger ownership, and negative-path tests through the wired path.
3. Distinct-approver rules and metadata-only audit are architecture properties, not story-local details. They need repeated checks at every command family added to the control floor.
4. Rate-limit controls differ from disable/quarantine controls. They are single-actor bounded policy mutations, so docs and tests must avoid implying an approval counterpart where none exists.
5. The command-capability control plane is per-tenant and distinct from both the static spine allowlist and Epic 5 service-client grant command lists.
6. Bookkeeping checks are part of quality in this repo: File Lists, test-count notes, sprint status, and submodule status all affect whether story evidence can be trusted.
