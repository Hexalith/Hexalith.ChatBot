# Story 7.23: Rate-limit command capability

Status: done

<!-- Validation: create-story checklist applied 2026-06-03. -->

## Story

As an authorized **policy administrator** (the epic's "security engineer" persona — there is no security-engineer scope; it maps to the policy scope) acting through a **single-actor, schema-bounded policy mutation**,
I want to rate-limit a **command capability** (a governed command *type*) for a tenant,
so that one command class cannot degrade the tenant workflow — **command admission applies the bounded per-window limit to that command type for every actor (human, service client, or AI actor) of the tenant** and returns a typed, redacted rate-limit response when the command type exceeds it, while unrelated command capabilities and unrelated tenants keep their own independent budgets and are protected from degradation where isolation is possible.

## Acceptance Criteria

1. Given a command capability exceeding policy thresholds, when an authorized **human policy administrator** configures a rate limit, then a durable per-`(tenant × command-type)` rate-limit budget is recorded and **command admission applies the bounded limit** to that command type's future submissions. This is a **standard, single-actor policy mutation** — explicitly **NOT** the Story 7.21/7.22 FR75d two-person control: FR74's decomposition states "disable and quarantine are security-sensitive admin operations (per FR75d two-person rule); **rate-limit is a standard policy mutation**." So the command follows the **single-actor** shape of `SubmitAiActorRateLimit` (Story 7.20) / `SubmitServiceClientRateLimit` (Story 7.17) / `SubmitMailboxSourceRateLimit` (Story 7.14) — one authority check, no approver — **not** the submit→second-person-approve flow of `SubmitCommandCapabilityDisable`/`SubmitCommandCapabilityQuarantine`. There is **no** `Approve…` counterpart, **no** distinct-approver guard, **no** `AcceptedCommandDispatcher` branch, and **no** `CommandCapabilityControlState`/lifecycle transition (rate-limit is a *parameter*, not a control state). [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.23`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`; `_bmad-output/implementation-artifacts/7-20-rate-limit-ai-actor.md`; `src/Hexalith.ChatBot.Contracts/Commands/AiActorControlContracts.cs:124`]

2. Given the rate-limit value, when it is validated, then it is **bounded by the Tenant Policy Schema** (FR75): the configured per-window command budget is accepted only within a declared, closed, non-negative min/max range, and an out-of-range / wrong-type / undeclared value is **rejected with a safe reason code** (and, at the enforcement seam, falls back to safe defaults — never silently raising the cap). Mirror the closed `AiActorRateLimitBounds` / `ServiceClientRateLimitBounds` discipline (`Minimum`/`Maximum`/`SafeDefaults`/`IsWithinBounds`) — a tenant cannot introduce a new window dimension or a custom formula. The bound is a Standard (non-security-sensitive) knob, so no two-person rule applies. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75`; `src/Hexalith.ChatBot.Contracts/Commands/AiActorRateLimitBounds.cs`; `src/Hexalith.ChatBot.Contracts/Commands/ServiceClientRateLimitBounds.cs`]

3. Given authorization runs, when the command is evaluated, then it is permitted only for a **human policy administrator** — gate on **`AdminAuthorityEvaluator.HasHumanAdminScope(actor.Principal, AdminScope.Policy)`** (command-capability / command-allowlist governance is a security-sensitive policy concern — the same scope that gates `SubmitTenantPolicyChange`, the Story 7.21 command-capability disable, and the Story 7.22 quarantine; the epic's "security engineer" persona maps to the **policy** scope — there is **no** `AdminScope.Security`/`AdminRole.SecurityEngineer`). A `tenant-admin` still qualifies because `AdminScopes.ScopesForRole(TenantAdmin)` returns the full scope set (FR75a union) — so this is **not** a relaxation. The operation is **denied for service clients and AI actors** even when they carry admin-looking claims (the human-actor gate inside `HasHumanAdminScope`/`IsHumanActor`), and denied for non-policy human scopes (`mailbox-admin`/`compliance-admin`/`operations-admin`-only). There is **no** second-person/distinct-approver requirement; a single authorized human policy-admin applies it. Denial of the governance command itself uses `ChatBotAuthorizationReasonCodes.AuthorizationDenied`. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.23`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75a`; `src/Hexalith.ChatBot.Server/Governance/Admin/AdminAuthorityEvaluator.cs`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ParticipantAuthorizationStage.cs:112`]

4. Given the rate limit is applied (committed), when it is recorded, then the operation records — with **no skip-audit path** (FR74, FR75g, NFR15a) — the **actor** (requester identity / actor type), **scope used** (`admin-scope:policy`), **subject** (the safe command-capability ref — the rate-limited command type name), **reason** (documented justification reason code), **old state** (the prior budget / `unlimited`), **new state** (the new bounded budget), **window token**, **policy snapshot id** (the allowlist/policy version in effect), and **timestamp**, via the metadata-only `AuditEnvelope`. There is **no** `StateTransition` ref (rate-limit is not a lifecycle transition — old/new "state" are budgets). The audit is written through the existing fail-closed pre-commit seam (`IAuditWriter.RecordPreCommitAsync` via `CommandGateway`): when the pre-commit audit is unavailable, **no durable rate-limit state is written and no enforcement side effect occurs** (fail closed), reusing the disable/`CommandGateway` audit-unavailable behavior. No admin role bypasses NFR15a/NFR50a. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.23`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75g`; `src/Hexalith.ChatBot.Server/Audit/AuditEnvelopeFactory.cs:1908`; `src/Hexalith.ChatBot.Server/Gateway/CommandGateway.cs`]

5. Given a command capability has a rate-limit budget configured for a tenant, when **any actor** (human, service client, or AI actor) submits a command **of that rate-limited type** for that tenant and the recent **admitted-command** count in the trailing rolling window has reached the effective budget, then **command admission enforces the limit at the actor-agnostic `ParticipantAuthorizationStage`** — returning `ChatBotAuthorizationResult.Denied(ChatBotAuthorizationReasonCodes.CommandCapabilityRateLimited)` (a typed, redacted rate-limit response) so the over-budget submission is **not admitted and no restricted work is performed**. This is the **key divergence from the actor-subject rate-limit cells (7.14/7.17/7.20)**: the subject is a **command type**, not an actor or worker source, so enforcement must cover **all actor types** and therefore lives in the **actor-agnostic authorization stage** (`ParticipantAuthorizationStage`, which runs for every actor and has both `submission.Request.CommandType` and the authenticated `tenantBinding`) — **not** in `ServiceClientGrantValidator` (which only runs for `service`/`ai` actors via `RequiresGrant` and would miss human submissions, exactly as the 7.21/7.22 disable/quarantine cells argued). The rate-limit check is placed as the **final gate** in `AuthorizeAsync` — **after** the top-of-stage command-capability Disabled/Quarantined control-state switch, **after** the `ServiceClientGrantValidator` call, **and after** the participant-authority + per-command admin-scope branches — so only otherwise-fully-admissible commands count against the budget and a disabled/quarantined/under-scoped/unauthorized command keeps its own precise reason code (rate-limit never masks a security denial). The FR74 governance commands are **exempt** (so a rate-limited tenant can still govern/reverse). When the command type is **under** budget the submission is admitted normally. The trailing-window count is computed with the established clock-injected window math (`NotificationThrottleEvaluator.CountInTrailingWindow`: server-measured UTC age, never client/item-supplied time), keyed per-`(tenant × command-type)`. A submission of any **other (un-throttled)** command type for the same tenant, or the same command type for a **different** tenant, is unaffected (isolation). The new `command_capability_rate_limited` reason is **distinct from** `command_capability_disabled` / `command_capability_quarantined` (same command-capability family, control states not a parameter), `command_not_allowlisted` (the global static spine-allowlist refusal), `service_client_grant_under_scoped` (the per-grant allowlist), and every actor-control / actor-rate-limit reason (`ai_actor_rate_limited`, `service_client_rate_limited`, etc.). [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.23`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ParticipantAuthorizationStage.cs:65`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ServiceClientGrantValidator.cs:155`; `src/Hexalith.ChatBot.Server/Notifications/NotificationThrottleEvaluator.cs:63`]

6. Given rate-limiting is in effect, when capacity impact is observed, then admission **exposes capacity-impact metrics that surface the throttling/backlog effect** — at minimum the effective budget, the observed trailing-window admitted-command count, and whether this submission was throttled for the command type — carried as safe, finite integer tokens at the audit/observable seam (mirror the `AiActorRateLimitObservation` / `ServiceClientRateLimitObservation` shape: integer/rational arithmetic, never floats). Rate-limiting **protects unrelated tenants/command-capabilities from degradation where isolation is possible** (NFR30, NFR18): each command type's budget and trailing-window counter are **independent**, so throttling a noisy command type never throttles a sibling command type or another tenant. Full operational-dashboard wiring is Epic 8 and is out of scope here — this story exposes the metric at the audit/observable seam only. **"Safe status to authorized operators"** (the epic AC phrase) is satisfied by the catalog guidance + the authorization reason code + the audit metric refs, consistent with the 7.12–7.22 deferral of an S5 surface. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.23`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR30`; `src/Hexalith.ChatBot.Server/Gateway/Stages/IAiActorRateLimitProvider.cs:47`]

7. Given a command is denied for a rate-limited command capability, when guidance is surfaced, then **safe recovery guidance** is shown from the **finite message catalog** — a safe headline (≤ 80 chars), a one-line reason conveying "this command's capacity is temporarily limited to protect the tenant workflow; retry shortly", a next-action of **`retry-later`** (transient, **not** `request-access` — the command capability is not disabled or quarantined), and a **transient** `dependency-degraded` reason (**not** `disabled-action`) — using `ChatBotMessageCatalog` / `ChatBotMessageCodes` / `ChatBotMessageNextActions` / `ChatBotDisabledActionReasons`, never raw error text. This matches the Story 7.20 `AiActorRateLimited` / 7.17 `ServiceClientRateLimited` catalog choice and is deliberately distinct from the terminal `command_capability_disabled` / `command_capability_quarantined` entries (`request-access` + `disabled-action`). The guidance never names an unauthorized project/file/party/mailbox-content/audit detail (NFR2); EN/FR via existing localization; stable machine tokens (reason codes, window tokens, correlation ids, command type names) stay untranslated. 8. Given the rate-limit subject and audit refs are metadata, when the command and audit envelope are serialized, then they carry **only safe, finite tokens** — the safe command-capability ref (the command type name, a finite identifier), `admin-operation:command-capability-rate-limit` / `admin-scope:policy`, the reason code, old/new budget values, the window token, policy-snapshot id, correlation id, UTC timestamp — and **never** credentials, OAuth grant fingerprints, bearer tokens, secrets, model prompts/completions, raw claims/headers, delegated-user PII, mailbox/project/proposal/evidence content, or raw GUIDs that are not already safe identifiers (NFR2, NFR4, NFR5). ## Dev Notes

### Scope Boundaries

- Story 7.23 is the **twelfth** cell of the FR74 enforcement series (7.12–7.26: five subject classes — mailbox / service-client / AI-actor / **command-capability** / outbound — × three actions — disable / quarantine / rate-limit) and the **third (final) command-capability cell**. It implements exactly **one** cell: **command capability × rate-limit**. Disable (7.21) and quarantine (7.22) were **security-sensitive** admin operations gated by the **FR75d two-person rule**; **rate-limit (this story) is a standard, single-actor policy mutation** bounded by the Tenant Policy Schema. **Do not** implement any other subject class, the disable/quarantine actions, a future rate-limit-release/reset flow, or the Story 7.27 command-allowlist-v1 / full-lifecycle work here. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`; `_bmad-output/planning-artifacts/epics.md#Story 7.27`]
- **This story is a cross-product: take the 7.20 single-actor rate-limit pattern and apply it to the 7.21/7.22 command-capability subject + actor-agnostic admission seam.** Read 7.20 (rate-limit AI actor, commit `2579a42`) for the *single-actor command / bounds / window / direct-activation aggregate / audit-without-StateTransition / transient catalog / no-dispatcher-branch / no-lifecycle-transition / dedicated read-side providers* shape, and 7.21/7.22 (command-capability disable/quarantine, commits `c79da68`/`6f08dca`) for the *command-capability subject (a command TYPE) + `HasHumanAdminScope(AdminScope.Policy)` authority + **actor-agnostic enforcement at `ParticipantAuthorizationStage`** + `Fr74GovernanceCommandTypes` self-lockout + read-side deferral*. The result is the command-capability cell that is both single-actor **and** enforced actor-agnostically.
- **The two meaningful divergences — read these first:**
  1. **Enforcement seam moves from `ServiceClientGrantValidator` to `ParticipantAuthorizationStage` (the 7.21/7.22 wrinkle).** For the actor-subject rate-limits (7.14/7.17/7.20) the budget keys on an actor and the enforcement lived in `ServiceClientGrantValidator` (which only runs for `service`/`ai` actors and already has `ISystemClock` + the budget/history providers). The command-capability subject is a command **type**, so a **human** submission of the rate-limited type must also be throttled — the only seam that runs for **all** actor types and has both `submission.Request.CommandType` and the authenticated `tenantBinding` is the **actor-agnostic `ParticipantAuthorizationStage`**. That stage has **no clock today**, so this story injects `ISystemClock` + the two new dedicated providers into it. **Rejected:** a `ServiceClientGrantValidator` branch (misses humans — same reason 7.21/7.22 gave) or a worker check.
  2. **Rate-limit is a parameter, not a control state — the one meaningful semantic difference from 7.21/7.22.** "Per-command limits enforced at admission" = future submissions of that command type **fail closed at `ParticipantAuthorizationStage` with a transient, retryable response** (`command_capability_rate_limited` / `retry-later` / `dependency-degraded`) once the trailing-window count reaches the budget — **not** a hard, terminal control state. So **no** `CommandCapabilityControlState` value, **no** `LifecycleStates`/`LifecycleTransitionValidator`/`CommandSubmissionLifecycleTransitionGuard` change, **no** `Approve…` command, **no** pending-approval event/dictionary, **no** `AcceptedCommandDispatcher` branch, **no** distinct-approver guard. "Old/new state" in the audit = old budget / new budget; there is **no** `StateTransition` ref.
- **Authorization scope = policy-admin** (same as 7.20/7.21/7.22). There is **no** `AdminScope.Security` / `AdminRole.SecurityEngineer`; the epic's "security engineer" persona maps to the security-sensitive **policy** scope. Gate on **`HasHumanAdminScope(actor.Principal, AdminScope.Policy)`**. A `tenant-admin` still passes via the FR75a scope union — **not** a relaxation. Single actor — do **not** add a second-person requirement the epic does not impose. **Rejected:** a new `AdminScope.Security` (scope-creep) and `HasHumanTenantAdmin` (too coarse).
- **Placement = final gate** (the 7.20 doctrine, relocated). The rate-limit check is the **last** thing `AuthorizeAsync` does before returning `Allowed`, so only otherwise-fully-admissible commands consume budget and a Disabled/Quarantined/under-scoped/unauthorized command keeps its precise reason. The top-of-stage Disabled/Quarantined control-state switch (`:87–102`) stays where it is — it is a hard fail-closed control state; the rate-limit is a soft transient limit that coexists with it as the final gate.
- **Bounded by the Tenant Policy Schema (FR75).** The budget value is accepted only within a declared closed range. Reuse the `AiActorRateLimitBounds`/`ServiceClientRateLimitBounds` discipline: `Minimum`/`Maximum`/`SafeDefaults`/`IsWithinBounds`, out-of-bounds → safe default (= maximum), never raise the cap. A tenant cannot add a new window dimension or a custom formula.
- **Isolation (NFR30/NFR18).** Each command type has an independent budget + trailing-window counter keyed per-`(tenant × command-type)`. Throttling a noisy command type must never throttle a sibling command type or another tenant. Tenant identity is always from the **authenticated gateway binding**, never the command body. The subject (command type name) and all audit refs are **metadata-only, safe tokens** (NFR2); credentials, OAuth grant fingerprints, model prompts/completions, and delegated-user PII never appear (NFR4/NFR5).
- Rate-limit affects **future command admission only**. It must never delete, rewrite, or hide already-committed commands, events, proposals, associations, files, approvals, conversation content, or their audit trails (NFR17, FR75c).

### What "command capability" means here, and where it is rate-limited

- A **command capability** is a first-party governed command **type** that the tenant may submit through the command gateway (the universe is `ChatBotSpineCommandAllowlist.AllowedCommandTypes`). "Rate-limit a command capability" = record a per-`(tenant × command-type)` budget so its future submissions are throttled (fail closed transiently) once the trailing-window admitted count reaches the budget — distinct from the three existing allowlist-like concepts and from the 7.21/7.22 `Disabled`/`Quarantined` control states (same subject class, a *parameter* not a control state):
  - **`ChatBotSpineCommandAllowlist`**: a **global, static, all-tenant, code-level** fail-closed boundary checked in `CommandGateway.SubmitAsync` (reason `command_not_allowlisted`). **Never** tenant-mutable — do not touch it as the rate-limit mechanism (only append the one new governance command name).
  - **`ServiceClientGrant.AllowedCommandNames`** (Epic 5): a **per-grant** scope checked in `ServiceClientGrantValidator` for `service`/`ai` actors only (reason `service_client_grant_under_scoped`). Does not cover human submissions, so it is not the seam.
  - **The actor rate-limit planes** (`ServiceClientRateLimitConfigured`/`AiActorRateLimitConfigured`): rate-limit an **actor**, not a command type.
- The command flows through the gateway pipeline in this order: **(1) Authentication** → **(2) Tenant binding** → **(3) Authorization** (`ParticipantAuthorizationStage`: top-of-stage command-capability Disabled/Quarantined switch → `ServiceClientGrantValidator` → participant-authority + per-command admin-scope branches → **NEW final rate-limit gate**) → **(4) Spine allowlist** (in `CommandGateway`) → **(5) Risk** → **(6) Approval gate**. The command-capability rate-limit belongs at the **end of stage 3**, so it covers all actor types and only fires for otherwise-admissible commands. [Source: `src/Hexalith.ChatBot.Server/Gateway/CommandGateway.cs`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ParticipantAuthorizationStage.cs:65`]
