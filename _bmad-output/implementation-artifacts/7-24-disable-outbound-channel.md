# Story 7.24: Disable outbound channel

Status: done

<!-- Validation: create-story checklist applied 2026-06-03. -->

## Story

As an authorized **policy administrator** (a human admin holding the policy scope, under a two-person rule),
I want to disable an **outbound channel** for a tenant,
so that unsafe or policy-violating external communication cannot leave the project boundary — **every approved outbound send through that channel fails closed at the outbound send seam** — while **pending drafts and approvals remain inspectable** and every prior record stays intact and auditable, and safe recovery guidance is shown.

## Acceptance Criteria

1. Given an outbound channel producing unsafe or policy-violating activity, when an authorized **human policy admin** proposes a **disable** and a **second** authorized human policy admin approves it (FR75d two-person rule), then the outbound channel transitions to a durable **Disabled** governance control state and **future approved sends through that channel fail closed at the outbound send seam** (`AcceptedCommandDispatcher`'s `ExecuteApprovedOutboundDraft` branch) — **no external message is dispatched to the outbound adapter** — while **unrelated outbound channels and unrelated tenants continue normally** (isolation, NFR30/NFR18). The disable is a security-sensitive FR74 governance control — **not** the Epic 6 outbound draft/approval authority path — so it MUST go through the same submit→second-person-approve flow established for the Story 7.21 command-capability disable (`SubmitCommandCapabilityDisable`→`ApproveCommandCapabilityDisable`) and the Story 7.18/7.15/7.12 disable cells; a single-actor disable never takes effect. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.24`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75d`; `_bmad-output/implementation-artifacts/7-21-disable-command-capability.md`; `src/Hexalith.ChatBot.Server/Gateway/Stages/AcceptedCommandDispatcher.cs:643`]

2. Given the disable proposal and approval, when authorization runs, then the operation is permitted only for a **human policy administrator** — gate on **`AdminAuthorityEvaluator.HasHumanAdminScope(actor.Principal, AdminScope.Policy)`** (outbound-channel governance is a security-sensitive policy concern — the same scope that gates `SubmitTenantPolicyChange` and the Story 7.18–7.23 actor / command-capability controls; the epic's persona is "policy administrator"). There is **no** `AdminScope.Security`/`AdminRole.SecurityEngineer`. A `tenant-admin` still qualifies because `AdminScopes.ScopesForRole(TenantAdmin)` returns the full scope set (FR75a union) — so this is **not** a relaxation. The operation is **denied for service clients and AI actors** even when they carry admin-looking claims (the human-actor gate inside `HasHumanAdminScope`/`IsHumanActor`), and denied for non-policy human scopes (`mailbox-admin`/`compliance-admin`/`operations-admin`-only). The approving admin MUST be a **different person** from the proposer: both `RequesterRef != ApproverRef` (Ordinal safe-token compare) and `RequesterActorId != approver envelope UserId` are enforced — at the gateway validation stage, the accepted-command dispatcher, **and** re-checked in the aggregate, mirroring `IsValidCommandCapabilityDisableApproval`, `AcceptedCommandDispatcher`'s distinct-approver guard, and `GovernedOperationAggregate.Handle(ApproveCommandCapabilityDisable)`. 3. Given the disable is applied (approval committed), when it is recorded, then the operation records — with **no skip-audit path** (FR74, FR75g, NFR15a) — the **actor** (admin identity / actor type), **scope used** (`admin-scope:policy`), **subject** (the safe outbound-channel ref — e.g. `adapter:mailbox-outbound`), **reason** (documented justification reason code), **old state** (`Active`), **new state** (`Disabled`), **policy snapshot id**, and **timestamp**, via a metadata-only `AuditEnvelope` whose `StateTransition` is `"Active->Disabled"`. The audit is written through the existing fail-closed pre-commit seam (`IAuditWriter.RecordPreCommitAsync` via `CommandGateway`): when the pre-commit audit is unavailable, **no durable disable state is written and no send-blocking side effect occurs** (fail closed), reusing the `CommandGateway` audit-unavailable behavior. No admin role bypasses NFR15a/NFR50a. 4. Given an outbound channel is Disabled for a tenant, when an `ExecuteApprovedOutboundDraft` send targeting **that channel** (keyed by the safe channel ref `AdapterRef`) is dispatched for that tenant, then the **send fails closed at the outbound send seam before any external dispatch**: in `AcceptedCommandDispatcher`'s `ExecuteApprovedOutboundDraft` branch, the disabled-channel check runs **before `IOutboundMailboxSender.SendAsync`** (`AcceptedCommandDispatcher.cs:669`) and short-circuits the adapter — producing a fail-closed send-rejected outcome with the finite reason `outbound_channel_disabled` so **no message is sent to the outbound adapter and no external communication leaves the boundary**. This reuses the existing `AdapterStatus != "sent"` → `RejectOutboundSend(...)` path in `GovernedOperationAggregate.Handle(ExecuteApprovedOutboundDraft)` (`:1178`), so the blocked send is recorded as a rejected-send outcome rather than a silent drop. This is the **key divergence from the 7.12/7.15/7.18/7.21 cells**: the subject is an **outbound channel**, so enforcement lives at the **outbound send seam** (the dispatcher's `ExecuteApprovedOutboundDraft` branch, the only place the channel ref `AdapterRef` and the authenticated `TenantBinding` meet before the external adapter call) — **not** at the mailbox intake worker (7.12), the `ServiceClientGrantValidator` actor seam (7.15/7.18), or the actor-agnostic `ParticipantAuthorizationStage` admission gate (7.21). A send targeting any **other (still-Active)** channel for the same tenant, or the same channel for a **different** tenant, is unaffected (isolation). The new `outbound_channel_disabled` reason is **distinct from** `outbound_adapter_unavailable` (the adapter-not-configured/unreachable case), `adapter_not_approved_mode`, `command_capability_disabled`, and every actor-control reason (`service_client_disabled`, `ai_actor_disabled`, etc.). [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.24`; `src/Hexalith.ChatBot.Server/Gateway/Stages/AcceptedCommandDispatcher.cs:643`; `src/Hexalith.ChatBot.Server/Adapters/Mailbox/IOutboundMailboxSender.cs`; `src/Hexalith.ChatBot.Server/Operations/GovernedOperationAggregate.cs:1178`]

5. Given an outbound channel is disabled, when its prior and pending activity is inspected, then **all previously recorded outbound drafts, approval requests, approval decisions, send outcomes, audit envelopes, and conversation content remain visible, intact, and fully reconstructable**, and **pending drafts/approvals (created or awaiting approval) remain inspectable** — disable affects **only future sends**, never already-committed records (`OutboundDraftCreated`, `OutboundApprovalRequested`, `OutboundApprovalDecisionRecorded`, prior `OutboundSendSucceeded`) or their audit trails (NFR17 visible/recoverable states; FR75c admins cannot mutate project-level records). The disable does **not** block `CreateOutboundDraft`, `RequestOutboundSendApproval`, or `DecideOutboundApproval` (drafts and approvals stay inspectable) — it blocks **only the send/execute step** through the disabled channel. Disable is reversible by a future re-enable flow; this story does not delete or rewrite any prior record. ## Dev Notes

### Scope Boundaries

- Story 7.24 is the **thirteenth** cell of the FR74 enforcement series (7.12–7.26: five subject classes — mailbox / service-client / AI-actor / command-capability / **outbound** — × three actions — disable / quarantine / rate-limit) and the **first outbound-channel cell**. It implements exactly **one** cell: **outbound channel × disable**. Disable (this story) and quarantine (7.25) are **security-sensitive** admin operations gated by the **FR75d two-person rule**; rate-limit (7.26) is a standard policy mutation. **Do not** implement quarantine, rate-limit, any other subject class, a future re-enable/release flow, or the Story 7.27 command-allowlist-v1 / full-lifecycle work here. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`; `_bmad-output/planning-artifacts/epics.md#Story 7.27`]
- **This story is a structural mirror of Story 7.21 (disable command capability), retargeted from the command-type subject to the outbound-channel subject, with one major divergence (read this first):**
  1. **The enforcement seam is the outbound SEND seam, not an admission/intake seam.** "Disable" blocks **future sends through that channel**. The only place the channel ref (`AdapterRef`) and the authenticated `TenantBinding` meet immediately before the external adapter call is `AcceptedCommandDispatcher`'s `ExecuteApprovedOutboundDraft` branch (`:643`), where `IOutboundMailboxSender.SendAsync` is invoked (`:669`). Place the disabled-channel check **after** validation + authority `Classify` and **before** `SendAsync`, short-circuiting the adapter so **no external message is dispatched** and the existing `AdapterStatus != "sent"` → `RejectOutboundSend(...)` aggregate path (`:1178`) records the block. **Rejected alternatives:** the mailbox intake worker (inbound — wrong direction, that is 7.12), `ServiceClientGrantValidator` (per-actor, misses human sends — 7.15/7.18), or a `ParticipantAuthorizationStage` admission gate (the channel ref is in the command body and the dispatcher already deserializes it; keeping the block adjacent to the adapter call makes "no external send" provably local).
- **The subject is an outbound channel, not an actor or command type.** The channel is identified by its safe `AdapterRef` (`adapter:mailbox-outbound` — the M365 mailbox outbound channel, the only channel in M0/M1). Unlike 7.21 there is **no self-lockout guard** (the subject is not a governance command type, so disabling it cannot lock out governance). The disable blocks **only the send/execute step**; `CreateOutboundDraft`/`RequestOutboundSendApproval`/`DecideOutboundApproval` stay admissible so pending drafts/approvals remain inspectable (AC5).
- **Authorization scope = policy-admin** (same as 7.18–7.23). There is **no** `AdminScope.Security`/`AdminRole.SecurityEngineer`; the epic's "policy administrator" persona maps to the security-sensitive **policy** scope. Gate on **`HasHumanAdminScope(actor.Principal, AdminScope.Policy)`**. A `tenant-admin` still passes via the FR75a scope union — **not** a relaxation. Two-person: submit→second-person-approve; a single-actor disable only ever produces a pending approval. Distinct approver enforced **three times** (gateway validator, accepted-command dispatcher, aggregate re-check), `RequesterRef != ApproverRef` Ordinal AND `RequesterActorId != envelope.UserId`. **Rejected:** a new `AdminScope.Security` (scope-creep) and `HasHumanTenantAdmin` (too coarse).
- The disable affects **future sends only**. It must never delete, rewrite, or hide already-committed drafts, approval requests/decisions, send outcomes, conversation content, or their audit trails (NFR17, FR75c). It is reversible by a future re-enable flow (out of scope here).
- Tenant identity is always from the **authenticated gateway binding**, never the command body. The subject (channel ref) and all audit refs are **metadata-only, safe tokens** (NFR2); recipient/sender addresses, message content, credentials, OAuth grant fingerprints, model prompts/completions, and delegated-user PII never appear (NFR4/NFR5).

### What "outbound channel" means here, and where it is blocked

- An **outbound channel** is the governed external-send path through which an approved outbound draft leaves the project boundary. In M0/M1 the single outbound channel is the **M365 mailbox outbound adapter**, identified by the safe `AdapterRef` token `adapter:mailbox-outbound` (set on `ExecuteApprovedOutboundDraft.AdapterRef` and `OutboundMailboxSendResult.AdapterRef`). "Disable an outbound channel" = mark that channel **Disabled for the tenant** so its future sends fail closed — distinct from the Epic 6 **authority** controls:
  - **`SenderAuthorityClass` / `OutboundSendAuthorityEvaluator`** (Epic 6): governs *who/what may send* (draft-only vs send posture, M365 mapping) — checked per-send in the dispatcher (`AcceptedCommandDispatcher.cs:657`). Not a channel on/off switch.
  - **`OutboundDraftAuthorityEvaluator`** (Epic 6): governs *who may draft*. Disabling a channel must **not** touch drafting.
  - **`ChatBotSpineCommandAllowlist`**: a global, static, code-level fail-closed boundary — never tenant-mutable; only append the two new governance command names.
- The outbound flow is a four-step governed pipeline: **(1) `CreateOutboundDraft`** → **(2) `RequestOutboundSendApproval`** → **(3) `DecideOutboundApproval`** → **(4) `ExecuteApprovedOutboundDraft`** (the send, where `IOutboundMailboxSender.SendAsync` performs the external dispatch via the `AcceptedCommandDispatcher`). The outbound-channel disable belongs at **step 4, before `SendAsync`**, so it blocks the external send while steps 1–3 (drafts/approvals) stay inspectable. [Source: `src/Hexalith.ChatBot.Server/Gateway/Stages/AcceptedCommandDispatcher.cs:597–692`; `src/Hexalith.ChatBot.Server/Operations/GovernedOperationAggregate.cs:960–1230`]

### Completion Notes List

Story 7.24 is a structural mirror of Story 7.21 (disable command capability, commit `c79da68`), retargeted from the command-type subject to the outbound-channel subject, with the **outbound send-seam enforcement** as the one major divergence. Variances decided (all as recommended in Dev Notes):

1. **Dedicated `OutboundChannelControlState { Active, Disabled }` enum** (`Contracts/Enums/`), append-only ordering so Story 7.25 can append `Quarantined`. It is a dedicated outbound-channel control plane — distinct from the Epic 6 outbound **authority** path (`SenderAuthorityClass`/`OutboundSendAuthorityEvaluator`/`OutboundDraftAuthorityEvaluator`), which governs *who may draft/send* — not *whether a channel is open*. **Rejected:** (a) overloading a `SenderAuthorityClass` value (bypasses two-person, conflates authority with channel state); (b) mutating the static `ChatBotSpineCommandAllowlist` per-tenant (global, code-level, never-mutable boundary).
2. **Subject-specific `SubmitOutboundChannelDisable`/`ApproveOutboundChannelDisable`** command pair (+ `OutboundChannelControlSchemaVersions.V1 = "outbound-channel-control-schema.v1"`).
3. **Authorization scope = `HasHumanAdminScope(AdminScope.Policy)`** — there is no `AdminScope.Security`; the "policy administrator" persona maps to the Policy scope. A tenant-admin still passes via the FR75a scope union (not a relaxation); service/AI actors denied via the human-actor gate. Distinct approver enforced **three times** (gateway validator, accepted-command dispatcher, aggregate re-check): `RequesterRef != ApproverRef` (Ordinal) AND `RequesterActorId != envelope.UserId`.
4. **Send-seam enforcement (the key divergence from 7.12/7.15/7.18/7.21):** the disabled-channel check lives in `AcceptedCommandDispatcher`'s `ExecuteApprovedOutboundDraft` branch, **after** trusted-metadata validation + authority `Classify` and **before** `IOutboundMailboxSender.SendAsync`. When the channel is `Disabled`, the adapter call is skipped entirely and the send is marked `AdapterStatus = "blocked"`, so the aggregate's existing `AdapterStatus != "sent"` → `RejectOutboundSend(...)` path records a fail-closed rejected-send outcome — no external message is dispatched. The aggregate maps `"blocked"` → the finite `outbound_channel_disabled` reason, **distinct from** `outbound_adapter_unavailable`/`adapter_not_approved_mode`/`command_capability_disabled`/actor-control reasons. **Placement rationale:** the dispatcher's `ExecuteApprovedOutboundDraft` branch is the only seam where the channel ref (`AdapterRef`) and the authenticated `TenantBinding` both exist immediately before the external adapter call. **Rejected:** the mailbox intake worker (inbound — 7.12), `ServiceClientGrantValidator` (per-actor — 7.15/7.18), the `ParticipantAuthorizationStage` admission gate (channel ref is in the command body; keep the block adjacent to the adapter call so "no external send" is provably local).
5. **Subject ref = the safe channel `AdapterRef`** (`adapter:mailbox-outbound`), validated via `AuditMetadata.IsSafeStableIdentifier`. **No self-lockout guard / `Fr74GovernanceCommandTypes` membership check** (the divergence from 7.21) — the subject is a channel, not a governance command type, so disabling it cannot lock out governance.
