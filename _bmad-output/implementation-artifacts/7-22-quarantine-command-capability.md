# Story 7.22: Quarantine command capability

Status: done

<!-- Validation: create-story checklist applied 2026-06-03. -->

## Story

As an authorized **security engineer** (a human admin holding the policy scope, under a two-person rule),
I want to quarantine a suspicious **command capability** for a tenant,
so that suspicious command execution is paused for investigation — **every actor's attempt to submit that command type (human, service client, or AI actor) is blocked or routed to manual review and fails closed at the command-admission pipeline with safe next-action guidance**, the allowlist version in effect is preserved in audit, and every prior execution and audit record stays intact and reconstructable — until the quarantine is cleared.

## Acceptance Criteria

1. Given a command capability under investigation, when an authorized **human policy admin** (the "security engineer" persona) proposes a **quarantine** and a **second** authorized human policy admin approves it (FR75d two-person rule), then the command capability transitions to a durable **Quarantined** governance control state and **future submissions of that command type are blocked / routed to manual review and fail closed** at the command-admission pipeline for the tenant (they cannot execute until quarantine is cleared), while **unrelated command capabilities and unrelated tenants continue normally** (isolation, NFR30). The quarantine is a security-sensitive FR74 governance control — **not** a tenant-policy knob and **not** the static `ChatBotSpineCommandAllowlist` (a global, code-level fail-closed allowlist, never tenant-mutable) — so it MUST go through the same submit→second-person-approve flow established for the Story 7.21 command-capability disable (`SubmitCommandCapabilityDisable`→`ApproveCommandCapabilityDisable`) and the Story 7.19 AI-actor quarantine (`SubmitAiActorQuarantine`→`ApproveAiActorQuarantine`); a single-actor quarantine never takes effect. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.22`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75d`; `_bmad-output/implementation-artifacts/7-21-disable-command-capability.md`; `_bmad-output/implementation-artifacts/7-19-quarantine-ai-actor.md`; `src/Hexalith.ChatBot.Server/Operations/GovernedOperationAggregate.cs:399`]

2. Given the quarantine proposal and approval, when authorization runs, then the operation is permitted only for a **human policy administrator** — gate on **`AdminAuthorityEvaluator.HasHumanAdminScope(actor.Principal, AdminScope.Policy)`**. There is **no dedicated `AdminScope.Security`/`AdminRole.SecurityEngineer`** in the model; the epic's "security engineer" persona maps to the **policy** scope (command-capability / command-allowlist governance is a security-sensitive policy concern — the same scope that gates `SubmitTenantPolicyChange`, the AI-actor controls 7.18–7.20, and the Story 7.21 command-capability disable). A `tenant-admin` still qualifies because `AdminScopes.ScopesForRole(TenantAdmin)` returns the full scope set (FR75a union) — so this is **not** a relaxation. The operation is **denied for service clients and AI actors** even when they carry admin-looking claims (the human-actor gate inside `HasHumanAdminScope`/`IsHumanActor`), and denied for non-policy human scopes (`mailbox-admin`/`compliance-admin`/`operations-admin`-only). The approving admin MUST be a **different person** from the proposer: both `RequesterRef != ApproverRef` (Ordinal safe-token compare) and `RequesterActorId != approver envelope UserId` are enforced — at the gateway validation stage, the accepted-command dispatcher, **and** re-checked in the aggregate, mirroring `IsValidCommandCapabilityDisableApproval`, `AcceptedCommandDispatcher`'s distinct-approver guard, and `GovernedOperationAggregate.Handle(ApproveCommandCapabilityDisable)`. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.22`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75a`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75d`; `src/Hexalith.ChatBot.Server/Governance/Admin/AdminAuthorityEvaluator.cs:10`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ParticipantAuthorizationStage.cs:200`]

3. Given the quarantine is applied (approval committed), when it is recorded, then the operation records — with **no skip-audit path** (FR74, FR75g, NFR15a) — the **actor** (approver identity / actor type), **scope used** (`admin-scope:policy`), **subject** (the safe command-capability ref — the quarantined command type name), **reason** (documented justification reason code), **old state** (`Active`), **new state** (`Quarantined`), **policy snapshot id** (the allowlist version in effect — preserved per the epic AC), and **timestamp**, via a metadata-only `AuditEnvelope` whose `StateTransition` is `"Active->Quarantined"`. The audit is written through the existing fail-closed pre-commit seam (`IAuditWriter.RecordPreCommitAsync` via `CommandGateway`): when the pre-commit audit is unavailable, **no durable quarantine state is written and no admission-blocking side effect occurs** (fail closed), reusing the disable/`CommandGateway` audit-unavailable behavior. No admin role bypasses NFR15a/NFR50a. [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.22`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75g`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR15a`; `src/Hexalith.ChatBot.Server/Audit/AuditEnvelopeFactory.cs:1555`; `src/Hexalith.ChatBot.Server/Gateway/CommandGateway.cs`]

4. Given a command capability is Quarantined for a tenant, when **any actor** (human, service client, or AI actor) submits a command **of that quarantined type** for that tenant, then the authorization stage **fails closed before admission**: `ParticipantAuthorizationStage.AuthorizeAsync` returns `ChatBotAuthorizationResult.Denied("command_capability_quarantined")` for the quarantined command type, **before** the service-client grant validation, the per-command admin-scope checks, and the downstream spine-allowlist / risk / approval gates — so no command of the quarantined type is admitted and no restricted work is performed. As in Story 7.21, this is the **key divergence from the actor-subject cells (7.13/7.16/7.19)**: the subject is a **command type**, not an actor or a worker source, so enforcement must cover **all actor types** and therefore lives in the **actor-agnostic authorization stage** (`ParticipantAuthorizationStage`, which runs for every actor and has both the command type and the authenticated tenant binding) — **not** in `ServiceClientGrantValidator` (which only runs for `service`/`ai` actors and would miss human submissions) and **not** in a worker. The new `command_capability_quarantined` check sits **beside** the Story 7.21 `command_capability_disabled` check at the top of `AuthorizeAsync`, reading the same `ICommandCapabilityControlStateProvider` (which returns a single `CommandCapabilityControlState` — `Quarantined` is just a new possible value, **no provider signature change**). A submission of any **other (still-Active)** command type for the same tenant, or the same command type for a **different** tenant, is unaffected (isolation). The new `command_capability_quarantined` reason is **distinct from** `command_capability_disabled` (same command-capability governance family, different control state), `command_not_allowlisted` (the global static spine-allowlist refusal), `service_client_grant_under_scoped` (the per-grant allowlist), and every actor-control reason (`ai_actor_quarantined`, `service_client_quarantined`, etc.). [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.22`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ParticipantAuthorizationStage.cs:85`; `src/Hexalith.ChatBot.Server/Gateway/ChatBotAuthorizationReasonCodes.cs:76`; `src/Hexalith.ChatBot.Server/Gateway/ChatBotSpineCommandAllowlist.cs`]

5. Given a command capability is quarantined, when its prior activity is inspected, then **all previously recorded commands, events, audit envelopes, proposals, associations, files, approvals, conversation content, and workflow items that originated from that command type remain visible, intact, and fully reconstructable** — quarantine affects **only future admission**, never already-committed records or their audit trails (NFR17 visible/recoverable states; FR75c admins cannot mutate project-level records). Quarantine is reversible by a future release/re-activate flow; this story does not delete or rewrite any prior record. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR17`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75c`; `_bmad-output/implementation-artifacts/7-21-disable-command-capability.md`]

6. Given an actor encounters a quarantined command capability (admin viewing status, or an admission blocked / routed to review), when guidance is surfaced, then **safe recovery guidance** is shown from the **finite message catalog** — a safe headline (≤ 80 chars), a one-line reason from a finite set conveying "contained for review", a next-action pointing to the responsible role (review/release is a policy-admin/two-person action), and a `disabled-action` reason — using `ChatBotMessageCatalog` / `ChatBotMessageCodes` / `ChatBotDisabledActionReasons`, never raw error text. The guidance conveys that the command is paused while evidence is reviewed and never names an unauthorized project/file/party/mailbox-content/audit detail (NFR2); EN/FR via existing localization; stable machine tokens (reason codes, state tokens, correlation ids, command type names) stay untranslated. ### Scope Boundaries

- Story 7.22 is the **eleventh** cell of the FR74 enforcement series (7.12–7.26: five subject classes — mailbox / service-client / AI-actor / **command-capability** / outbound — × three actions — disable / quarantine / rate-limit) and the **second command-capability cell**. - **This story is the Story 7.21 command-capability disable cell with `Quarantine`/`Quarantined` substituted for `Disable`/`Disabled` — i.e. it applies the 7.19 disable→quarantine substitution to the command-capability row that 7.21 built.** Read 7.21 and 7.19 first. There are **two** things to carry forward together:
  1. **The actor-agnostic enforcement seam (the command-capability divergence, from 7.21).** "Quarantine" blocks a command capability from admitted execution **for every actor of a tenant** (human, service client, AI actor). So the enforcement seam is the **actor-agnostic `ParticipantAuthorizationStage.AuthorizeAsync`**, which runs for **all** actor types and has both `submission.Request.CommandType` and the authenticated `tenantBinding` — **not** `ServiceClientGrantValidator` (it runs only for `service`/`ai` actors; a human submission of the quarantined command would slip through). The new `Quarantined` check sits **beside** the 7.21 `Disabled` check at the **top** of `AuthorizeAsync` (after the guards, before the grant-validator call), reading the same `ICommandCapabilityControlStateProvider`. **Rejected alternatives:** a `ServiceClientGrantValidator` branch (misses humans), per-tenant mutation of the static `ChatBotSpineCommandAllowlist`, or a worker check.
  2. **Quarantine ≈ Disable at the command-capability admission seam — the one meaningful semantic difference** (the 7.16/7.19 lesson). "New executions are blocked or routed to manual review and cannot execute" = future submissions of that command type **fail closed before admission** at `ParticipantAuthorizationStage`, with a **distinct reason code, state token, lifecycle transition, and safe next-action guidance** (`quarantined` / "contained for review" vs `disabled` / "blocked until re-enabled"). There is **no** intake-routing branch and **no** worker change.
- **Authorization scope = policy-admin** (same as 7.21). There is **no** `AdminScope.Security` / `AdminRole.SecurityEngineer`; the epic's "security engineer" persona maps to the security-sensitive **policy** scope. Gate on **`HasHumanAdminScope(actor.Principal, AdminScope.Policy)`**. A `tenant-admin` still passes via the FR75a scope union — **not** a relaxation. **Rejected alternatives:** a new `AdminScope.Security` (scope-creep) and `HasHumanTenantAdmin` (too coarse).
- **Same as 7.21 (preserve the two-person machinery):** submit→second-person-approve; a single-actor quarantine only ever produces a pending approval. Distinct approver enforced **three times** (gateway validator, accepted-command dispatcher, aggregate re-check), `RequesterRef != ApproverRef` Ordinal AND `RequesterActorId != envelope.UserId`. Control state via the fixed FR74 path, never a tenant knob or the static spine allowlist. Terminal catalog guidance (`request-access` + `disabled-action`), not transient.
- **Self-lockout guard (carried from 7.21, extended):** because the subject is a command type, an admin could in principle quarantine the FR74 governance commands themselves and lock the tenant out of governing/reversing. Guard both ways: (a) the gateway validator **rejects** a propose whose `CommandCapabilityRef` is in `Fr74GovernanceCommandTypes`; and (b) the enforcement seam **exempts** the FR74 governance commands. **Add the two new quarantine command names to `Fr74GovernanceCommandTypes`** so they join the disable commands in that finite set.

### What "command capability" means here, and where it is blocked

- A **command capability** is a first-party governed command **type** that the tenant may submit through the command gateway (the universe is the `ChatBotSpineCommandAllowlist.AllowedCommandTypes`). "Quarantine a command capability" = mark that command type **Quarantined for the tenant** so its future submissions fail closed / are held for review — distinct from the three existing allowlist-like concepts and from the 7.21 `Disabled` state (same control plane, different control-state value):
  - **`ChatBotSpineCommandAllowlist`**: a **global, static, all-tenant, code-level** fail-closed boundary checked in `CommandGateway.SubmitAsync` (reason `command_not_allowlisted`). **Never** tenant-mutable — do not touch it as the quarantine mechanism. The "allowlist version" the epic AC asks to preserve in audit is captured via the `policy-snapshot:<id>` ref, not by mutating the allowlist.
  - **`ServiceClientGrant.AllowedCommandNames`** (Epic 5): a **per-grant** scope checked in `ServiceClientGrantValidator` for `service`/`ai` actors only (reason `service_client_grant_under_scoped`). Does not cover human submissions, so it is not the seam.
  - **The actor control planes** (`ServiceClientControlState`/`AiActorControlState`): quarantine an **actor**, not a command type.
- The command flows through the gateway pipeline in this order (per `CommandGatewayServiceCollectionExtensions` + `CommandGateway.SubmitAsync`): **(1) Authentication** → **(2) Tenant binding** → **(3) Authorization** (`ParticipantAuthorizationStage`, which first calls `ServiceClientGrantValidator`) → **(4) Spine allowlist** (in `CommandGateway`) → **(5) Risk** → **(6) Approval gate**. The quarantined-capability check belongs at the **start of stage 3** (before the grant validator and the per-command admin-scope branches), so it covers all actor types and fails closed before any downstream work.
