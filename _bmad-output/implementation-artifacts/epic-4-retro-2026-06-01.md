## What Went Well

- The team kept the AI mediation work inside the existing contract/client/server/gateway/projection/UI pattern instead of creating a side channel for model or tool behavior.
- Risk classification became deterministic and testable. Reviews hardened it against caller-supplied metadata spoofing and unknown action-class values.
- Low-risk execution was conservative. Provider invocation happens only after policy and project authorization; policy-false and unavailable policy states route to approval without a provider call.
- Approval work became durable and visible. The S3 surface, approval events, DAPR projection endpoints, project-conversation rows, generated client, and tests now share the same AI approval metadata.
- Refusal and safe-block behavior reused the versioned message catalog and existing blocked-state UI, preserving localization, metadata-only display, and cross-surface rejection parity.
- Correction invalidation closed a critical safety gap: approvals and executions now fail closed when the source association context has been superseded.

## Challenges

- Gateway-stage trust boundaries were easy to get subtly wrong. Story 4.3 needed fixes so unknown commands could not spoof low-risk metadata and unknown action classes returned safe `approval-required` output.
- Low-risk execution had several hidden gates. Story 4.4 review fixed missing project authorization, policy-false durability, idempotency composition, safe-next-action validation, and projection risk metadata.
- Runtime projection wiring repeatedly needed explicit verification. Stories 4.5 and 4.7 both had direct translator coverage before review found missing durable domain-event endpoint wiring.
- The `Project.AppendConversationMessage` M0 command semantics required precision. The implementation now prepares metadata-only append results before EventStore submission rather than implying a pre-persistence sibling-context mutation.
- Preview unavailable states needed exact token handling. Story 4.6 fixed `not-yet-produced` so generated content did not render as available.
- Traceability hygiene remained noisy. Several reviews fixed story File Lists and test-summary references after code and validation artifacts changed.
- The local validation constraint remains: `dotnet test` through VSTest can fail in this sandbox with a socket permission error, so compiled xUnit v3 runners remain the reliable validation path.

## Key Insights

1. Governed AI mediation is not a chat feature; it is a command-admission workflow with evidence, policy, approval, audit, projection, and refusal semantics.
2. Server-owned metadata is the trust boundary. Caller-supplied command, risk, allowlist, and action-class metadata must be treated as untrusted until validated against server-side providers.
3. Low-risk does not mean ungoverned. Low-risk execution still needs project authorization, current context-package metadata, policy snapshot evidence, idempotency, audit, and projection.
4. Runtime projection endpoints need the same review weight as aggregate and translator tests. If DAPR/EventStore events are not mapped and registered, the UI can miss real durable outcomes.
5. Safe preview states are security states. `not-yet-produced`, unavailable, blocked, redacted, and allowed are not interchangeable UI labels.
6. Correction propagation must invalidate downstream AI proposals by construction; approval and execution cannot rely on stale context-package claims.

## Significant Discoveries

- Epic 4 replaced the original risk/approval stubs with concrete registered gateway stages: `DeterministicAiActionRiskClassifier` and `AiActionApprovalGate`.
- The M0 approved-execution path has two allowlists: the ChatBot spine allowlist admits typed ChatBot commands, while `ApprovedAiActionCommandAllowlist` constrains approved AI execution to `Project.AppendConversationMessage` under `ai-action-command-allowlist.m0`.
- The current conversation writer is metadata-only. It prepares append results for the approved execution payload before EventStore submission; it is not yet a durable sibling `Hexalith.Conversations` write binding.
- Projection endpoint registration is a recurring risk area and should remain a review checklist item for EventStore/DAPR materialization stories.
- Story 4.9 proved that correction invalidation must be enforced at proposal, approval, execution, projection, and UI layers, not just as a display warning.
