# Story 7.14: Rate-limit mailbox source

Status: done

<!-- Validation: create-story checklist applied 2026-06-02. -->

## Story

As an authorized mailbox administrator,
I want to rate-limit a noisy mailbox source through a single-actor, schema-bounded policy mutation,
so that backlog from one source does not starve other workflow items — mailbox processing applies the bounded per-window limit, defers (never drops) intake that exceeds it, exposes queue-impact metrics, and protects unrelated tenants/sources from degradation where isolation is possible.

## Acceptance Criteria

1. Given a mailbox source exceeding policy thresholds, when an authorized **human mailbox-admin** (or **tenant-admin** union) configures a rate limit, then a durable per-source rate-limit budget is recorded and **mailbox processing applies the bounded limit** to that source's intake. This is a **standard, single-actor policy mutation** — explicitly **NOT** the Story 7.12/7.13 FR75d two-person control: FR74's decomposition guidance states "disable and quarantine are security-sensitive admin operations (per FR75d two-person rule); **rate-limit is a standard policy mutation**." So the command follows the **single-actor** `SubmitMailboxConfigurationChange` authorization shape (one `AdminAuthorityEvaluator.HasHumanAdminScope(principal, AdminScope.Mailbox)` check), **not** the submit→second-person-approve flow; there is **no** `Approve…` counterpart, **no** distinct-approver guard, and **no** `MailboxSourceControlState`/lifecycle transition (rate-limit is a *parameter*, not a control state). [Source: `_bmad-output/planning-artifacts/epics.md#Story 7.14`; `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`; `src/Hexalith.ChatBot.Server/Gateway/Stages/ParticipantAuthorizationStage.cs:97`; `_bmad-output/implementation-artifacts/7-13-quarantine-mailbox-source.md`]

2. Given the rate-limit value, when it is validated, then it is **bounded by the Tenant Policy Schema** (FR75): the configured per-window message budget is accepted only within a declared, closed, non-negative min/max range, and an out-of-range / wrong-type / undeclared value is **rejected with a safe reason code** (and, at the enforcement seam, falls back to safe defaults — never silently raises the cap). Mirror the closed `NotificationThrottleCeilings` bounds discipline from Story 7.9 (`Minimum`/`Maximum`/`SafeDefaults`/`IsWithinBounds`) — a tenant cannot introduce a new window dimension or a custom formula. The bound is a Standard (non-security-sensitive) knob, so no two-person rule applies. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR75`; `src/Hexalith.ChatBot.Contracts/Commands/NotificationThrottleCeilings.cs:16`; `src/Hexalith.ChatBot.Server/Notifications/NotificationThrottleEvaluator.cs:46`]

3. Given authorization runs, when the command is evaluated, then it is permitted only for a **human** holding the **mailbox-admin** (or **tenant-admin** union) admin scope and is **denied for service clients and AI actors** even when they carry tenant-admin-looking claims — exactly as `AdminAuthorityEvaluator.HasHumanAdminScope(principal, AdminScope.Mailbox)` already gates `SubmitMailboxConfigurationChange`/`SubmitMailboxSourceDisable`. There is **no** second-person/distinct-approver requirement for rate-limit; a single authorized human mailbox-admin applies it. Denial uses `ChatBotAuthorizationReasonCodes.AuthorizationDenied`, kept indistinguishable from safe-not-found where required. 4. Given the rate limit is applied (committed), when it is recorded, then the operation records — with **no skip-audit path** (FR74, FR75g, NFR15a) — the **actor** (requester identity / actor type), **scope used** (`admin-scope:mailbox`), **subject** (the safe mailbox-source ref), **reason** (documented justification reason code), **old state** (the prior budget / `unlimited`), **new state** (the new bounded budget), **policy snapshot id**, and **timestamp**, via the metadata-only `AuditEnvelope`. The audit is written through the existing fail-closed pre-commit seam (`IAuditWriter.RecordPreCommitAsync` via `CommandGateway`): when the pre-commit audit is unavailable, **no durable rate-limit state is written and no enforcement side effect occurs** (fail closed), reusing the disable/`CommandGateway` audit-unavailable behavior. The `tenant-admin` role does **not** bypass NFR15a/NFR50a. 5. Given a mailbox source has a rate-limit budget configured, when a Graph mailbox notification arrives and the source's recent intake count in the trailing rolling window has reached the budget, then `GraphMailboxIntakeWorker.ProcessAsync` **defers** intake — returning `MailboxIntakeWorkerResult.Recoverable("mailbox_source_rate_limited")` **before** any Graph fetch or `CaptureMailboxMessageIntake` submission — so **no restricted content is fetched for a deferred message** and the message is **queued for automatic retry-later, never dropped** (`NextRetryAt` set, `SafeNextAction == "retry-later"`, owner role `mailbox-operator`). The trailing-window count is computed with the established clock-injected window math (`NotificationThrottleEvaluator.CountInTrailingWindow` discipline: server-measured UTC age, never client/item-supplied time). When the source is **under** budget the notification processes normally (fetch + capture). This check sits **after** the disable/quarantine control-state blocks and applies only to an `Active` source. Rate-limiting **protects unrelated tenants/sources from degradation where isolation is possible** (NFR30, NFR18): each mailbox source's budget and trailing-window counter are **independent**, so deferring a noisy source never throttles or starves a sibling source or another tenant. Full operational-dashboard wiring is Epic 8 and is out of scope here — this story exposes the metric at the audit/observable seam only. ## Dev Notes

### Scope Boundaries

- Story 7.14 is the **third** cell of the FR74 enforcement series (7.12–7.26: five subject classes — mailbox / service-client / AI-actor / command-capability / outbound — × three actions — disable / quarantine / rate-limit). It implements exactly **one** cell: **mailbox source × rate-limit**. Disable (7.12) and quarantine (7.13) are **security-sensitive** admin operations gated by the **FR75d two-person rule**; **rate-limit (this story) is a standard, single-actor policy mutation** bounded by the Tenant Policy Schema. **Do not** implement any other subject class, the disable/quarantine actions, or a future rate-limit-release/reset flow here. [Source: `_bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#FR74`]
- **The three meaningful divergences from the 7.12/7.13 template — read these first:**
  1. **Single-actor, not two-person.** No `Approve…` command, no pending-approval event/dictionary, no `AcceptedCommandDispatcher` distinct-approver guard, no aggregate distinct-approver re-check. One `HasHumanAdminScope(…, AdminScope.Mailbox)` gateway check (mirror `SubmitMailboxConfigurationChange`, ParticipantAuthorizationStage:97), plus a single direct-activation aggregate handler (mirror the non-sensitive `SubmitTenantPolicyChange` immediate-activation path).
  2. **Not a control state / not a lifecycle transition.** Rate-limit is a *bounded parameter*, so **do not** add to `MailboxSourceControlState`, `LifecycleStates`, `LifecycleTransitionValidator`, or `CommandSubmissionLifecycleTransitionGuard`. "Old state"/"new state" in the audit = old budget / new budget, not `Active→X`.
  3. **Deferred (retryable), not blocked (await-admin).** The worker outcome is `Recoverable("mailbox_source_rate_limited")` on the **retryable** path (`NextRetryAt` set, `retry-later`, owner `mailbox-operator`) — intake is queued for automatic retry, never dropped or escalated-to-admin. Disable/quarantine return the non-retryable await-admin path. The catalog entry uses `retry-later` + `dependency-degraded`, not `request-access` + `disabled-action`.
- **Bounded by the Tenant Policy Schema (FR75).** The budget value is accepted only within a declared closed range. Reuse the `NotificationThrottleCeilings` bounds discipline (Story 7.9): `Minimum`/`Maximum`/`SafeDefaults`/`IsWithinBounds`, out-of-bounds → safe default, never raise the cap. A tenant cannot add a new window dimension or a custom formula.
- **Isolation (NFR30/NFR18).** Each mailbox source has an independent budget + trailing-window counter. Deferring a noisy source must never throttle a sibling source or another tenant. Tenant identity is always from the **authenticated gateway binding**, never the command body. The subject and all audit refs are **metadata-only, safe tokens** (NFR2).
