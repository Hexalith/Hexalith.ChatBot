# Story 1.9: First Governed Command End-to-End with Surface-Origin Attribution

Status: done

<!-- Validation completed against .agents/skills/bmad-create-story/checklist.md on 2026-05-30. -->

## Story

As a product owner,
I want one trivial allowlisted command to execute end-to-end through the full CommandGateway from the UI, with its surface origin attributed and immutable,
so that the walking skeleton is provably complete — the safety floor (tenant isolation, authorization, fail-closed audit, idempotency) is real, not stubbed — before feature work begins.

## Acceptance Criteria

1. Given a minimal UI core-operations shell (FR81), when a signed-in user submits the one trivial governed command, then the command flows through the full spine in order — `auth → tenant-bind → authorize → risk-classify → approval-gate → coarse-idempotency → pre-commit-audit → [EventStore: fine-idempotency → execute → publish → projection] → post-commit-audit` — the resulting durable state is written through EventStore (a domain event persisted then published to `chatbot.events` and projected to `chatbot-statestore`), and the operation outcome is visible in the UI together with its audit history (metadata-only). [Source: _bmad-output/planning-artifacts/epics.md#Story 1.9; Source: _bmad-output/planning-artifacts/architecture.md#Process Patterns; Source: _bmad-output/planning-artifacts/architecture.md#API & Communication Patterns]
2. Given the adapter boundary, when the command is constructed, then its surface origin (`ui` for the UI shell, `api` for a direct REST caller) is attached at that boundary, travels with the `ChatBotCommandSubmission` / Command record into the audit envelope, and cannot be read or mutated differently by any downstream pipeline stage; a submission with a missing/unknown origin defaults to a safe value and is still audited, never trusted from an arbitrary downstream rewrite (FR85, S7). [Source: _bmad-output/planning-artifacts/epics.md#Story 1.9; Source: _bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#S7; Source: _bmad-output/planning-artifacts/architecture.md#Communication Patterns]
3. Given the M0 surface scope, when the command executes, then tenant partitioning, fail-closed behavior, the two-phase audit, and coarse + fine idempotency are REAL (not stubbed) — `tenantId` is bound from authenticated Keycloak claims only, a state write that cannot complete the pre-commit audit returns a typed rejection and writes no durable state — even though `risk-classify` and `approval-gate` remain pass-through stubs whose results are recorded but not yet enforced. [Source: _bmad-output/planning-artifacts/epics.md#Story 1.9; Source: _bmad-output/planning-artifacts/architecture.md#Process Patterns; Source: _bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/prd.md#NFR15a]
4. Given the gateway's allowlist guardrail, when a command that is not on the M0 spine allowlist is submitted, then it is rejected fail-closed with a catalog-backed, redacted problem response and writes no durable state, while the single allowlisted trivial command is admitted — proving the allowlist stage is enforced mechanically, not decoratively. [Source: _bmad-output/planning-artifacts/architecture.md#Process Patterns; Source: _bmad-output/planning-artifacts/prds/prd-Hexalith.ChatBot-2026-05-28/addendum.md#Command Allowlist v0]
5. Given the M0 vertical loop, when a Tier 3 Aspire E2E test exercises the command end-to-end through the real DAPR topology (ChatBot + sidecars + EventStore + Keycloak, `WaitFor` healthy), then it inspects the actual `chatbot-statestore` end-state (the projected read model) and the audit envelope fields — not just an HTTP 202 — and asserts origin attribution, tenant partitioning, idempotent replay (one durable effect for a repeated submission), and never-false-Done. [Source: _bmad-output/planning-artifacts/epics.md#Story 1.9; Source: _bmad-output/planning-artifacts/architecture.md#Enforcement Guidelines]

## Dev Notes

### Implementation Intent

Story 1.9 is the **value proof of Epic 1**: everything stories 1.1–1.8 built (buildable module, contract spine + typed client + `IChatBotCommand`, the `auth→tenant-bind→authorize` admission stages, the fail-closed audit-commit seam, two-altitude idempotency, lifecycle transitions, message catalog + redaction, correlation + operation status) is wired into **one trivial command that actually mutates durable state through EventStore and is visible in a UI with its audit trail**. After this story, the spine is provably end-to-end and feature epics (2–4) build on a real walking skeleton. [Source: _bmad-output/planning-artifacts/epics.md#Epic 1; architecture.md#Decision Impact Analysis]

Two concrete gaps make this story non-trivial despite the "trivial command":

1. **The dispatcher is a stub.** `AcceptedCommandDispatcher.DispatchAsync` currently returns `new ChatBotDispatchResult(clock.UtcNow)` and nothing else — no aggregate, no event, no projection. The entire `[EventStore: execute → publish → projection]` segment of the spine does not exist yet for ChatBot. Story 1.9 makes it real behind the existing `ICommandDispatcher` seam, without changing the gateway's stage order or fail-closed/idempotency semantics. [Source: src/Hexalith.ChatBot.Server/Gateway/Stages/AcceptedCommandDispatcher.cs; src/Hexalith.ChatBot.Server/Gateway/CommandGateway.cs]
2. **There is no UI and no surface-origin attribution.** No `Hexalith.ChatBot.UI` project exists, and `CommandSubmissionWireRequest`/`ChatBotCommandSubmission`/`AuditEnvelope` carry no origin. Story 1.9 adds the minimal Blazor shell and threads origin from the adapter boundary into the audit envelope, immutably (FR85/S7). [Source: src/Hexalith.ChatBot.Server/Gateway/CommandSubmissionWireRequest.cs; Hexalith.ChatBot.slnx]

The gateway pipeline already implemented (verified in `CommandGateway.cs`) runs: authenticate → tenant-bind → authorize → `riskClassifier.Classify` (PassThrough) → `approvalGate.Evaluate` (PassThrough) → `idempotencyStore.RecordAdmission` → `lifecycleTransitionGuard.ValidateCommandSubmission` (Received→Proposed) → `auditWriter.RecordPreCommit` → `dispatcher.DispatchAsync` → `idempotencyStore.RecordOutcome` → `auditWriter.RecordPostCommit` → `operationStatusStore.Upsert`. Story 1.9 changes ONLY the dispatch body (make EventStore real) and ADDS origin attribution; it must not reorder or weaken any stage. [Source: src/Hexalith.ChatBot.Server/Gateway/CommandGateway.cs; src/Hexalith.ChatBot.Server/Program.cs]

### The trivial command (read carefully — a real decision)

The architecture's M0 allowlist names **exactly one** command: `Project.AppendConversationMessage` (addendum §Command Allowlist v0). **That is the AI-action execution allowlist** — the command the *AI mediation + approval* vertical loop exercises (Epic 4), and it is a write into `Hexalith.Conversations` bounded to an *associated project* (which requires email intake + association from Epics 2–3). It is therefore **not buildable as the Story 1.9 walking-skeleton command** — there is no project, conversation, or association at this point in Epic 1.

Story 1.9's command must be **self-contained** so the skeleton is "provably complete before feature work begins." Recommendation: a ChatBot-owned trivial governed command — `RecordGovernedNote` → event `GovernedNoteRecorded` → `GovernedOperationAggregate`/`GovernedOperationState` → projection `GovernedOperationView` in `chatbot-statestore` — placed on a **hardcoded M0 spine allowlist** distinct from the AI-action allowlist. This exercises every real stage (tenant-partition, fail-closed audit, coarse+fine idempotency, lifecycle Received→Proposed, EventStore execute→publish→project, post-commit audit, origin attribution) with zero sibling-aggregate dependency. The dev may choose a different trivial command identity, but it MUST be: imperative-named (no `Command` suffix), ChatBot-owned, in-tenant, append-only, on the allowlist, and free of Epic 2–4 dependencies. Record the chosen command in the Dev Agent Record.

Two allowlists, do not conflate: addendum §Command Allowlist v0's `Project.AppendConversationMessage` is the **AI-action execution allowlist** (which commands an approved AI action may run — Epic 4), governed by the addendum's change-control clause (PRD update + decision-log entry + re-validation). Story 1.9's **spine allowlist** is an orthogonal mechanical gate proving the gateway rejects non-allowlisted commands fail-closed; it is not the AI-action allowlist and does not alter it. Add a brief `.decision-log.md` note recording the spine-allowlist's trivial command so a reviewer does not read it as bypassing the addendum's change-control. [Source: addendum.md#Command Allowlist v0; architecture.md#Governed AI Mediation; _bmad-output/planning-artifacts/epics.md#Story 1.9]

### EventStore write path (sibling pattern — do not reinvent)

Reuse the canonical sibling pattern; do not invent a new event-sourcing approach. **Use Pattern A** (mirror `ConversationAggregate`), the simplest fit for a trivial command:

- Aggregate (the processor): `GovernedOperationAggregate : EventStoreAggregate<GovernedOperationState>` with typed `public static DomainResult Handle(<command>, GovernedOperationState? state)` and `Apply(<event>)` on the state record. The base `EventStoreAggregate<TState>` already implements `IDomainProcessor.ProcessAsync` and reflection-discovers `Handle`/`Apply` — so **there is no separate domain-processor class**. `Handle` returns `DomainResult.Success(IEventPayload[])` or `DomainResult.Rejection(IRejectionEvent[])`. [Source: Hexalith.Conversations/src/Hexalith.Conversations/Aggregates/ConversationAggregate.cs; Hexalith.EventStore/src/Hexalith.EventStore.Client/Aggregates/EventStoreAggregate.cs]
- (Why not Pattern B: `Hexalith.Folders` uses a plain `static class FolderAggregate` + a hand-written `FolderDomainProcessor : IDomainProcessor` because it orchestrates many services. That is overkill here and must not be combined with inheriting the base class — pick Pattern A only.) [Source: Hexalith.Folders/src/Hexalith.Folders/Aggregates/Folder/FolderAggregate.cs; Hexalith.Folders/src/Hexalith.Folders.Server/FolderDomainProcessor.cs]
- Events: sealed, past-tense records implementing `IEventPayload` (and `{Target}{Reason}Rejection : IRejectionEvent`); **payload-only, no envelope metadata** (EventStore owns correlation/causation/tenant/persistence/publish/snapshots/projection-invalidation). No transient data (timestamps, display names) in the event payload. These types live in `.Server` (they reference `EventStore.Contracts`), mirroring `Hexalith.Conversations.Events`. [Source: Hexalith.Conversations/src/Hexalith.Conversations/Aggregates/ConversationAggregate.cs; Hexalith.EventStore/_bmad-output/project-context.md]
- Projection: handler subscribes to the published event and writes the tenant-partitioned read model to `chatbot-statestore`; idempotent + order-tolerant (version-stamped). [Source: Hexalith.Folders/src/Hexalith.Folders.Server/FoldersTenantEventHandler.cs; architecture.md#Communication Patterns]
- The Server csproj currently references only `Hexalith.EventStore.Contracts`; add `Hexalith.EventStore.Client` (+ server/actor host as needed) via `$(HexalithEventStoreRoot)`. [Source: src/Hexalith.ChatBot.Server/Hexalith.ChatBot.Server.csproj]

### Surface-origin attribution (FR85 / S7)

Origin is **provenance, declared by the adapter at the boundary** (not a security control inferred server-side). The UI declares `ui`; a raw API caller declares `api` (or it defaults to `api`). Capture it once when constructing the immutable `ChatBotCommandSubmission` in `Program.cs`, validate against a closed surface enum, and write it into the audit envelope. Immutability is structural: `ChatBotCommandSubmission` → `ChatBotGatewayContext` → `AuditEnvelope` are records constructed at the boundary and never rewritten by a stage. S7's *attribution view* is M1; M0 only needs the attribution to be captured and audited immutably. Add a test proving a downstream stage cannot change origin and that an absent/unknown origin defaults safely and is still audited. [Source: prd.md#S7; architecture.md#Communication Patterns; src/Hexalith.ChatBot.Server/Gateway/ChatBotCommandSubmission.cs; src/Hexalith.ChatBot.Server/Audit/AuditEnvelopeFactory.cs]

Two ripple effects to plan for: (1) `AuditEnvelope` is an 18-parameter **positional record** built at multiple `AuditEnvelopeFactory` call sites (`Create`/pre-commit, post-commit, `RejectedLifecycleTransition`); adding `surfaceOrigin` changes the constructor and every call site, and the audit-completeness assertions (`CommandGatewayTests`, ~lines 405–422) plus the `RedactionDecision == "metadata_only"` and leakage-sentinel checks must stay green. Prefer appending the field to avoid reordering. (2) `IChatBotClient.SubmitAsync` has no origin parameter today; adding `ui`/`api` means a new optional parameter or overload on `IChatBotClient`/`ChatBotClient`, the OpenAPI `origin` field, NSwag regeneration, and the sha256 fixture refresh — verify no existing `SubmitAsync` caller/test breaks. [Source: src/Hexalith.ChatBot.Server/Audit/AuditEnvelope.cs; src/Hexalith.ChatBot.Server/Audit/AuditEnvelopeFactory.cs; src/Hexalith.ChatBot.Client/IChatBotClient.cs; tests/Hexalith.ChatBot.Server.Tests/Gateway/CommandGatewayTests.cs]

### Architecture Guardrails

- **One spine, no second pipeline.** Every state mutation routes through `CommandGateway` in the fixed order; the UI/adapters construct only `IChatBotCommand` and call `IChatBotClient.SubmitAsync`. Adapters MUST NOT touch `IRiskClassifier|IApprovalGate|IAuditWriter|IIdempotencyStore` or `DispatchAsync` (NetArchTest, compile-time). [Source: architecture.md#Process Patterns; architecture.md#Enforcement Guidelines]
- **Fail-closed is real.** Pre-commit audit unavailable / tenant unresolved / authz failure / command-not-in-allowlist → typed rejection, **zero durable state**, replay intent queued, operator alert. Never an "audit unavailable → continue" branch. New write path stays on the single audit-commit seam. [Source: architecture.md#Process Patterns; prd.md#NFR15a]
- **Aggregate `Handle` is pure**; never throw for business-rule violations (return `DomainResult` rejection so the idempotency cache is honored); no sibling-client calls inside `Handle`; backward-compatible event deserialization (additive + upcasting, no `V2` types). [Source: architecture.md#Process Patterns]
- **Events & projections.** Persist-then-publish (never publish before persistence); DAPR pub/sub is at-least-once + unordered → all handlers idempotent + order-tolerant; projection reads surface `stale|rebuilding|unavailable`, never a premature freshness/Done. [Source: architecture.md#Communication Patterns]
- **Metadata-only everywhere.** No command payloads, tenant/project/file/party names, secrets, tokens, local paths, or raw exception text in events, logs, traces, spans, audit envelopes, status/UI responses, OpenAPI examples, or test snapshots. Raw error text to a user is a release-blocking defect (NFR40). [Source: architecture.md#Format Patterns; prd.md#NFR40]
- **Reuse stable vocabularies.** `LifecycleState` (`Received|Proposed|…`), health strings (`healthy|degraded|failed|unknown`), `ChatBotMessageCodes`/`NextActions`/`DisabledActionReasons`, RFC 9457 problem shape — reference, never fork; never derive status from counts. [Source: src/Hexalith.ChatBot.Contracts/Enums/; src/Hexalith.ChatBot.Contracts/Messages/]
- **Identity & time.** ULIDs only (`Ulid.TryParse`, never `Guid`); EventStore identity `{tenant}:chatbot:{aggregateId}`; DAPR names `chatbot` / `chatbot-eventstore` / `chatbot-statestore` / `chatbot.events` / `deadletter.chatbot.events`; `DateTimeOffset` UTC via `ISystemClock`, `{Action}At` naming, no `DateTime.Now`/`.ToLocalTime()`/`TimeZoneInfo.ConvertTime*` in `.Server`/`.Contracts`. [Source: architecture.md#Naming Patterns; architecture.md#Format Patterns]
- **Generated client is NSwag-only**; never hand-edit `Generated/`; regenerate + refresh `tests/fixtures/hexalith-chatbot-generated-client.sha256` on any contract change. Central package management only; no inline versions. [Source: _bmad-output/implementation-artifacts/1-8-...md]
- **Submodules.** Use only root-declared submodules; never `--recursive`; never initialize nested submodules. [Source: CLAUDE.md#Git Submodules]
