## What Went Well

- The service-client foundation made automation least-privilege instead of piggybacking on UI roles or project-owner membership.
- Story 5.1 kept identity and grants layered correctly: Keycloak authenticates the service account, while ChatBot owns command/query authorization, surface binding, expiry/revocation, and audit evidence.
- The CLI implementation stayed thin. It uses the generated client facade, maps state-changing verbs to existing typed commands, and preserves partial-success honesty when audit/projection reconciliation is pending.
- The MCP implementation treated tool exposure as a narrowing adapter catalog, not as authorization. Backend service-client grants remain authoritative.
- Adapter-boundary fitness tests now load CLI and MCP assemblies and reject direct references to server/gateway/governance/data-plane internals.
- Story 5.4 upgraded parity from aspiration to evidence by driving production CLI/MCP translation paths in conformance tests and comparing contract-level outcomes instead of presentation strings.
- Review auto-fixes were concrete and useful: service-client actor spoofing, grant identity mismatch, CLI safe-denial metadata, MCP malformed argument handling, and story/status traceability were all tightened before completion.

## Challenges

- Service-client identity classification had subtle spoofing risk. Review found that service-account posture needed to override conflicting human-looking actor-type claims.
- Grant validation needed exact identity binding. A grant whose service-client ID did not match the authenticated service-client identity now fails closed.
- CLI output initially under-reported accepted-command partial-success metadata and collapsed typed backend problem details into generic HTTP buckets.
- MCP direct invocation initially accepted malformed JSON object/list argument shapes too far into command construction. The adapter now rejects those before command submission.
- The conformance harness had to avoid two weak extremes: black-box response-code checks and duplicated adapter mapping in tests. The final version records production-adapter translations while comparing first-class contract facts.
- Story hygiene still needed review reinforcement. File lists, test summaries, and sprint-status rows required explicit reconciliation during final review.
- Planning-era docs lagged implementation. Architecture still mentioned M0 shims as the active harness and listed Keycloak service-account flows / full CLI/MCP harness wiring as M1 details after Epic 5 had implemented them.

## Key Insights

1. Cross-surface parity is an adapter-boundary property, not a UI feature. CLI and MCP must be boring translators over the same client seam.
2. `ChatBotSurfaceOrigin` is provenance and audit attribution, not authorization. Grants still need actor, tenant, surface, command/query, expiry, revocation, and delegation evidence.
3. Safe denial fidelity matters for machine surfaces. Losing catalog codes, client actions, retryability, or redaction visibility in CLI/MCP is a parity defect even when the backend denial was correct.
4. MCP tool catalogs are exposure metadata only. They narrow what the adapter offers but cannot replace service-client grants or the command spine allowlist.
5. Differential conformance must compare canonical outcomes: typed commands, read facts, admission/audit facts, state-store end-state, and non-vacuity checks. Exit codes and transport envelopes are insufficient.
6. Story review must reconcile source/test/docs/status changes explicitly. Epic 5 repeatedly improved after changed-file and story-file-list audits.
